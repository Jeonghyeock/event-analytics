# 측정 결과

같은 PC(i5-13600K, 64GB, PostgreSQL 18.6 기본 설정: `shared_buffers` 128MB, `max_connections` 100)에서 잰 숫자다. 절대 처리량을 주장하지 않고, 같은 장면의 비교로만 쓴다. 원본은 `load/results/`(gitignore)에 둔다.

## 2단계: 기본 데이터(2026-10-27)

`npm run load:generate -w @event-analytics/api -- --events 10000000 --days 90 --seed 1 --end-day 2026-10-27`

| 항목 | 값 |
|---|---|
| 이벤트 | 1,000만 건, 2026-07-29 ~ 2026-10-26(90일) |
| 넣은 시간 | 276초(초당 약 3.6만 건, 연결 하나, 배치 1,000건) |
| 크기 | 2.0GB(데이터 1,535MB, 인덱스 482MB), 파티션 98개 |

- 1단계의 중복 제거 측정(초당 9.3만 건)보다 느리다. 그때는 행이 작았고 배치마다 하루 안의 시각이었다. 생성기는 배치 하나가 90일에 흩어져 배치마다 여러 파티션의 키 인덱스를 건드린다.

## 2단계: 떼기 리허설(합격 기준 A4, 2026-10-27)

`npm run load:detach-rehearsal -w @event-analytics/api`

장면(세 회차가 같다):
- 개발 DB를 복제한 DB(13~14초)에 API를 따로 띄운다.
- 수집을 40초 동안 초당 2,000건으로 보낸다. 배치는 200건이고 0.1초 간격이다. 앞 요청이 끝나길 기다리지 않는 열린 모형이고, 배치는 시작 전에 만들어 둔다.
- 5초에 오래 도는 리포트를 건다. 앱 role의 트랜잭션에서 `select count(*) from events`를 한 뒤 20초 동안 연 채로 둔다.
- 8초에 가장 오래된 파티션(2026-07-29)을 뗀다. 기준선은 떼지 않는다.
- 뗐는지는 끝난 뒤 DB에 묻는다(`to_regclass`). 관리 작업은 오류 없이 그 날을 지웠고, 앞으로 쓸 날 하나(11-04)를 `ATTACH`로 만들었다.

떼기 구간에 보낸 요청이다. 떼기 구간은 8초부터 떼기가 끝날 때까지다(관리 작업은 만들기·떼기·지우기 전체이고, 기준선은 리포트가 끝날 때까지다).

| 회차 | 요청 | 응답 | 지연 p50 | p99 | 최대 | 떼기 구간 |
|---|---|---|---|---|---|---|
| 기준선(떼지 않음) | 176 | 200 × 176 | 4.8ms | 6.2ms | 6.2ms | 17.7초 |
| 관리 작업(`db:maintain`) | 176 | 200 × 176 | 4.8ms | 7.1ms | 7.6ms | 17.7초 |
| 일반 `DETACH`(`lock_timeout = 0`) 뒤 `DROP` | 177 | 200 × 60, **503 × 117** | 5,002ms | 7,947ms | 7,947ms | 17.7초 |

- 일반 `DETACH`의 503 원인: DB 쪽 50건(잠금 대기·교착·문장 시간 초과), 풀 연결 대기 초과 67건. 지연의 p50은 대부분 503이 나기까지 걸린 시간이다.
- 40초 전체로 보면 기준선과 관리 작업은 400건 모두 200이다. 일반 `DETACH`는 400건 가운데 503이 117건이다.
- 리허설은 세 번 돌렸다. 기준선 없이 한 번, 기준선을 더해 한 번, 리뷰 반영 뒤 데이터를 다시 만들어 한 번이다. 503 수는 116, 116, 117이고, 관리 작업의 5xx는 늘 0이었다. 위 표는 마지막 회차다.

해석:
- **두 방식 모두 리포트가 끝날 때까지 기다렸다.** 다른 것은 그동안 수집이 어떻게 되었느냐다.
- **관리 작업은 수집에 5xx가 0건이었고, 지연도 기준선과 같았다**(합격 기준 A4).
  - `CONCURRENTLY`가 부모에 거는 `ShareUpdateExclusiveLock`은 INSERT의 `RowExclusiveLock`과 부딪히지 않는다.
  - 기다림은 리포트의 트랜잭션(`virtualxid`)에만 걸린다.
- **일반 `DETACH`**는 부모를 `AccessExclusiveLock`으로 잠그려고 리포트 뒤에 줄을 섰다. 그 뒤로 수집 INSERT가 줄을 섰다.
  - INSERT는 잠금 대기 한도(3초)에 닿아 503 `busy`가 되었다.
  - 막힌 요청이 연결을 3초씩 쥐어 풀(10개)이 찼다. 그 뒤 요청은 연결을 5초 기다리다 503이 되었다. 최대 7.9초다.
  - 리포트가 끝나기 몇 초 전에 보낸 요청은 성공했다(200 × 60). 잠금이나 연결을 기다리는 사이에 리포트가 끝나 떼기가 지나갔기 때문이다.
- 503은 다시 보내면 되는 응답이라 보내는 쪽 계약상 데이터는 잃지 않는다(DESIGN 6.1). 다만 18초 동안 수집이 멈춘 것과 같다.

## 3단계: 원본에서 세는 리포트 시간(2026-10-27)

`npm run load:report-bench -w @event-analytics/api -- --runs 3 --as-of 2026-10-27T12:00:00Z --explain`

API와 같은 길(`runReport`, 리포트 SQL 그대로, `LIMIT` 포함)로 개발 DB의 1,000만 건을 센다. 리포트마다 첫 회차를 따로 두고 그 뒤 세 번의 가운데 값을 적는다. 시간대는 Asia/Seoul이다.

| 리포트 | 행 | 첫 회차 | 가운데 값 |
|---|---|---|---|
| 30일 일별, 이벤트 | 30 | 1,297ms | 1,567ms |
| 30일 일별, 이벤트 + 사용자 | 30 | 4,065ms | 4,127ms |
| 90일 캠페인별 합계, 이벤트 | 201 | 699ms | 622ms |
| 90일 캠페인별 합계, 이벤트 + 사용자 | 201 | 15,159ms | 14,771ms |
| 7일 시간별 × 플랫폼, 이벤트 + 사용자 | 504 | 1,344ms | 1,258ms |
| 하루 시간별, 이벤트 + 사용자 | 24 | 128ms | 127ms |

실행 계획(`EXPLAIN (ANALYZE, BUFFERS)`, 원본은 `load/results/`)에서 본 것:
- **90일 캠페인별, 이벤트만(0.6초)**: 병렬 부분 해시 집계다(작업자 2, `Partial HashAggregate` 201무리). 990만 행을 읽지만 무리가 적어 메모리 40KB로 센다.
- **같은 리포트에 사용자를 더하면(14.8초, 24배)**: `count(distinct)`는 부분 집계를 할 수 없어 병렬이 꺼진다. 990만 행을 (캠페인, 사용자)로 디스크에서 정렬한다(external merge, 251MB).
- **30일 일별, 이벤트만(1.6초)**: 무리가 30개뿐인데 해시 집계가 아니라 333만 행을 디스크에서 정렬한다(39MB). 계획기가 `date_trunc(…, 시간대)`로 묶은 무리 수를 행 수만큼으로 어림하기 때문이다(설계 리뷰가 본 것: 333만 vs 실제 30). 병렬도 쓰지 않는다.
- 첫 회차와 그 뒤가 비슷하다. 2GB가 `shared_buffers`(128MB)에 들어가지 않아 매번 그 밖(OS 캐시나 디스크)에서 읽는다(`shared read`).

4단계(집계 표)가 줄일 것이 여기서 정해진다.
- 고유 사용자 수: 행마다 정렬하는 비용을 미리 줄인 표(사용자 × 일)로 옮긴다.
- 이벤트 수: 시간별로 미리 센 표를 읽으면 무리 어림과 정렬이 사라진다.

## 4단계: 시간 집계 표(2026-10-27)

**채우기**: `npm run rollup:run -w @event-analytics/api`가 보관 기간의 시작(07-29 0시 UTC)부터 끝난 시간(10-27 13시)까지 2,173시간을 하루 조각 91개로 40.2초에 채웠다.

| 표 | 행 | 크기 |
|---|---|---|
| `events`(데이터가 든 파티션 90개, 전체 98개) | 10,000,000 | 2,021MB |
| `hourly_rollup` | 3,849,379 | 694MB(표 334MB + 유일 인덱스 360MB) |

행이 2.6배만 준다. 시간 × 차원 다섯(이벤트 이름, 플랫폼, 나라, 채널, 캠페인 200개)의 조합이 한 시간 안에서 거의 겹치지 않기 때문이다. 그래서 집계 표가 빠른 까닭은 리포트마다 다르다(아래 실행 계획). 일·시간 묶음은 계획(무리 수 어림)의 차이이고, 90일 캠페인별은 읽는 행의 차이다.

**autovacuum**: 개발 DB의 표는 autovacuum이 한 번도 처리하지 않았다(`last_autoanalyze`·`last_autovacuum`이 모두 비어 있고 횟수 0, 설정은 기본값으로 켜짐, 서버는 10-21부터 켜져 있음). 그래서 `hourly_rollup`은 통계가 없었다. 코드 리뷰 때 집계 표 경로가 원본보다 느렸던 것(90일 캠페인별 3.7초 vs 0.6초, 리뷰가 잰 값)은 이것과 집계 표 쪽을 먼저 묶지 않은 것, 둘 때문이다. 측정 전에 소유자로 `ANALYZE`했다.
- 서버 로그에는 테스트가 DB를 지울 때 자동 청소 프로세스가 끊긴 기록(오늘 16번)이 있다. 다른 DB의 표를 처리한 작업자의 기록도 한 줄 있다. 작업자는 돈다는 뜻이라, 왜 이 DB에는 오지 않는지가 7단계의 질문이다. 서버 설정은 바꾸지 않는다.
- autovacuum이 고쳐져도 분할 표의 부모(`events`)는 분석하지 않는다(PostgreSQL이 분할 표의 부모를 처리하지 않음). 원본의 무리 어림(333만)을 만든 부모 통계는 손으로 한 `ANALYZE`에서 왔다. 부모 `ANALYZE`는 따로 해야 한다(7단계).

**리포트 시간**: `npm run load:report-bench -w @event-analytics/api -- --runs 3 --as-of 2026-10-27T12:00:00Z --explain`(그리고 `--raw`). 3단계와 같은 방법으로 재고, 가운데 값(ms)을 적는다. 이벤트만 묻는 두 리포트(7일, 하루)를 더했다. 이번 결과 파일의 계획은 비용을 끈 것이라, 아래 어림(333만·2,152)은 비용을 켠 `EXPLAIN`을 따로 돌려 봤다(도구는 이제 비용과 워터마크도 남긴다).

| 리포트 | 3단계(원본, `count(distinct)`) | 4단계 원본(`--raw`) | 4단계 |
|---|---|---|---|
| 30일 일별, 이벤트 | 1,567 | 1,404 | **232**(집계 표) |
| 30일 일별, 이벤트 + 사용자 | 4,127 | 3,049 | 3,029(원본, 두 단계) |
| 90일 캠페인별 합계, 이벤트 | 622 | 649 | **265**(집계 표) |
| 90일 캠페인별 합계, 이벤트 + 사용자 | 14,771 | 3,763 | **3,831**(원본, 두 단계) |
| 7일 시간별 × 플랫폼, 이벤트 | — | 567 | **77**(집계 표) |
| 7일 시간별 × 플랫폼, 이벤트 + 사용자 | 1,258 | 830 | 793(원본, 두 단계) |
| 하루 시간별, 이벤트 | — | 51 | **16**(집계 표) |
| 하루 시간별, 이벤트 + 사용자 | 127 | 84 | 63(원본, 두 단계) |

- 사용자를 묻는 리포트는 4단계에서도 원본이다. 가운데 두 열의 차이는 잡음이고, 3단계(`count(distinct)`)와의 차이가 두 단계 `GROUP BY`의 효과다(90일 캠페인별 14.8초 → 3.8초, 30일 일별 4.1초 → 3.0초).
- 잡음의 크기: 30일 일별 이벤트 `--raw`의 세 회차가 1,130 / 1,404 / 1,945ms다.
- 모든 리포트의 기간 끝(10-26 15:00 UTC)이 워터마크(10-27 13시) 앞이라, 집계 표 경로의 원본 꼬리는 계획에서 통째로 빠졌다(꼬리의 비용은 재지 않았다). 실제로는 꼬리가 1시간 이내다(작업은 지금의 UTC 정시까지 세고 1분마다 돈다).
- 이벤트만 묻는 네 리포트는 두 경로의 행이 값까지 같았다(따로 견줌. 결과 파일에는 행 수만 남는다).
- 3단계 기록이 적은 "사용자 × 일 표"는 두지 않았다. 차원 없는 리포트만 돕기 때문이다(DESIGN 6.4). 대신 원본에서 두 단계 `GROUP BY`로 센다.

실행 계획에서 본 것:
- **30일 일별, 이벤트: 원본 1.4초 → 집계 표 0.23초.** 원본은 333만 행을 디스크에서 정렬한다(39MB). 계획기가 `date_trunc(…, 시간대)`의 무리 수를 `occurred_at`의 서로 다른 값 수로 어림하기 때문이다(333만, 실제 30). 집계 표의 `hour`는 서로 다른 값이 2,160개뿐이라 2,152로 어림하고(실제 30), 병렬 부분 해시 집계(작업자 2, 105KB)가 된다. 집계 표 경로는 385만 행을 다 훑고 거른다. 그래도 정렬이 없어 빠르다.
- **90일 캠페인별, 이벤트: 0.65초 → 0.27초.** 둘 다 병렬 부분 해시 집계다. 읽는 행이 990만에서 385만으로 준 만큼 빠르다.
- **하루 리포트는 원본 파티션을 계획하지 않는다.** 워터마크를 매개변수로 넘겨 원본 꼬리 [max(시작, 워터마크), 끝)가 비는 것을 계획할 때 안다(코드 리뷰 전에는 서브쿼리라 91개 파티션을 계획했다).
- **사용자 리포트는 메모리 한도에 막힌다.** 해시 집계는 `work_mem` × `hash_mem_multiplier`(4MB × 2 = 8MB), 정렬은 `work_mem`(4MB)까지다.
  - 90일 캠페인별은 (캠페인, 사용자) 208만 무리를 해시로 묶다 17개 배치로 나눠 디스크에 쓴다(리더와 작업자 둘, 프로세스마다 64~97MB). 정렬도 디스크다.
  - 30일 일별은 계획기가 병렬을 고르지 않는다((날, 사용자) 무리를 행 수만큼 어림). 해시 집계가 65개 배치로 127MB를 쓴다.
  - 7단계에서 리포트 트랜잭션의 `work_mem`을 올려 본다.
