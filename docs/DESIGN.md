# 이벤트 분석 대시보드 — 설계 문서

> 상태: 확정(2026-10-27, 사용자 "그대로해줘"). 단계마다 설계 PR에서 자세히 정하고, 결과는 PROGRESS.md에 쓴다.

## 1. 목표

마케터가 앱·웹의 행동 이벤트를 **어떻게 볼지 설정**해 그래프와 표로 보는 리포트 대시보드의 뒷단을 만든다. AB180에서 앞단(화면)을 맡았던 리포트 대시보드의 반대쪽이다. 다음을 지킨다.

1. 이벤트를 빠짐없이, 한 번만 저장한다. 같은 배치가 다시 오거나, 이벤트가 늦게 와도 그렇다.
2. 리포트 설정(지표 × 차원 × 필터 × 기간 × 단위)을 안전한 SQL로 바꾼다. 결과는 작은 데이터에서 손으로 센 값과 같다.
3. 수천만 건에서도 리포트가 빠르다. 시간 파티션, 집계 표(rollup), 실행 계획으로 보인다.
4. 퍼널(단계의 순서와 전환 기간)과 리텐션을 낸다. 생성기 데이터로는 다섯 단계(목록 → 좌석 지도 → 선점 → 주문 → 결제), seat-booking의 서버 이벤트로는 세 단계(선점 → 주문 → 결제) 예매 퍼널을 그린다(조회는 보내지 않는다, 10장 65).
5. 위 넷을 테스트와 측정 **숫자**로 보인다. 숫자는 수집 처리량, 리포트 p95, 원본과 집계 표의 일치다.

**왜 PostgreSQL인가.** 분석에는 컬럼형 DB(ClickHouse 등)가 더 맞다는 것을 알고 PostgreSQL을 쓴다. 이 프로젝트의 목적은 PostgreSQL을 많은 데이터에서 운영하는 것이다(파티션, 집계, 파티션 가지치기, 튜닝). 그래서 주장도 "분석 DB를 골랐다"가 아니다. "PostgreSQL에서 파티션과 집계로 N천만 이벤트의 리포트를 X ms 안에 냈다"이다.

### 이력서 주장과 근거

| 쓸 수 있게 될 주장 | 근거(단계) |
|---|---|
| 재전송·중복 배치에도 이벤트를 한 번만 저장했다 | 수집 멱등 테스트(1) |
| 일 단위 파티션으로 리포트가 필요한 날만 읽게 했다. 보관 기간이 지난 파티션은 쓰기를 막지 않고 뗐다 | 실행 계획, 수집 중 리허설(2) |
| 화면의 리포트 설정을 허용 목록 기반의 매개변수 SQL로 바꿨다 | 쿼리 빌더 테스트(3) |
| 시간 집계 표로 리포트 시간을 X → Y ms로 줄였다. 원본과 같은 값임을 테스트로 보였다 | 측정표와 일치 테스트(4) |
| 부하 중 리포트 p95를, 측정이 가리킨 병목을 고쳐 X → Y로 줄였다 | 같은 날 번갈아 잰 전후(7) |
| seat-booking의 업무 이벤트(선점·주문·결제)를 outbox로 빠짐없이 받아 예매 퍼널을 그렸다 | 연결 테스트·리허설(8) |

## 2. 하지 않을 것

- **수집 SDK나 실제 앱은 없다.** 이벤트는 생성기와 seat-booking의 outbox가 보낸다.
- **어트리뷰션 계산은 없다.** 광고 클릭과 설치를 맞추는 일은 AB180 제품의 핵심이지만 범위를 넘는다. 채널·캠페인은 이벤트에 붙어 온다고 본다.
- **컬럼형 DB, Kafka, Redis, 스트림 처리는 없다.** PostgreSQL만으로 어디까지 되는지 잰다.
- **여러 고객(테넌트)은 없다.** 앱은 하나다.
- **로그인은 없다.** 로컬 도구다. 수집 API만 쓰기 키로 지킨다.
- **배포는 없다.** 로컬과 CI로 끝낸다(seat-booking과 같음).
- **화면은 최소로 한다.** 리포트 설정, 그래프와 표, 퍼널까지다. 대시보드를 꾸미거나 공유하는 기능은 없다.

## 3. 합격 기준

모든 기준은 앱 로그가 아니라 **DB를 직접 조회하는 SQL**로 확인한다.

| # | 상황 | 통과 조건 |
|---|---|---|
| A1 | 같은 배치를 다시 보내거나, 한 배치 안에 같은 `event_id`가 있음 | `event_id`마다 한 번만 저장한다. 응답에 받은 수·새로 넣은 수·중복 수가 있다 |
| A2 | 받을 수 있는 기간 밖의 이벤트(너무 늦거나 미래) | 이유와 함께 거절한다. 조용히 버리지 않는다 |
| A3 | 하루 범위의 리포트 | 실행 계획이 그날의 파티션만 읽는다 |
| A4 | 보관 기간이 지난 파티션 떼기 | 수집이 도는 중에도 쓰기 오류가 0이다. 대기 시간을 숫자로 남긴다 |
| A5 | 리포트 결과 | 작은 고정 데이터에서 손으로 센 값과 같다. 집계 표의 결과가 원본의 결과와 같다 |
| A6 | 늦게 온 이벤트 | 다음 집계 뒤 집계 표와 원본이 다시 같다 |
| A7 | 부하 중 리포트 | p95를 개선 전후로 잰다(숫자). 개선은 측정이 가리킨 병목이다 |
| A8 | seat-booking의 이벤트 | outbox로 빠짐없이 한 번 이상 오고, 저장은 한 번이다 |

## 4. 구조

```
[브라우저: React + Vite]
        │  REST(JSON)
[API 서버: Fastify] ── POST /ingest(쓰기 키) ── POST /reports/query ── 퍼널·리텐션
        │
[PostgreSQL 18] events(일 단위 파티션) · 시간 집계 표 · 다시 집계할 시간 목록
        ▲
[집계 작업: 명령 또는 서버 안 타이머]    [이벤트 생성기 CLI] → /ingest    [seat-booking outbox 릴레이] → /ingest
```

- seat-booking과 같은 PostgreSQL 서버에 DB를 따로 둔다(`event_analytics`). role도 따로 둔다(소유자, 앱).
- 저장소 구조는 seat-booking과 같다: `apps/api`, `apps/web`, `packages/shared`(zod), `load/`.

## 6. 핵심 결정 (단계마다 설계 PR에서 자세히)

### 6.1 수집 (1단계 설계)

**정확히 한 번은 약속하지 않는다.** 보내는 쪽은 응답을 못 받으면 같은 배치를 다시 보낸다("한 번 이상"). 받는 쪽은 `event_id`로 중복을 걸러 한 번만 저장한다(멱등 저장). 둘을 합치면 저장 결과는 정확히 한 번과 같다.

**요청.** `POST /ingest`, 헤더 `X-Write-Key`, 본문 `{ "events": [ … ] }`(1~1,000건, 본문 6MiB까지).

**이벤트 한 건**(`packages/shared`의 `IngestEvent`)

| 필드 | 규칙 | 열 |
|---|---|---|
| `eventId` | UUID(버전은 묻지 않는다. 보내는 쪽에는 v7을 권한다) | `event_id uuid` |
| `occurredAt` | ISO 8601, 오프셋 필수(`Z`, `+09:00`) | `occurred_at timestamptz`(밀리초) |
| `userId` | 1~128자(익명 id) | `user_id text` |
| `eventName` | 영문 소문자로 시작, 소문자·숫자·밑줄, 64자까지 | `event_name text` |
| `platform` | `ios` · `android` · `web` | `platform text` + CHECK |
| `country` | 대문자 두 글자(ISO 3166-1) 또는 없음 | `country text` |
| `channel`, `campaign` | 1~128자 또는 없음 | `channel`, `campaign text` |
| `properties` | 객체, 객체·배열 10단계까지, JSON으로 UTF-8 4KiB까지, 없으면 `{}` | `properties jsonb` |

- 모르는 필드가 있으면 그 이벤트를 거절한다. 조용히 버리면 보내는 쪽의 오타가 데이터 손실이 된다.
- **문자열은 NUL(`\u0000`)과 짝 없는 서로게이트를 거절한다.** `properties` 안의 키와 값도 그렇다. 확인한 것은 셋이다.
  - NUL은 text(22021)와 jsonb(22P05) 모두에서 배치 전체를 실패시킨다.
  - 짝 없는 서로게이트는 jsonb에서 배치 전체를 실패시킨다(22P02).
  - text에서는 node-postgres가 U+FFFD로 조용히 바꿔 저장한다.
- `properties`의 깊이 한도는 검사가 재귀하지 않게 하려는 것이다. 수천 단계로 중첩된 값은 재귀 검사의 스택을 넘쳐 배치 전체를 500으로 만들었다(리뷰가 재현함). 검사는 반복문으로 하고, 깊이를 먼저 막는다.
- `properties`의 정수는 JSON을 풀 때 JS 숫자가 되므로 2^53을 넘으면 정밀도를 잃는다. 큰 id는 문자열로 보낸다.
- `received_at`은 DB가 넣는다(트랜잭션 시각). 4단계에서 늦게 온 이벤트를 가리는 데 쓴다.
- **시각은 밀리초로 잘라 저장한다**(JS `Date`를 거친 ISO 글자). 보내는 쪽이 처음에는 마이크로초로, 재전송 때는 밀리초로 같은 시각을 쓰더라도 키가 같아진다. 분석에는 밀리초보다 작은 차이가 필요 없다. 반올림하지 않고 잘라서 자정 직전의 이벤트가 다음 날 파티션으로 넘어가지 않는다.

**검사**
- 키가 없거나 틀리면 401이다. 본문을 읽기 전에 본다.
- 봉투가 틀리면 400이다. 본문이 JSON 객체가 아니거나, `events`가 1~1,000개의 배열이 아닌 경우다.
- 본문 어딘가에 `__proto__` 키나 `constructor.prototype`이 있어도 400이다. Fastify가 JSON을 풀 때 거절한다(기본값 `onProtoPoisoning: 'error'`). 프로토타입 오염을 노린 본문이라 배치째 거절한다.
- 본문이 6MiB를 넘으면 413이다. 보통의 글자로 꽉 채운 이벤트는 한 건에 5.6KB쯤이라 1,000건이 들어간다. 이스케이프(`\uXXXX`)를 많이 쓰면 넘을 수 있다.
- **이벤트는 한 건씩 판단한다.** 틀린 이벤트는 이유와 함께 `rejected`에 담고, 나머지는 저장한다. 한 건 때문에 배치를 통째로 거절하면, 보내는 쪽은 그 배치를 끝없이 다시 보내거나 통째로 버려야 한다.
- 거절 이유는 셋이다.
  - `invalid`: 스키마. 어느 필드가 왜 틀렸는지 함께 준다. 같은 배치에 같은 `eventId`가 다른 시각으로 또 있으면 뒤의 것도 `invalid`다(합격 기준 A1: `event_id`마다 한 번).
  - `too_old`: 지금 − 7일보다 앞.
  - `too_far_in_future`: 지금 + 1시간보다 뒤.
  - 경계는 받는다. 받는 범위는 `지금 − 7일 ≤ occurred_at ≤ 지금 + 1시간`이다.
- "지금"은 DB의 트랜잭션 시각이다. 파티션 관리(2단계)와 같은 시계를 쓰고, 한 배치는 한 시각으로 판단한다.

**응답과 보내는 쪽이 할 일**

| 응답 | 뜻 | 보내는 쪽이 할 일 |
|---|---|---|
| 200 | `{ received, inserted, duplicates, rejected: [{ index, reason, message }] }`. `received = inserted + duplicates + rejected 수` | 배치를 지운다. `rejected`는 로그로 남긴다 |
| 400, 415 | 봉투가 틀림(배치 전체) | 다시 보내지 않는다. 따로 보관하고 알린다(보내는 쪽 버그) |
| 401 | 키가 없거나 틀림 | 배치를 지니고 보내기를 멈춘 뒤 알린다. 지우면 잃는다 |
| 413 | 본문이 6MiB를 넘음 | 배치를 반으로 나눠 다시 보낸다 |
| 503 `partition_missing`, `busy` | 다시 보내면 되는 실패. 아무것도 저장하지 않았다 | 같은 배치를 간격을 늘리며 다시 보낸다 |
| 500, 네트워크 오류, 시간 초과 | 알 수 없음. 저장됐을 수도 있다 | 같은 배치를 다시 보내되, 횟수를 정해 두고 넘으면 따로 보관한다 |

- `rejected`는 "이 요청이 저장하지 않은 것"이다. 재전송이 받을 기간의 경계를 넘으면, 첫 요청에서 저장된 이벤트가 둘째 요청에서는 `too_old`로 나올 수 있다.
- **알고 받아들이는 손실은 셋이다.**
  - `too_far_in_future`: 기기 시계가 앞선 경우다. 나중에 보내면 받아질 수도 있지만, 보내는 쪽은 200을 받으면 지운다.
  - 파티션 장애가 7일을 넘는 경우다. 그동안 다시 보낸 이벤트는 `too_old`가 된다.
  - 보내는 쪽이 재전송 때 시각을 새로 만드는 경우다. 아래의 `(event_id, occurred_at)` 한계다.
- 파티션이 없을 때 PostgreSQL이 내는 23514는 이렇게 가린다. 부모 표(`events`) 이름이 붙고 제약 이름이 없다(확인함). CHECK 위반은 제약 이름이 있고, 파티션 경계 위반은 파티션 이름이 붙는다. 이것만 503 `partition_missing`으로 바꾼다. 2단계 전이거나 관리 작업이 멈춘 경우다. 기본 파티션이 없으므로 이벤트가 엉뚱한 곳에 조용히 쌓이지 않는다.
- 503 `busy`로 바꾸는 것은 넷이다. 잠금 대기 초과(55P03), 교착(40P01), 문장 시간 초과(57014), 풀에서 연결을 얻지 못함이다. 같은 이벤트를 넣는 다른 트랜잭션을 기다리다 한도에 닿을 수 있다. 그 밖의 오류는 500이다.

**저장**
- 배치 하나를 문장 하나로 넣는다. `INSERT … SELECT FROM unnest($1::uuid[], …) WITH ORDINALITY ORDER BY event_id, occurred_at, 순번 ON CONFLICT (event_id, occurred_at) DO NOTHING`. 들어간 행 수가 `inserted`이고, 받은 것 중 나머지가 `duplicates`다. 문장이 거르는 것은 충돌뿐이라 나머지는 모두 중복이다.
- **키 순서로 넣는다.** 겹치는 두 배치가 서로 반대 순서로 넣으면, 서로 상대가 넣은 키를 기다리는 교착이 난다(리뷰가 재현함). 같은 순서로 넣으면 한쪽만 기다린다. 같은 키가 둘이면 배열에서 앞의 것이 남는다.
- 같은 문장 안의 중복도 DO NOTHING이 거른다(확인함: 같은 키 두 줄을 넣으면 1행).
- 같은 이벤트가 동시에 오면, 뒤의 것은 유일 인덱스에서 앞 트랜잭션이 끝나길 기다린다. 앞이 커밋하면 중복이 되고, 되돌리면 뒤의 것이 넣는다.
- 넣는 방법(`unnest`, 행마다 INSERT, `COPY`)의 비교는 7단계 측정에서 한다.
- 트랜잭션에는 문장 5초, 잠금 대기 3초의 한도를 둔다. 실행기의 1초보다 길다. 그래서 마이그레이션 뒤에 줄 선 수집이 먼저 포기하지 않는다(10장 12).

**쓰기 키**
- `INGEST_WRITE_KEY` 환경 변수다. 32자 이상이어야 하고, 없으면 서버가 뜨지 않는다.
- 비교는 두 값의 SHA-256을 `timingSafeEqual`로 한다. 길이가 달라도 같은 시간이 걸린다.
- 키는 하나다(10장 8). 키를 바꾸는 동안 둘을 함께 받는 기능은 없다. 그래서 바꾸는 동안 보내는 쪽은 401을 받는다. 401이면 배치를 지니고 멈추는 이유다.

**중복 제거: `(event_id, occurred_at)` 기본 키 vs 최근 id 표**(10장 5의 대안, 측정)

같은 조건으로 쟀다. 8일에 퍼진 200만 건을 배치 1,000건씩, 연결 하나로 `unnest`로 넣었다.

| | 초당 저장 | 더 쓰는 공간 | 거르는 범위 |
|---|---|---|---|
| A. 파티션 표의 기본 키 | 92,600건 | 없음(파티션마다 키 인덱스, 합 105MB) | 같은 id + 같은 시각(밀리초) |
| B. 파티션하지 않은 최근 id 표 | 83,200건 | id 표 184MB | 같은 id면 시각이 달라도 |

- B는 A보다 10% 느리다. 모든 쓰기가 파티션하지 않은 표 하나에 모이고, 이 표는 데이터와 함께 커진다. 오래된 id를 지우는 DELETE와 VACUUM도 따로 돌려야 한다. 이 표를 다시 파티션하면, 유일 키에 파티션 키가 들어가야 하는 같은 문제로 돌아온다.
- B가 더 거르는 것은 보내는 쪽이 재전송 때 시각을 새로 만드는 경우뿐이다. SDK는 보통 이벤트를 만들 때 시각을 찍어 큐에 넣는다. 그래서 A로 간다.
- A의 한계는 배치 사이에서 같은 id가 다른 시각으로 오면 두 행이 된다는 것이다. 같은 배치 안에서는 거절로 막고, 배치 사이의 경우는 테스트로 남긴다. 보내는 쪽 계약은 "재전송 때 처음과 같은 `occurredAt`을 보낸다"이다.

**파티션(1단계 범위)**
- 1단계에서 만드는 것은 둘이다. 부모 표와, 날짜 범위의 일 파티션을 만드는 명령(`db:partitions`, 소유자)이다.
- `CREATE TABLE … PARTITION OF`는 부모 표에 `AccessExclusiveLock`을 건다. 오래 도는 리포트 뒤에서 이 잠금을 기다리면, 그 뒤에 수집이 줄을 서 3초 한도에 닿는다. 그래서 명령은 잠금 대기를 1초로 묶고, 닿으면 실패한다(다시 돌리면 된다).
- 테스트 템플릿은 지금 기준 −8일 ~ +2일의 파티션을 만든다.
- 미리 만드는 주기, 보관 기간이 지난 파티션 떼기, `ATTACH`로 잠금을 줄이는 것은 2단계다.

**PR 순서**: 이 설계 → 이벤트 표·공유 스키마·파티션 명령 → `POST /ingest`(A1, A2) → 기록

### 6.2 파티션 (2단계 설계)

**나누는 기준은 `occurred_at`의 일 단위(UTC)로 그대로 둔다**(1단계에서 만든 대로).
- 리포트는 거의 늘 이벤트 시각으로 기간을 거른다. 그래서 기간에 든 날의 파티션만 읽는다(가지치기, 아래 A3).
- 반대안은 `received_at`(받은 시각)으로 나누는 것이다. 늦게 온 이벤트가 지난 파티션에 들어가는 문제는 없다. 대신 이벤트 시각으로 하루를 보는 리포트가 그날부터 7일 뒤까지 여덟 파티션을 읽어야 한다(받을 기간이 7일이라 그날의 이벤트가 7일 뒤까지 온다). 보관 기간도 이벤트 시각이 아니라 받은 시각으로 지워진다.
- 늦은 이벤트의 대가(지난 파티션과 집계를 다시 건드림)는 받을 기간(7일)으로 범위를 묶고, 4단계의 다시 집계로 다룬다.

**가지치기가 되는 조건과 안 되는 조건**(확인함, 10일치 파티션)

| 조건 | 읽는 파티션 |
|---|---|
| `occurred_at >= '…-25 00:00+00' and occurred_at < '…-26 00:00+00'` | 1개 |
| 한국 시각의 하루(`+09`로 같은 식) | 2개(한국의 하루는 UTC로 두 날에 걸친다) |
| 매개변수(`$1`, `$2`)로 같은 식, 일반 계획 | 1개(실행할 때 9개를 뺀다, `Subplans Removed: 9`) |
| `occurred_at::date = '…-25'` | 10개 전부 |
| `(occurred_at at time zone 'Asia/Seoul')::date = '…-25'` | 10개 전부 |

- 파티션 키에 함수나 형 변환을 씌우면 가지치기가 되지 않는다. 가지치기는 `키 연산자 식` 모양의 조건만 쓴다. 변하지 않는 함수여도 키를 감싸면 쓰지 못한다.
- 그래서 리포트(3단계)는 기간을 늘 `occurred_at >= $시작 and occurred_at < $끝`(시각, 반열린 구간)으로 거른다. 리포트 시간대의 날짜를 시각으로 바꾸는 일은 SQL 밖(또는 상수 식)에서 한다.
- **리포트는 이름 없는 문장(node-postgres의 기본)으로 보낸다.** 그러면 매번 값을 아는 계획(custom plan)이라 표 하나와 인덱스 하나만 잠근다. 이름 붙인 문장이나 plpgsql은 몇 번 뒤 일반 계획으로 바뀐다. 일반 계획은 실행할 때 가지를 쳐도 98개 파티션을 모두 잠근다(리뷰가 확인함).
- 합격 기준 A3("하루 범위의 리포트는 그날의 파티션만 읽는다")은 UTC 하루로 본다. 리포트 시간대가 Asia/Seoul이면 두 파티션이 맞다. 둘 다 테스트로 남긴다.

**기본 파티션은 계속 두지 않는다**(확인함).
- 기본 파티션이 있으면 새 파티션을 붙일 때마다 기본 파티션을 `AccessExclusiveLock`으로 잠그고 훑는다. 그동안 거기 들어갈 수집이 멈춘다.
- 기본 파티션에 그 날의 행이 이미 있으면 새 파티션을 만들 수 없다(23514). 행을 옮겨야 한다.
- 받을 기간 밖은 수집이 거절하므로 기본 파티션에 들어갈 정상 이벤트가 없다. 파티션이 없으면 503 `partition_missing`으로 드러나는 편이 낫다(10장 20).

**관리 작업**(`db:maintain`, 소유자, 여러 번 돌려도 같은 결과)

하는 일은 다섯이고, 이 순서로 한다. 한 단계가 실패해도 다음 단계를 돌리고, 하나라도 실패했으면 끝에 실패(종료 코드 1)로 끝낸다. 수집에 가장 중요한 것(만들기)을 먼저 한다.
1. **앞으로 쓸 파티션 만들기.** 오늘(UTC) 기준 7일 전부터 7일 뒤까지 없는 날을 만든다. 1단계의 `CREATE TABLE … PARTITION OF`는 부모 표를 `AccessExclusiveLock`으로 잠근다. 그래서 바꾼다. 따로 표를 만들고(`LIKE events INCLUDING ALL`) `ATTACH PARTITION`으로 붙인다.
   - 부모에는 `ShareUpdateExclusiveLock`만 건다. 수집(INSERT)과 리포트(SELECT)는 막지 않는다(확인함: 열린 INSERT·전체 SELECT 트랜잭션이 있어도 3ms).
   - 만들기와 붙이기는 한 트랜잭션이다. 붙이다 실패하면(ANALYZE 뒤에서 잠금 대기 초과 등) 따로 만든 표도 남지 않는다.
   - 있는지는 이름이 아니라 `pg_inherits`(붙어 있는지)로 본다. 그 날 이름의 표가 붙지 않은 채 있으면(끊긴 작업이 남긴 것) 붙인다. 붙일 때 경계 밖 행이 있는지 PostgreSQL이 훑어 본다.
   - 기본 키 인덱스는 따로 만든 표의 것이 부모 인덱스에 붙는다(다시 만들지 않음, 확인함). 권한은 소유자의 기본 권한으로 붙는다(0단계 테스트).
2. **중간에 끊긴 떼기 마무리.** 떼기가 중간에 끊기면 파티션이 "떼는 중"(`pg_inherits.inhdetachpending`)으로 남는다. 취소, 프로세스 종료, 재부팅, 아래의 시간 한도가 그런 경우다. 떼는 중인 파티션이 있으면 다른 파티션은 뗄 수 없다(55000, 확인함). 그래서 `DETACH PARTITION … FINALIZE`로 먼저 마무리한다.
   - FINALIZE는 DB의 더 오래된 스냅샷이 모두 끝나길 기다린다. 그래서 잠금 대기 1초로 묶는다. 묶지 않으면 기다리는 동안 부모의 `ShareUpdateExclusiveLock`을 쥐어 다음 실행의 ATTACH를 막는다(리뷰가 확인함).
3. **보관 기간이 지난 파티션 떼기.** 오늘 − 90일보다 앞선 날을 `DETACH PARTITION … CONCURRENTLY`로 뗀 뒤 `DROP TABLE`로 지운다. 떼는 중인 것이 남아 있으면 이 단계를 건너뛴다(다음 실행이 마무리부터 한다).
   - CONCURRENTLY는 부모 표에 잠금을 쥔 트랜잭션이 모두 끝나길 기다린다(`virtualxid`). 그 파티션을 읽지 않았어도 기다린다(리뷰가 확인함: 오늘만 읽고 쉬는 트랜잭션도). 그동안 수집과 ATTACH는 막히지 않는다(확인함: 기다리는 중 INSERT 6ms).
   - 잠금 줄은 만들지 않으므로 잠금 대기 한도는 끈다. 대신 문장 시간 한도(5분)를 둔다. 한도가 없으면 열린 채 잊힌 트랜잭션 앞에서 작업이 끝나지 않는다. 그러면 다음 날의 예약 실행이 건너뛰어져(Windows 작업 스케줄러의 기본값) 만들기까지 멈춘다. 한도에 닿으면 파티션은 떼는 중으로 남고, 다음 실행이 마무리한다.
   - 떼고 난 표를 지우는 `DROP`은 그 표만 잠근다.
4. **남은 표 치우기.** 떼었지만 지우지 못한 표(`DROP` 직전에 끊긴 것)를 지운다. 이름이 `events_pYYYYMMDD`이고 붙어 있지 않으며 보관 기간이 지난 표다.
5. **부모 표의 통계**(7단계에서 더함, 10장 62). `ANALYZE ONLY events`로 부모의 통계만 새로 한다. autovacuum은 파티션 부모를 분석하지 않는다(PostgreSQL의 설계).
   - 부모의 통계는 파티션을 가로지르는 묶기·조인의 어림에 쓰인다. 없으면 무리 수가 기본값(200 × 200 = 4만)이 된다.
   - 리텐션 31일은 그 어림 때문에 병렬 해시 묶기를 골라, 리더의 마지막 묶기가 문장 한도 30초를 넘겼다(한도 없이 40초 넘게, 실제 무리 115만~237만, 10장 62).
   - 잎은 다시 분석하지 않는다(`ONLY`, autovacuum의 일). 표본 3만 행이라 1,000만 건에서 0.2~0.4초다. 부모에 `ShareUpdateExclusiveLock`을 걸어 수집·리포트는 막지 않는다.
   - 부모의 확장 통계(마이그레이션 0004의 (사용자, 한국 날) 무리 수)도 이때 만들어진다. 부모 통계만으로는 어림이 반대로 틀릴 수 있어 둘이 한 고침이다(10장 62).

- **겹쳐 돌지 않는다.** 시작할 때 advisory lock을 잡아 보고(`pg_try_advisory_lock`), 다른 실행이 돌고 있으면 바로 실패한다.
- **"오늘"은 DB 시각의 UTC 날짜다**(10장 16). 서버의 경고도 같다.
- **소유자 확인.** 마이그레이션 실행기처럼 DB 소유자(슈퍼유저 아님)로 돌리는지 먼저 본다. 슈퍼유저가 만든 파티션에는 앱 role의 권한이 붙지 않는다.
- 지운 파티션은 되살리지 않는다. 지우기 전에 보관(덤프)하는 일은 범위 밖이다(seat-booking 7단계의 백업 리허설이 방법을 보였다).
- **누가 언제 돌리나.** 하루 한 번 OS의 예약 작업(cron, Windows 작업 스케줄러)으로 돌린다. 앞으로 7일치를 미리 만들어 두므로, 관리 작업이 멈춰도 7일 동안은 수집이 503이 되지 않는다.
- API 서버가 관리 작업을 대신 돌리지 않는다. 서버는 앱 role(DML만)로 접속하고, 표를 만들고 떼는 권한은 소유자에게만 둔다(10장 12). 대신 서버는 뜰 때와 한 시간마다 받을 기간(과거 7일)부터 앞으로 3일까지 붙어 있지 않은 날이 있는지 보고, 있으면 경고 로그를 남긴다. 관리 작업이 7일을 미리 만드므로, 이 경고가 뜨면 4일 넘게 돌지 않은 것이다.
- `db:partitions`(1단계)는 `db:maintain`으로 바꾼다.

**이벤트 생성기**(`load:generate`)
- 씨앗(seed)으로 정해지는 의사 난수를 쓴다. 같은 씨앗과 같은 끝 날(`--end-day`)이면 같은 이벤트가 나온다. `event_id`도 씨앗에서 만들므로, 다시 넣으면 모두 중복이 된다(재실행이 안전하다). 시각을 "지금"에서 재면 다른 날 다시 돌릴 때 키가 달라 두 배가 되므로, 끝 날을 고정해 잰다.
- 분포(DESIGN 6.6)
  - 캠페인은 소수가 대부분을 차지한다(zipf).
  - 시간대별로 많고 적다(밤에 적음).
  - 사용자마다 이벤트 수가 다르다(소수의 헤비 사용자).
  - 행동은 seat-booking의 예매 흐름을 따른다(목록 → 좌석 지도 → 선점 → 주문 → 결제, 단계마다 이탈). 5단계 퍼널에 쓸 데이터다.
- 보내는 곳은 둘이다.
  - 수집 API: 받을 기간(7일) 안만 보낼 수 있다. 떼기 리허설(A4)과 7단계 측정이 이 생성기로 지금 근처의 이벤트를 만들어 보낸다.
  - DB(`load:generate`): 소유자로 바로 넣는다. 지난 90일을 채우는 데 쓴다(받을 기간 밖). 필요한 파티션을 만들고, 수집과 같은 문장(`unnest` + `ON CONFLICT`)으로 넣는다. 보관 기간보다 앞선 날은 넣지 않는다(관리 작업이 지울 날을 다시 만들게 되므로).
- 기본 데이터는 1,000만 건이다(10장 6). 크기와 넣는 시간은 2단계 기록에 숫자로 남긴다.

**떼기 리허설(합격 기준 A4)**
- 생성기가 수집으로 일정한 속도(초당 2,000건, 배치 200건)를 보내는 동안, 오래 도는 리포트(20초)를 하나 걸어 두고 관리 작업 전체(`maintain`: 만들기, 마무리, 떼기, 치우기)로 90일 지난 파티션을 뗀다.
- 보내는 쪽은 열린 모형이다. 앞 요청이 끝나길 기다리지 않고 정해진 간격으로 보낸다. 기다리면 막힌 동안 보내는 양이 줄어 지연이 가려진다.
- 잰다.
  - 수집 응답 코드별 수(5xx 0이어야 함)
  - 수집 지연(p50, p99, 최대)
  - 떼기가 기다린 시간
- 비교는 둘이다.
  - 기준선: 같은 장면에서 아무것도 떼지 않는다.
  - 일반 `DETACH`: 잠금 대기 한도 없이(`lock_timeout = 0`) 돌린다. 이것은 부모를 `AccessExclusiveLock`으로 잠그려고 리포트 뒤에 줄을 서고, 수집은 그 뒤에 줄을 선다. 한도를 1초로 두면 떼기가 먼저 포기해 수집이 거의 다치지 않는다(리뷰가 확인함). 그래서 한도를 적어 둔다.
- 503은 원인별로 센다. 원인은 잠금 대기 초과와 풀 연결 대기 초과다.
- 리허설 DB는 개발 DB를 복제해 만들고 끝나면 지운다(seat-booking 7단계와 같은 방식).

**PR 순서**: 이 설계 → 관리 작업(ATTACH로 만들기, CONCURRENTLY로 떼기, 마무리, 서버의 남은 날 경고) → 가지치기 테스트(A3) → 생성기 → 떼기 리허설(A4) → 기록

### 6.3 리포트 설정 → SQL (3단계 설계)

**요청.** `POST /reports/query`, 본문은 리포트 설정(`packages/shared`의 `ReportQuery`)이다. 로그인은 없다(10장 8). 화면(6단계)과 같은 스키마를 쓴다.

| 필드 | 규칙 |
|---|---|
| `metrics` | `events`(이벤트 수), `users`(고유 사용자 수) 가운데 1~2개 |
| `dimensions` | `event_name` · `platform` · `country` · `channel` · `campaign` 가운데 0~2개, 겹치지 않게 |
| `filters` | `[{ dimension, values }]`. 차원은 위 목록이고 같은 차원은 한 번만, 값은 1~100개. 값 목록 안에 있으면 남긴다(`IN`). `null`을 넣으면 값이 없는 것(예: 캠페인 없음)도 남긴다. 여러 필터는 모두 맞아야 한다(AND) |
| `from`, `to` | 리포트 시간대의 날짜(`YYYY-MM-DD`, 달력에 있는 날), 둘 다 포함, 90일까지 |
| `granularity` | `hour` · `day` · `week` · `total` |
| `timezone` | 허용 목록의 IANA 이름(대소문자까지 그대로). 기본 `Asia/Seoul` |

- 모르는 필드와 목록 밖의 값, `from > to`는 400이다(수집과 같다). 시간대를 허용 목록으로 두는 것은 PostgreSQL이 `asia/seoul`이나 부호가 뒤집힌 `UTC+5`도 받기 때문이다(리뷰가 확인함).
- 시간대 허용 목록은 `UTC`, `Asia/Seoul`, `Asia/Tokyo`, `Asia/Singapore`, `Asia/Kolkata`(+05:30), `Europe/London`, `America/New_York`, `America/Los_Angeles`다. 일광 절약 시간이 있는 곳과 30분 단위 오프셋이 하나씩 들어 있다. 시간 집계 표(4단계)가 어느 시간대를 그대로 받을지는 4단계에서 정한다.
- `week`는 월요일에 시작하는 주다(PostgreSQL `date_trunc`).
- **묶음은 기간 끝에서 늘리지 않는다.** 기간이 수요일에 시작하면 첫 주 묶음은 그 주 월요일의 순간이지만, 안에는 수요일부터의 이벤트만 있다. 그래서 `bucket`이 `from`보다 앞설 수 있다. 이런 묶음은 응답의 묶음 목록에 `partial: true`로 표시한다(일부만 찬 주가 줄어든 것처럼 보이지 않게).
- `total`은 기간 전체를 한 묶음으로 센다. `bucket`은 `from`의 시작 순간, `label`은 `from ~ to`다.

**보관 기간과 늦은 이벤트**
- 기간의 시작이 보관 기간(90일, UTC 날짜 기준)보다 앞서면 422 `out_of_retention`이다. 조용히 0을 돌려주면 "그때는 이벤트가 없었다"로 읽힌다. 시작 날이 일부만 남은 경우(한국 시각의 하루가 지운 UTC 날에 걸친 경우)도 거절한다.
- 기간의 끝이 지금으로부터 7일 안이면 `meta.provisional: true`다. 받을 기간이 7일이라 늦은 이벤트가 더 올 수 있다.

**SQL을 만드는 규칙**(주입 막기)
- 식별자(열 이름)는 허용 목록의 차원을 코드의 상수 표로 바꾼 것만 쓴다. 설정의 글자를 SQL에 넣지 않는다.
- 값(날짜, 시간대, 필터 값)은 모두 매개변수(`$n`)로 넘긴다. 필터는 `col = any($n::text[])`이고, `null`을 골랐으면 `or col is null`을 더한다.
- 리포트는 이름 없는 문장으로 보낸다(10장 26). 그러면 매번 값을 아는 계획이라 계획할 때 가지를 친다.
- **풀에서 연결 하나를 빌려 그 위에서** 트랜잭션을 연다. 읽기 전용이고, 트랜잭션 안에서만 걸리는 설정(`set_config(…, true)`)으로 문장 30초, 잠금 대기 3초(수집과 같다)를 건다. `pool.query`로 `set local`을 보내면 트랜잭션 밖이라 아무것도 걸리지 않는다(리뷰가 확인함).
  - 잠금 대기 한도가 없으면, 일반 `DETACH` 같은 `AccessExclusiveLock` 요청 뒤에 리포트가 줄을 선다(A4 리허설).
- **리포트는 수집과 다른 연결 풀(4개)을 쓴다.** 리포트는 30초까지 연결을 쥘 수 있다. 수집과 풀을 함께 쓰면 느린 리포트 몇 개가 수집의 연결을 빼앗아 수집이 503이 된다.
- **요청한 지표만 센다.** `users`를 고르지 않으면 `count(distinct user_id)`를 하지 않는다. 원본 리포트 시간의 대부분이 이것이다.

**기간과 시간대**
- 기간은 `occurred_at >= ($from::date::timestamp at time zone $tz) and occurred_at < (($to::date + 1)::timestamp at time zone $tz)`로 거른다. 리포트 시간대의 하루가 UTC의 어느 구간인지 PostgreSQL이 바꾼다. 일광 절약 시간이 바뀌는 날은 23시간이나 25시간이 된다.
- `timezone(text, timestamp)`는 변하지 않는 함수(immutable)라, 매개변수가 든 이 식도 계획할 때 상수가 되어 가지를 친다(확인함: 서울·뉴욕·콜카타의 하루 → 파티션 2개, UTC 하루 → 1개).
- 시간 묶음은 `date_trunc($unit, occurred_at, $tz)`다(3인자, PostgreSQL 14부터, immutable). 시간대의 자정·정시로 자르고 일광 절약 시간을 따른다.

**응답**

```json
{
  "rows": [{ "bucket": "2026-10-26T15:00:00.000Z", "label": "2026-10-27", "dimensions": { "platform": "ios" }, "events": 120, "users": 37 }],
  "meta": {
    "timezone": "Asia/Seoul", "from": "…", "to": "…", "rowCount": 1, "source": "raw", "provisional": false,
    "buckets": [{ "bucket": "2026-10-26T15:00:00.000Z", "label": "2026-10-27", "utcOffset": "+09:00", "partial": false }]
  }
}
```

- `label`은 리포트 시간대의 벽시계 글자다. `hour`는 `YYYY-MM-DD HH:MM`, `day`·`week`는 `YYYY-MM-DD`, `total`은 `from ~ to`다.
- `meta.buckets`는 기간의 모든 묶음이다(이벤트가 없는 묶음도). 4인자 `generate_series(…, $tz)`로 만든다. 행에는 이벤트가 있는 묶음만 있으므로, 화면은 이 목록으로 빈 묶음을 0으로 채운다(그래프가 빈 시간을 건너뛰어 잇지 않게). 묶음마다 UTC 오프셋이 있어, 일광 절약 시간이 끝나는 날의 두 `01:00`(`-04:00`, `-05:00`)을 가린다.
- 차원 값이 없으면(국가·채널·캠페인이 비어 있음) `null`로 묶는다.
- 행은 묶음 → 차원 순으로 정렬한다. 차원 값의 정렬은 builtin `C.UTF-8`의 코드 포인트 순서이고, `null`은 맨 뒤다(10장 13).
- 행에는 요청한 지표만 있다.
- **`users`는 행끼리 더할 수 없다.** 같은 사람이 여러 묶음·여러 차원 값에 나온다(7일 일별 × 플랫폼의 합 30만 vs 실제 13만, 리뷰가 잼). 기간 전체의 사용자 수는 `total`, 차원 없이 묻는다.
- 행이 20,000개를 넘으면(`LIMIT 20001`로 본다) 422 `too_many_rows`다. 잘라서 주지 않는다(잘린 표를 전체로 오해하지 않게). 이 한도로 92일 시간별 × 플랫폼(6,624행)이나 30일 일별 × 캠페인(6,030행)은 들어간다. "상위 N개 + 기타"는 화면(6단계)에서 정한다.
- 문장 한도에 닿으면 503 `report_timeout`, 잠금 대기·교착·연결 대기는 503 `busy`다.
- `source`는 3단계에서 늘 `raw`(원본)다. 4단계에서 `rollup`이 생긴다.

**고유 사용자 수**
- 원본에서 `count(distinct user_id)`로 정확히 센다. 묶음마다 따로 센다. 하루의 사용자 수는 그 날 시간별 사용자 수의 합이 아니다(6.4).

**합격 기준 A5(손으로 센 값)**
- 작은 고정 데이터(이벤트 수십 건)를 테스트 파일만 쓰는 새 DB에 넣고, 손으로 센 값과 견준다. 경우는 이렇다.
  - 한국 시각 자정을 사이에 둔 이벤트(UTC로는 같은 날)
  - 같은 사용자가 여러 시간에 나오는 경우(시간별 사용자 합 ≠ 하루 사용자)
  - 뉴욕의 일광 절약 시간이 끝나는 날(2026-11-01). 하루가 25시간이라 시간 묶음이 25개이고, 벽시계 `01:00` 묶음이 둘이다(`bucket`과 `utcOffset`이 다름)
  - 뉴욕의 일광 절약 시간이 시작하는 날(2027-03-14). 시간 묶음이 23개이고 `02:00`이 없다
  - 수요일에 시작하는 기간의 주 묶음(일부만 찬 첫 주, `partial`)
  - 차원 값이 없는 경우와 그것을 고르는 필터, 필터 여러 개, 30분 단위 시간대
- 주입 시험: 허용 목록 밖의 차원 이름과 시간대는 400이다. SQL 글자가 든 필터 값은 그저 값이다(결과 0행, 표는 그대로).
- 리포트 SQL 자체에 대한 가지치기 시험: 한국 시각 하루 리포트가 파티션 2개만 읽는다.
- 보관 기간과 "지금"은 테스트가 정한 시각으로 판단한다(실제 날짜가 지나도 테스트가 깨지지 않게).

**원본에서 세는 시간**(1,000만 건, 같은 PC, 탐색에서 한 번)

| 리포트 | 시간 |
|---|---|
| 30일 일별, 이벤트 수 + 고유 사용자 | 2.6초 |
| 90일 캠페인별(상위 20), 이벤트 수 + 고유 사용자 | 15.3초 |

- 3단계 기록에서 정한 리포트 몇 개를 API가 만드는 SQL 그대로(`LIMIT` 포함) 세 번씩 잰다(가운데 값, 첫 회차는 따로). 그 실행 계획(`EXPLAIN (ANALYZE, BUFFERS)`)도 남긴다.
- 리뷰가 실행 계획에서 본 것은 둘이다. 이것을 기록에서 확인한다.
  - 계획기는 `date_trunc(…, $tz)`로 묶은 무리의 수를 행 수만큼으로 어림한다(333만 vs 실제 30). 그래서 모든 행을 디스크에서 정렬한다.
  - 부분 집계는 `count(distinct)`가 없어도 쓰이지 않는다. `LIMIT`이 붙으면 병렬 계획으로 바뀐다.
- 이것이 4단계(집계 표)와 7단계(측정)의 "전" 숫자다.

**PR 순서**: 이 설계 → 공유 스키마와 SQL 만들기(순수 함수, 단위 테스트) → `POST /reports/query`(A5, 주입, 가지치기) → 기록(원본 시간)

### 6.4 집계 (4단계 설계)

**측정으로 고른 것**(개발 DB 1,000만 건을 복제한 버리는 DB, 세 번의 가운데 값)

| 방법 | 크기·만드는 시간 | 리포트 |
|---|---|---|
| 원본(3단계) | - | 90일 캠페인별 이벤트 622ms, 30일 일별 이벤트 1,567ms |
| **시간 집계 표**(UTC 정시 × 차원 다섯) | 385만 행(원본의 38%), 360MB, 12.6초 | 90일 캠페인별 279ms(2.2배), 30일 일별 234ms(6.7배), 7일 시간별 × 플랫폼 182ms |
| 고유 사용자: `count(distinct)`(3단계) | - | 90일 캠페인별 14,545ms, 30일 일별 4,160ms |
| **고유 사용자: 두 단계 `GROUP BY`**(원본) | - | 90일 캠페인별 3,142ms(4.6배), 30일 일별 2,894ms |
| 고유 사용자: 사용자 × 시간 표(차원 다섯) | 992만 행(원본과 거의 같음), 869MB, 22.9초 | 90일 캠페인별 4,026ms |

- **이벤트 수는 시간 집계 표 하나로 센다.** 차원 다섯을 모두 담아 어떤 차원·필터 조합도 답한다. 캠페인(200개)이 섞여 원본의 38%까지만 줄지만, 리포트는 2~7배 빨라진다. 일별 리포트가 특히 빨라지는 것은, 원본에서 `date_trunc`로 묶은 무리 수를 계획기가 어림하지 못해 333만 행을 정렬하던 일이 사라지기 때문이다(3단계 측정).
- **고유 사용자 수는 표를 더 두지 않고, 원본에서 두 단계 `GROUP BY`로 정확히 센다.** `count(distinct)`는 부분 집계를 할 수 없어 병렬이 꺼진다. (묶음, 차원, 사용자)로 먼저 묶으면 정렬 대신 해시로 센다. 묶음이 `date_trunc` 식이 아니면(기간 전체 × 캠페인) 그 단계가 병렬 부분 해시 집계가 된다. 그다음 무리마다 행 수를 센다. 값은 같고, 90일 캠페인별은 4.6배(4단계 기록에서는 3.9배) 빠르다. 일·시간 묶음은 (날, 사용자)의 무리 수를 행 수만큼으로 어림해 병렬을 쓰지 않아, 해시로 세는 만큼만 빠르다(30일 일별 1.35배, 4단계 기록).
  - 사용자 × 시간 표는 줄지 않는다. 한 사람이 한 시간에 한 차원 조합으로 이벤트를 하나쯤 내기 때문이다. 오히려 느려 버린다.
  - 사용자 × 일 표(차원 없음)는 차원 없는 리포트만 돕는다. 넣지 않는다.
  - HLL 같은 근사는 확장(`hll`)이 없어 쓰지 않는다(확인함).

**표**

| 표 | 열 | 메모 |
|---|---|---|
| `hourly_rollup` | `hour`(UTC 정시), `event_name`, `platform`, `country`, `channel`, `campaign`, `events` | 유일 키는 `(hour, 차원 다섯)`이고 `NULLS NOT DISTINCT`다(값 없는 차원도 한 무리). 이 키의 인덱스가 `hour` 범위 조회도 맡는다 |
| `dirty_hours` | `hour` | 다시 셀 시간의 기록. 유일 키가 없다(아래 "늦은 이벤트"). 같은 시간이 여러 행일 수 있다 |
| `rollup_state` | `watermark`(NOT NULL) | 이 순간 앞의 시간은 집계 표에 있다(한 행). 마이그레이션이 보관 기간의 시작(UTC 날짜로 90일 전 0시)으로 넣는다 |

- 셋 다 파티션하지 않아 drizzle 스키마로 둔다. 앱 role은 기본 권한으로 DML을 한다.
- `dirty_hours`는 작은 대기열이다. 끝난 시간의 행은 작업이 1분마다 가져간다. 진행 중인 시간(과 받을 기간의 1시간 뒤)의 행은 그 시간이 끝날 때까지 쌓인다. 초당 배치 10개면 한 시간에 3.6만 행쯤이다. 리뷰가 잰 비용은 작다(1분 가져오기 3ms, 시간이 바뀔 때 18ms, 2.5MB).
- 워터마크가 `null`이면 첫 실행이 과거를 0으로 만든다(`hour >= null`이 거짓이라 아무것도 넣지 않고 워터마크만 옮김, 리뷰가 재현함). 그래서 NOT NULL로 두고 시작값을 넣는다. 행이 없으면 작업은 건너뛰지 않고 오류를 낸다(`skip locked`가 0행을 돌려주는 것과 가린다).

**늦은 이벤트(합격 기준 A6)**
- 수집은 이벤트를 넣는 같은 트랜잭션에서, 배치에 든 시간마다 `dirty_hours`에 행을 하나씩 **덧붙인다**(유일 키도 충돌 확인도 없다). 지금 시간도 넣는다. 늦은 것만 넣으려면 "지금"을 언제 쟀느냐에 기대야 해서 경쟁이 생긴다.
  - 유일 키에 `ON CONFLICT DO NOTHING`을 쓰면 안 된다. DO NOTHING은 이미 있는 행을 잠그지 않는다. 그래서 다음 순서가 생긴다.
    1. 수집 T가 H의 이벤트를 넣고 H의 행이 이미 있어 넘어간다.
    2. 작업이 그 행을 지우며 가져간다.
    3. 작업이 원본을 다시 센다. T는 아직 커밋 전이라 T의 이벤트는 빠진다.
    4. T가 커밋한다. 이제 H를 다시 셀 표시가 남아 있지 않아, H는 영영 고쳐지지 않는다(조언이 찾음).
  - 덧붙이면 T의 행은 T 자신이 쓴 것이다. 커밋 전이라 작업이 지우지 못하고, T가 커밋한 뒤 남아 다음 작업이 센다. 수집끼리 같은 행을 두고 기다리지도 않는다.
- 집계 작업 한 번은 트랜잭션 하나이고, 이 순서로 한다.
  1. 새 워터마크 = 지금의 UTC 정시(끝난 시간까지).
  2. 새 워터마크 앞의 더러운 시간을 지우며 가져온다(`delete … returning`, 같은 시간은 하나로).
  3. 다시 셀 시간 = [옛 워터마크, 새 워터마크) ∪ 가져온 시간이다. 이것을 중복 없는 한 집합으로 만들어, 그 시간들의 집계 행을 지우고 원본에서 **INSERT 하나로** 다시 센다. 가져온 시간이 범위 안에 있을 때 범위 INSERT와 따로 넣으면 같은 시간이 두 번 들어가, 유일 키에 막혀 워터마크가 영영 멈춘다(유일 키가 없으면 조용히 두 배가 된다, 리뷰가 재현함).
     - 가져온 시간은 흩어져 있어 `date_trunc(…) = any(…)`만으로는 가지를 치지 못한다(파티션 9개 전부). 그래서 그 시간들의 최소·최대로 `occurred_at` 범위도 함께 건다(파티션 2개).
  4. 워터마크를 새 워터마크로 바꾼다.
- 경쟁을 막는 이유
  - 수집 트랜잭션은 이벤트와 더러운 시간을 함께 커밋한다.
  - 작업의 2단계보다 먼저 커밋한 수집은, 3단계가 원본을 읽을 때 그 이벤트가 보인다.
  - 2단계보다 늦게 커밋한 수집의 더러운 시간은 지워지지 않고 남는다. 다음 작업이 다시 센다.
  - 그래서 집계 표가 원본과 다른 것은 늦은 이벤트가 들어온 뒤 다음 작업까지뿐이다(A6).
- 처음 돌 때나 오래 멈췄다 돌 때는 다시 셀 시간이 많다. 하루씩 나눠 트랜잭션을 여러 번 돈다.
  - 조각마다 범위 [워터마크, 조각 끝)의 더러운 시간과, 워터마크 앞의 가장 이른 더러운 시간부터 `chunkHours`만큼만 가져온다(늦은 시간에 한도가 없으면 따라잡은 뒤 수천 시간이 한 트랜잭션에 들어 문장 한도에 닿는다, 코드 리뷰). 다시 세는 범위는 [워터마크, 조각 끝) ∪ 가져온 시간이고, 그다음 워터마크를 조각 끝으로 옮긴다.
  - 처음 조각이 새 워터마크 앞의 것을 모두 가져가고 자기 하루만 다시 세면, 나머지가 사라진다.

**집계 작업**
- API 서버 안의 타이머가 1분마다 돈다. 집계 표는 DML만 하므로 앱 role로 된다(관리 작업과 달리 DDL이 없다).
- 겹쳐 돌지 않게, 조각 트랜잭션의 첫 문장에서 `rollup_state` 행을 `for update skip locked`로 잡는다. 못 잡으면 다른 작업이 도는 것이니 이번은 건너뛴다. 세션 advisory lock은 풀의 연결에 남아 다음에 빌린 쪽으로 새기 쉬워 쓰지 않는다. 행 잠금은 커밋할 때 풀린다.
  - 잠근 행에서 매 조각의 워터마크를 읽는다(조각 사이에 다른 실행이 끼어도 겹치지 않게). 시작은 `greatest(워터마크, 보관 기간의 시작)`이다.
  - 타이머는 `setInterval`이 아니라 끝난 뒤 다음을 거는 `setTimeout`이다(한 프로세스 안에서 실행 둘이 조각을 번갈아 돌지 않게).
  - 조각 트랜잭션은 문장 60초, 잠금 대기 3초로 묶는다. 멈춘 조각이 `events`의 잠금을 쥐어 관리 작업의 `DETACH … CONCURRENTLY`를 붙잡지 않게.
  - 집계 작업은 수집·리포트와 다른 연결(풀 1개)로 돈다.
- 명령(`rollup:run`)도 둔다. 처음 채우기와 테스트에 쓴다.
- 보관 기간이 지난 집계 행(90일 전 UTC 날짜)은 집계 작업이 지운다.

**리포트**
- **이벤트만 묻고, 시간대가 정수 시간 오프셋이면** 집계 표로 센다. 허용 목록의 여덟 가운데 콜카타(+05:30)만 아니다.
  - 기간 [시작, 끝)을 워터마크로 나눈다. [시작, min(끝, 워터마크))는 집계 표의 `sum(events)`로, [max(시작, 워터마크), 끝)는 원본의 `count(*)`로 센다. 두 부분을 각각 묶은 뒤 합쳐 다시 묶는다(집계 표 쪽도 먼저 묶지 않으면 90일에 집계 행 385만 개를 정렬한다, 코드 리뷰).
  - 워터마크는 리포트 트랜잭션(읽기 전용, 반복 읽기)의 첫 문장에서 읽어, 리포트 문장에 매개변수로 넘긴다. 반복 읽기라 두 부분과 워터마크가 한 스냅샷이고, 그 사이에 작업이 커밋해도 겹치거나 빠지지 않는다.
    - 처음에는 같은 문장 안의 서브쿼리(`(select watermark from rollup_state)`)로 읽었다. 그러면 계획할 때 값을 몰라 원본 쪽 아래 끝으로 가지를 치지 못해, 하루 리포트도 파티션 91개를 계획했다(실행할 때야 뺀다, 코드 리뷰). 매개변수면 이름 없는 문장이라 계획할 때 상수다(26).
  - 기간이 워터마크에서(또는 뒤에서) 시작하면 집계 표 부분이 비므로 원본으로 센다고 알린다(`meta.source = raw`). 상태 행이 없어도 원본으로 센다(집계 작업이 오류를 남긴다).
  - 시간대의 정시는 UTC의 정시와 같으므로 시간 집계 표의 행을 리포트 시간대의 시간·일·주로 그대로 묶을 수 있다(`date_trunc(…, hour, $tz)`).
  - `meta.source`는 `rollup`이다. `meta.rollupWatermark`는 그 순간이다.
- **고유 사용자를 묻거나, 30분 단위 시간대면** 원본에서 센다(`meta.source = raw`).
  - 이때 이벤트 수와 사용자 수를 한 번에 센다. 안쪽에서 (묶음, 차원, 사용자)로 묶어 `count(*)`를 내고, 바깥에서 무리마다 그 합(이벤트)과 행 수(사용자)를 낸다.
- 집계 표가 원본과 다를 수 있는 것은 늦은 이벤트가 들어온 시간이 다음 작업(1분)까지 옛 값인 경우뿐이다. 그때 리포트는 `meta.stale: true`다(기간 안, 워터마크 앞에 아직 다시 세지 않은 더러운 시간이 있음). 작업이 계속 실패하면 이 표시가 계속 켜진다.
  - 더러운 시간을 리포트가 원본으로 세면 늘 정확하다(리뷰가 확인함). 하지만 더러운 시간은 흩어져 있어 원본의 가지를 치지 못하고, 늦은 이벤트가 늘 들어오는 실제 수집에서는 리포트마다 원본을 넓게 읽게 된다. 그래서 표시만 한다.

**테스트**
- A5(집계 표 = 원본): 생성기 데이터(수만 건)를 새 DB에 넣고 작업을 돌린다. 그다음 여러 설정(단위 넷, 차원, 필터, 시간대 일곱)을 집계 표 경로와 원본 경로로 각각 돌려 같은지 본다.
  - 워터마크는 런던(10-25)과 뉴욕(11-01)의 일광 절약 시간이 끝나는 때보다 뒤에 둔다. 집계 표 쪽에서도 그날의 두 01:00을 따로 세는지 본다(코드 리뷰).
  - 가지치기(A3): 원본 꼬리가 워터마크부터의 파티션만 계획하는지, 기간 앞뒤 파티션이 계획에서 빠지는지 본다.
- A6: 작업 뒤 늦은 이벤트를 넣으면 집계 표 경로가 옛 값이다. 작업 한 번 뒤 다시 같다.
- 경쟁(위의 순서를 결정적으로 재현): 끝난 시간 H에 대해 미리 더러운 행이 하나 있다. 수집 T가 H의 이벤트와 더러운 행을 넣고 커밋하지 않은 채 쥐고 있다. 그 사이 작업을 돌린 뒤 T를 커밋한다. 그러면 H는 원본과 다르다. 작업을 한 번 더 돌리면 같다. 유일 키 + DO NOTHING이면 둘째 작업이 할 일을 찾지 못해 실패한다.
- 나눠 돌기: 여러 날에 걸친 더러운 시간이 조각마다 빠짐없이 다시 세지는지 본다. 가져온 시간이 그 조각의 범위 안에 있어도 한 번만 센다.
- 처음 실행: 보관 기간 안의 기존 데이터가 모두 집계 표에 들어간다.
- 두 단계 `GROUP BY`의 사용자 수가 3단계 A5의 손으로 센 값과 같다(3단계 테스트가 그대로 지킨다).

**PR 순서**: 이 설계 → 표 셋과 수집의 더러운 시간 → 집계 작업(타이머, 명령, 보관 기간) → 리포트가 집계 표·두 단계 `GROUP BY`를 씀(A5·A6) → 기록(전후 측정)

### 6.5 퍼널과 리텐션 (5단계 설계)

둘 다 원본에서 센다. 사용자마다 순서와 날을 봐야 해서 시간 집계 표(차원 × 시간의 이벤트 수)로는 셀 수 없다. 리포트(6.3)의 규칙을 그대로 쓴다: 허용 목록과 매개변수, 리포트 시간대의 날짜, 보관 기간(422 `out_of_retention`), 리포트 전용 풀의 읽기 전용 트랜잭션(문장 30초, 잠금 대기 3초), 503 `report_timeout`·`busy`, 이름 없는 문장.

**퍼널 요청.** `POST /funnels/query`, 본문 `FunnelQuery`(`packages/shared`).

| 필드 | 규칙 |
|---|---|
| `steps` | 이벤트 이름 2~6개(수집의 이벤트 이름 규칙). 같은 이름이 다시 나와도 된다(A → A) |
| `windowMinutes` | 전환 기간(분), 1~10,080(7일) |
| `filters` | 리포트와 같되 차원에서 `event_name`을 뺀다(단계가 이벤트 이름이다). **모든 단계의 이벤트**에 건다 |
| `breakdown` | 차원(`event_name` 빼고) 0~1개. 값은 진입한 1단계 이벤트에서 읽는다 |
| `from`, `to`, `timezone` | 리포트와 같다(90일까지). 진입(1단계)이 이 기간에 있어야 한다 |

**퍼널의 정의: 첫 진입 기준 전환**
- **진입**: 사용자의 기간 안 첫 1단계 이벤트(필터에 맞는 것). 사용자는 한 번만 진입하고, 뒤의 1단계는 다시 시작하지 않는다. Mixpanel의 기본(고유 사용자 세기)이 이렇다.
- **전환 기간**은 진입 순간부터 정해진 분이다. 달력의 날이 아니라 시간이라 일광 절약 시간과 상관없다. 뒤 단계는 모두 [진입, 진입 + 기간) 안이어야 한다. 기간의 끝을 넘어도 된다. 그래서 읽는 구간은 [기간 시작, 기간 끝 + 전환 기간)이다.
- **k단계**는 k−1단계로 고른 순간보다 **엄격히 뒤**의 첫 k단계 이벤트다. 같은 밀리초는 뒤가 아니다. 그래서 A → A에서 같은 이벤트를 두 번 쓰지 않는다.
- **단계마다 가장 이른 이벤트를 고르는 것이 늘 최선이다.** 고른 것을 g_k라 하면, 어떤 유효한 사슬 c에서도 귀납으로 c_k ≥ g_k이고 g_k ≤ c_k < 진입 + 기간이다(설계 리뷰). 전환 기간이 진입에 묶여 있어야 성립한다. "단계 사이 시간"처럼 단계마다 기간을 두면 깨진다.
- **첫 진입만 보는 대가가 크다.** 첫 시도에서 기간 안에 못 끝내고 다음 시도에서 끝낸 사용자는 전환하지 않은 것으로 센다. 생성기 데이터(7일, 전환 기간 15분)에서 결제 단계가 첫 진입 기준 16,871명, 아무 시도 기준 33,234명이다. 같은 주의 "결제한 사용자" 리포트보다 퍼널의 끝이 작게 보인다.
  - 아무 시도 기준(Amplitude가 고유 사용자를 세는 방식, "가장 이르고 긴 시도")은 사용자마다 이벤트를 시각 순서로 훑으며, 엄격히 앞선 행들의 k−1단계 진입 순간 가운데 가장 늦은 것을 들고 간다(창 함수 `max(…) over (… range between unbounded preceding and interval '1 microsecond' preceding)`, 단계마다 한 겹).
  - 쟀더니 7일 2.0초, 30일 13초, 90일 31초였다. 90일은 문장 한도를 넘고, 병목은 단계 이벤트 전체를 사용자·시각으로 정렬하는 일이다(30일 172MB를 디스크에서).
  - 넓은 기간에서는 뜻도 흐려진다. 90일·1일이면 아무 시도 기준으로 81%가 "결제까지 전환"이다. 이것은 퍼널이라기보다 "결제한 적 있음"이다.
  - 그래서 첫 진입 기준으로 하고, 응답과 화면에 그 이름을 붙인다. 아무 시도 기준은 7단계에서 정렬 비용(인덱스, `work_mem`)을 다시 잰 뒤 정한다. 최종 검토에서 사용자가 정할 제품 결정으로 올린다.
- **필터는 모든 단계에, 나눔은 진입에 건다.** 그래서 같은 값이어도 나눔의 행과 그 값으로 거른 퍼널이 다를 수 있다. 진입이 naver이고 2단계가 google이면 나눔의 naver 행에는 들고, naver 필터에서는 1단계만이다.
  - 8단계 주의: seat-booking의 서버 이벤트에 채널·캠페인이 없으면, 채널·캠페인 필터가 뒤 단계를 0으로 만든다. 그때 "귀속 차원은 진입에만"을 다시 본다.
  - 8단계 주의: outbox가 한 트랜잭션에서 `now()`로 두 단계를 쓰면 시각이 같아 엄격한 `>`에 빠진다. `clock_timestamp()`를 쓰거나 이 규칙을 다시 본다. (8단계에서 닫음: seat-booking은 한 트랜잭션에 이벤트를 하나만 넣고, 시각은 넣는 순간의 `clock_timestamp()`다. 10장 67)
- **응답은 단계별 사용자 수뿐이다.** 전환율은 화면이 나눈다(6단계의 질문 "화면이 무엇을 서버에 맡기나").

```json
{
  "rows": [{ "dimensions": { "channel": "naver" }, "steps": [1200, 700, 240, 170, 145] }],
  "meta": { "timezone": "Asia/Seoul", "entry": "first", "rangeStart": "…", "rangeEnd": "…", "windowEnd": "…", "provisional": true }
}
```

- 나눔이 없으면 행은 늘 하나다(`dimensions: {}`). 진입이 0이어도 `[0, 0, …]`이다(무리로 묶지 않고 단계마다 센다).
- 나눔의 행은 서로 겹치지 않는다(사용자마다 진입은 하나). 그래서 6.3의 `users`와 달리 행끼리 더하면 전체와 같다. 나눔 값의 정렬은 리포트와 같다(코드 포인트 순서, `null`은 맨 뒤).
- `windowEnd` = 기간 끝 + 전환 기간. `provisional`은 `windowEnd`가 지금으로부터 7일 안이면 참이다(늦은 이벤트).
- `windowEnd`가 지금보다 뒤면, 전환 기간이 아직 끝나지 않은 진입이 "전환 안 함"으로 세어져 있다. 장치를 더하지 않고, 화면이 이것을 알린다.

**퍼널 SQL: 단계마다 조인한다**(두 모양을 개발 DB에서 재고 고름)
- `s1`: 기간 안의 1단계를 사용자로 묶어 `t1 = min(occurred_at)`. 나눔이 있으면 `distinct on (user_id) … order by user_id, occurred_at, event_id`로 진입 이벤트의 차원도 읽는다(같은 밀리초의 1단계 둘이면 `event_id`로 정한다. 없으면 같은 데이터에서도 고르는 것이 바뀐다, 설계 리뷰가 재현함).
- `sk`: `s(k−1)`과 원본의 k단계 이벤트를 `user_id`로 조인하고, `occurred_at > t(k−1) and occurred_at < t1 + 기간`인 것의 최솟값을 사용자마다 `tk`로 낸다. 해시 조인과 해시 집계다.
- 단계마다 `count(*)`를 센다. 단계 수만큼 원본을 훑지만, 훑을 때마다 그 단계의 이벤트만 해시에 담는다.
- 버린 모양 A(한 번 훑기): 단계 이벤트를 한 번 훑고, 사용자로 나눈 창 함수(`min(occurred_at) filter (…) over (partition by user_id)`)를 단계마다 한 겹씩 쌓는다. 정렬은 한 번이지만, 겹마다 사용자의 나눔을 통째로 담아야 한다. 무거운 사용자(하루 수천 이벤트)의 나눔이 메모리를 넘어 겹마다 디스크에 쓴다. 정렬도 디스크에서 171MB다(30일).
- **퍼널·리텐션 트랜잭션은 중첩 반복 조인을 끈다**(10장 47). 원본에 `user_id` 인덱스가 없어 중첩 반복은 안쪽을 바깥 행마다 다시 훑는다. 조인 조건의 범위(전환 기간, 날짜 차이)에 계획기가 기본 선택도를 써 2단계부터를 1행쯤으로 어림해, 통계가 있어도 그것을 고를 수 있다. 통계가 다 있는 개발 DB에서 1일·나라 VN·채널 나눔 퍼널이 켜면 61초, 끄면 0.2~0.4초였다(코드 리뷰). 통계가 없는 새 DB에서는 3만 건에 39초 vs 31ms였다.
- **기간 끝 + 전환 기간은 매개변수다.** `timestamptz + interval`은 변하지 않는 함수가 아니라서(STABLE) 문장에 넣으면 계획할 때 가지를 못 친다(실행 시작 때 쳐낸다, 설계 리뷰가 확인함). 트랜잭션의 첫 문장에서 계산해 넘긴다(4단계 워터마크와 같은 까닭).

**리텐션 요청.** `POST /retention/query`, 본문 `RetentionQuery`.

| 필드 | 규칙 |
|---|---|
| `startEvent` | 무리에 들게 하는 이벤트 이름. 없으면 모든 이벤트 |
| `returnEvent` | 돌아온 것으로 볼 이벤트 이름. 없으면 모든 이벤트 |
| `days` | N, 1~30 |
| `filters` | 리포트와 같되 `event_name`을 뺀다. 시작과 돌아옴 이벤트 모두에 건다 |
| `from`, `to`, `timezone` | 무리의 날(리포트 시간대), 31일까지 |

**리텐션의 정의: 날마다 무리**
- **무리 d**: 날 d(리포트 시간대)에 시작 이벤트가 하나라도 있는 사용자 전부다. 한 사람이 여러 날의 무리에 든다. 그래서 무리의 행끼리 더할 수 없다(6.3의 `users`와 같은 규칙).
- **N일째**: 그 사용자가 d + N일에 돌아옴 이벤트가 하나라도 있다("그날"이다. "그 뒤 아무 때"가 아니다).
- 날 차이는 **날짜끼리 뺀다**. 시각의 차이를 24시간으로 나누지 않는다. 뉴욕 10-31 23:30 → 11-01 00:30은 1일째다. 일광 절약 시간이 끝나 25시간인 날도 하루다.
- **아직 다 지나지 않은 칸은 `null`이다.** d + N일이 "지금"의 리포트 시간대 날짜와 같거나 뒤면 그 칸은 아직 모른다. 0을 주면 "아무도 안 돌아왔다"로 읽힌다.
- 버린 정의(처음 설계): 무리 = 기간 안 첫 시작 이벤트의 날. 기간 전부터 오던 사용자가 기간 앞쪽 날에 몰려, 무리 크기와 1일째 비율이 날마다 줄어드는 추세를 정의가 만든다(생성기는 시간에 따라 변하지 않는데 1일째가 30% → 14%). 같은 날의 무리도 `from`에 따라 값이 바뀐다(설계 리뷰가 잼). 날마다 무리는 `from`과 상관없다.
- "처음 온 사용자"의 리텐션(앞 L일에 이벤트가 없던 사용자)은 미룬다. 보관 기간이 90일이라 L만큼 앞을 읽어야 한다.

```json
{
  "rows": [{ "cohort": "2026-10-01", "cohortStart": "2026-09-30T15:00:00.000Z", "users": 1200, "returned": [310, 220, null] }],
  "meta": { "timezone": "Asia/Seoul", "rangeStart": "…", "rangeEnd": "…", "days": 3, "today": "2026-10-27", "provisional": true }
}
```

- 행은 기간의 모든 날이다(31개까지). 무리가 없는 날은 `users: 0`이고, 지난 칸은 0, 안 지난 칸은 `null`이다. 오늘의 무리는 지금까지 센 값이고, 오지 않은 날의 무리는 `users: null`이다.
- `meta.today`는 `null` 칸을 정한 "오늘"(리포트 시간대의 날짜)이다. 화면이 자기 시계로 다시 계산하지 않게 준다(코드 리뷰).
- 화면 참고: `users: 0`인 무리의 비율은 0/0이다. 일광 절약 시간대에서 `cohortStart`의 간격은 23·25시간이라, 날 글자는 `cohort`로 붙인다.
- `returned[i]`는 (i + 1)일째다.
- `provisional`은 마지막 칸의 날의 끝((`to` + 1 + N)일 자정, 리포트 시간대)이 지금으로부터 7일 안이면 참이다(늦은 이벤트).

**리텐션 SQL**
- 무리 c = (사용자, 날)로 묶은 시작 이벤트, 읽는 구간 [`from` 자정, `to` + 1 자정).
- 돌아옴 b = (사용자, 날)로 묶은 돌아옴 이벤트, 읽는 구간 [`from` + 1 자정, `to` + 1 + N 자정). 식은 `(($from::date + 1)::timestamp at time zone $tz)`와 `(($to::date + 1 + $N)::timestamp at time zone $tz)`로 못박는다. `기간 끝 + interval`로 쓰면 STABLE이라 계획할 때 가지를 못 치고, 뉴욕 일광 절약 시간이 끝나는 주에는 한 시간이 빠진다(설계 리뷰가 재현함).
- 무리 크기는 c를 날로 묶어 세고, 칸은 c와 b를 `user_id`로 조인해 날짜 차이 1~N을 (d, N)으로 센다. 한 문장에서 c를 두 번 쓴다(CTE는 한 번 만들어진다).
- 버린 모양: 사용자마다 시작한 날과 돌아온 날을 `bigint` 비트로 모으고 N마다 비트를 견주기. 무리 30일에 17초로 조인(15.4초)보다 느리다.

**공통**
- 리포트·퍼널·리텐션은 같은 트랜잭션 틀을 쓴다(빌린 연결, 읽기 전용 반복 읽기, 시간 한도, 보관 기간 확인, 422·503 바꾸기). `run.ts`에서 꺼내 셋이 함께 쓴다.
- 각자 첫 문장에서 기간의 순간, 보관 기간의 시작, `provisional`의 끝(리포트는 기간 끝, 퍼널은 `windowEnd`, 리텐션은 `to` + 1 + N), 리텐션의 "오늘"을 `asOf`로 계산한다. 워터마크 읽기는 리포트에만 있다.
- 보관 기간: 퍼널·리텐션은 `from`에서 앞으로만 읽으므로 지금의 `from < 보관 기간의 시작` 확인이면 된다(설계 리뷰가 확인함).

**테스트**
- 손으로 센 퍼널(고정 데이터, 한국 시각)
  - 순서대로 기간 안에 다 함(끝까지)
  - 2단계가 1단계보다 앞(1단계만)
  - 2단계가 정확히 진입 + 기간(기간은 반열린 구간이라 빠짐)
  - 첫 시도는 기간 안에 못 끝내고 다음 1단계부터는 기간 안에 끝냄(1단계만, 첫 진입 기준)
  - 1단계와 2단계가 같은 밀리초(1단계만), A → A의 두 A가 같은 밀리초(1)
  - 1단계가 기간 앞이고 기간 안에 다시 함(기간 안의 것으로 진입)
  - 2단계가 기간 끝 뒤지만 전환 기간 안(셈)
  - 필터: 1단계는 ios, 2단계는 web, ios로 거름(1단계만)
  - 나눔: 1단계 naver, 2단계 google → naver로 셈. 같은 밀리초의 1단계 둘(naver, google)은 `event_id`로 늘 같은 쪽. 나눔 행의 합 = 전체
  - 진입이 없음 → `[0, 0, …]` 한 행
- 손으로 센 리텐션: 한 사용자가 여러 무리에 듦, 한국 시각 자정을 사이에 둔 1일째, 뉴욕 일광 절약 시간이 끝나는 날을 사이에 둔 1일째, 아직 다 지나지 않은 칸(`null`), 무리 없는 날(`users: 0`), 시작·돌아옴 이벤트를 고름, `from`을 바꿔도 같은 날의 무리는 같음
- 변이 시험(실패해야 함): `>`를 `>=`로, 전환 기간 조건 빼기, 순서 조건 빼기, 날짜 차이를 시각 차이로, 나눔의 `event_id` 순서 빼기
- 생성기 데이터(3만 건) 확인: 전환 기간 15분이면 단계 비율이 생성기의 비율 근처다.
- 가지치기: 퍼널 계획의 파티션이 `to + 전환 기간`에서 멈추고, 리텐션은 `to + N일`에서 멈춘다.

**PR 순서**: 이 설계 → 트랜잭션 틀 꺼내기와 공유 스키마·SQL 만들기(순수 함수) → `POST /funnels/query`(손으로 센 값, 가지치기) → `POST /retention/query`(손으로 센 값) → 기록(시간)

### 6.6 측정

  - 캠페인은 소수가 대부분을 차지한다(zipf).
  - 시간대별로 많고 적다.
  - 사용자마다 이벤트 수가 다르다.
- 기본 데이터는 1,000만 건(약 3GB 예상)이다. 측정은 5,000만 건까지 한다. 디스크 여유는 547GB다(확인함).

### 6.7 화면 (6단계 설계)

마케터가 리포트를 설정해 그래프와 표로 보고, 퍼널을 보고, 설정을 저장해 다시 연다. 범위는 2장의 "최소"다: 리포트 설정, 그래프와 표, 퍼널, 저장한 리포트. 꾸미기·공유·대시보드 배치는 없다. 리텐션은 표 하나만 둔다(10장 49).

**구성**
- `apps/web`: React 19.3.0, React Router 8.4.0, TanStack Query 5.104.1, Vite, 단위 테스트는 Vitest + jsdom 29.1.1 + Testing Library, E2E는 Playwright 1.64.0. seat-booking 5단계와 같은 판이다(10장 48). 다른 점 둘(설계 리뷰):
  - `tsconfig`의 `lib`는 `ES2024`다. 공유 스키마가 원본(.ts) 그대로 들어오고 `isWellFormed()`(ES2024)를 쓴다. seat-booking의 `ES2023`을 그대로 가져오면 형 검사가 깨진다.
  - Vite는 루트에 이미 있는 판(vitest의 peer로 깔린 8.3.5)에 맞춘다. 낮은 판으로 고정하면 npm이 화면 밑에 따로 깔아 Vite가 두 벌이 된다. `package.json`의 판을 모두 먼저 적고 한 번만 설치한 뒤 `npm ls react react-dom vite`가 한 벌씩인지 본다(seat-booking에서 React가 두 벌이 됐던 일).
- 화면은 API와 같은 origin에 둔다. Vite가 `/api/*`를 API로 넘기며 `/api`를 뗀다(CORS가 필요 없다). 개발 화면은 5180, 프록시 기본값은 `127.0.0.1:3002`다(seat-booking의 5173·3001과 겹치지 않게).
- 요청·응답은 `packages/shared`의 zod 스키마를 그대로 쓴다. 보내기 전에 설정을 `parse`하고 받은 응답도 `parse`한다(계약이 어긋나면 조용히 틀리지 않고 오류로 보인다).
- 화면 셋: 리포트(`/reports`), 퍼널(`/funnels`), 리텐션(`/retention`). 저장한 리포트는 왼쪽 목록으로 셋 모두에서 연다.

**서버가 하는 것과 화면이 하는 것**(6단계의 질문)

| 일 | 맡는 쪽 | 까닭 |
|---|---|---|
| 세기, 시간대로 묶기, 일광 절약 시간 | 서버 | 시간대의 달력을 DB가 안다. 화면이 다시 하면 두 곳이 어긋난다 |
| 기간의 모든 묶음(빈 것, `partial`, `utcOffset`) | 서버(`meta.buckets`) | 25시간인 날의 두 `01:00`을 화면이 만들 수 없다 |
| "지금"(`meta.asOf`), `provisional`·`stale`·`entry`·`windowEnd`·`today`, 리텐션의 `null` 칸 | 서버 | "지금"과 데이터의 상태를 아는 쪽이 판단한다 |
| 빈 묶음을 0으로 채우기, 진행 중·아직 오지 않은 묶음 가리기 | 화면 | `meta.buckets`와 `meta.asOf`를 견주기만 한다(글자 비교, 날짜 계산 없음) |
| 행 → 계열로 펼치기, 상위 N개 + 기타 | 화면 | 보이는 방식의 일이다. 서버는 모든 행을 준다(20,000행까지) |
| 퍼널 전환율, 리텐션 비율 | 화면 | 나누기는 화면의 일이다. 서버는 셀 수 있는 수만 준다 |
| 글자 | 화면 | 날 글자는 서버의 `label`·`cohort`를 그대로 쓴다. 화면이 시각을 더해 만들지 않는다 |

- **화면은 날짜·시간대 계산을 하지 않는다.** 예외는 하나다: 양식의 기본 기간("최근 7일")을 만들 때만 `Intl.DateTimeFormat`(`timeZone`)으로 리포트 시간대의 오늘을 쓴다. 검사는 서버가 한다.
- 그래프와 표의 점은 묶음의 순간(`bucket`)을 키로, 글자는 `label`로 쓴다. 그래야 두 `01:00`이 따로 선다. 같은 `label`이 둘이면 `utcOffset`을 덧붙인다.
- **x축은 묶음 순서로 같은 간격이다.** 순간을 선형 눈금에 놓으면 23·25시간인 날만 간격이 달라진다.
- **진행 중·아직 오지 않은 묶음**(설계 리뷰): `partial`은 기간 끝에서 잘린 묶음만 뜻하고, "지금"은 보지 않는다. 그래서 리포트·퍼널 응답에 `meta.asOf`(서버가 판단에 쓴 "지금", UTC ISO)를 더한다.
  - `bucket > asOf`인 묶음은 그리지 않는다(0이 아니라 빈칸). 표는 서버의 행 그대로라 이벤트가 없는 묶음은 행이 없다.
  - `bucket ≤ asOf < 다음 묶음의 bucket`(마지막이면 `rangeEnd`)인 묶음은 "진행 중"이다. 점선과 표의 표시로 다르게 보인다(덜 센 값이 급락으로 읽히지 않게).
  - `partial` 묶음(일부만 찬 첫·끝 주)도 점선이다. 표의 첫 주 칸에는 "일부(`from`부터)"를 요청의 `from` 글자로 붙인다.

**계열, 상위 N개 + 기타**(3단계에서 미룬 것)
- 계열은 고른 차원 값의 짝이다(차원 둘이면 (플랫폼, 캠페인) 짝). 계열의 키는 `JSON.stringify([값…])`다(`null`과 글자 "null", 구분자가 섞이지 않게).
- 값이 없는 것(`null`)은 "(없음)"으로 적는 하나의 값이다. 다른 값처럼 순위에 들어(캠페인 없음은 이벤트의 40%라 보통 맨 앞이다) 따로 그려진다. 상위 N개 밖이면 다른 값처럼 "기타"에 든다. 필터 양식에도 "(없음)"이 있다.
- 그래프는 상위 N개(기본 5)만 그린다. 순위는 기간 합계로 매긴다: 지표에 이벤트 수가 있으면 이벤트 수, 사용자 수뿐이면 묶음별 사용자 수의 합이다(고유 사용자 수가 아니라고 화면에 적는다). 지표가 둘이면 같은 계열을 쓰고, 그래프는 지표 하나를 골라 그린다(탭).
- **이벤트 수는 나머지를 "기타" 하나로 더한다. 사용자 수는 더하지 않는다.** 한 사람이 여러 값에 나와 더하면 부푼다(7일 캠페인별로 실제 75,363명이 129,630명이 됨, 설계 리뷰가 잼). 사용자 수는 상위 N개만 그리고 "값 n개를 숨김"을 적는다.
- **표**는 서버의 행 그대로(묶음 × 계열, 긴 표)이고 모든 값을 보인다. 합계 행은 이벤트 수에만 둔다. 사용자 수의 기간 전체는 "단위를 '전체'로 다시 묻기"로 안내한다.
- 행 한도(20,000)가 화면의 상위 N개보다 먼저 걸린다(7일 시간별 × 캠페인 26,704행). 서버의 422 문장에 "단위를 넓히거나 필터로 값을 고르세요"를 보탠다. 시간별 × 캠페인은 사흘 안팎까지다.
- 퍼널의 나눔 행은 예외로 더할 수 있다(사용자마다 진입이 하나라 겹치지 않음, 6.5). 그래프는 나눔 행의 합(나누지 않은 퍼널)의 단계 막대이고, 값마다는 표(단계 수, 끝까지 전환율, 합계 행)다. 값이 많아도(캠페인 200개) 막대가 늘지 않는다.

**그래프**: 손으로 쓴 SVG 둘이다(10장 50). 십자선이 가장 가까운 묶음에 붙어 모든 계열의 값을 보이고(키보드로는 왼쪽·오른쪽 화살표), 계열이 둘 이상이면 범례가 있다.
- 시간 계열: 선(묶음 × 계열), `total`이면 막대.
- 퍼널: 단계마다 가로 막대(끝에 앞 단계 대비)와 표(앞 단계 대비, 1단계 대비). 0/0은 "—"이고, 1단계의 앞 단계 대비는 비운다. 나눔의 행은 진입 수가 큰 값부터다.
- 표가 늘 함께 있다(그래프의 접근성 대안이자 정확한 수).

**알림**
- 422 `out_of_retention`·`too_many_rows`, 503 `report_timeout`·`busy`는 서버의 문장을 그대로 보이고, 503에는 다시 하기 단추를 둔다.
- `provisional`(최근 리포트에서는 거의 늘 켜짐)과 `stale`은 작은 표시로 알린다.
- 퍼널: "첫 진입 기준 전환"과 한 줄 설명을 늘 보인다. "기간 안 첫 1단계부터 N분 안에 끝낸 사용자만 셉니다. 같은 기간의 '마지막 단계' 사용자 수 리포트보다 작거나 다를 수 있습니다." 필터는 모든 단계에, 나눔은 진입에 건다는 것도 적는다. `windowEnd > meta.asOf`이면 "전환 기간이 아직 끝나지 않은 진입이 있음"을 알린다(날짜 글자는 보이지 않는다).
- 리텐션: `users: null`(아직 오지 않은 날)인 행은 빼고 보인다. `null` 칸은 빈칸("아직 지나지 않음" 범례), `users: 0`인 무리의 비율은 "—"(0/0)로 기호를 나눈다. `cohort === meta.today`인 행에는 "진행 중"을 붙인다. 합계·평균 행은 두지 않는다(무리가 겹친다). N일째는 그날만 센다(누적이 아님)고 적는다. 비율은 한 색의 농도로도 보이되, 표의 가장 큰 비율이 가장 짙다(리텐션은 대개 몇 %~몇십 %라 비율 그대로면 보이지 않는다).

**차원 값과 이벤트 이름 목록**: 새 API 없이 `POST /reports/query`(이벤트 수, 단위 `total`, 차원 하나, 양식의 기간)로 채운다. 필터 값과 퍼널 단계를 손으로 치지 않게 한다(오타가 오류 없이 0이 된다).

**저장한 리포트**
- 표 `saved_reports(id uuid, name text, kind text, config jsonb, created_at, updated_at)`. `kind`는 `report`·`funnel`·`retention`이고 CHECK를 둔다. 이름은 유일하다(종류가 달라도).
- API: `GET /saved-reports`(목록, `lower(name), name` 순), `POST`, `PUT /saved-reports/:id`, `DELETE /saved-reports/:id`. 수집과 같은 풀을 쓴다(짧은 쓰기).
  - 본문은 공유 스키마의 `kind`별 합(`z.discriminatedUnion`)이다. **저장하는 것은 검사를 거친 값**이다(기본값이 채워진 것). 기본값이 나중에 바뀌어도 옛 설정의 뜻이 조용히 바뀌지 않는다.
  - 이름은 `Text(100)`(NUL·서로게이트 거절)이고 앞뒤 공백을 자른다. `:id`는 uuid로 검사한다(400). 이름이 겹치면 409(23505, POST와 이름을 바꾸는 PUT), 없는 id는 404다. PUT은 `updated_at = now()`다.
  - **목록의 응답은 `config: unknown`과 `valid: boolean`이다.** 서버가 행마다 `kind`의 스키마로 `safeParse`해 정한다. 응답 스키마를 `kind`별로 엄격하게 적으면, 맞지 않는 옛 설정 하나 때문에 목록 전체가 500이 된다(응답도 스키마로 직렬화하므로, 설계 리뷰).
  - 화면은 열 때 다시 `safeParse`한다. 맞지 않으면 "설정이 바뀌어 열 수 없음"과 설정 내용(읽기 전용)을 보이고 지우기만 할 수 있다.
- **저장한 기간은 날짜 그대로다**("최근 7일"이 아니다). 열면 양식에 날짜를 채우고 고칠 수 있다. 90일이 지나 422 `out_of_retention`이면 "날짜를 고치세요"로 안내한다. 상대 기간은 미룬다.
- 저장하는 것은 지금 보이는 결과의 설정이다(양식에서 고치고 "보기"를 누르기 전의 것이 아니다). 결과가 없거나 세는 중이면 저장할 수 없다. 열면 그 설정으로 양식을 채우고 바로 센다(목록에서 연 것을 다시 누르면 저장한 설정으로 돌아간다). 연 것은 "저장"이 PUT(이름을 고쳐 저장하면 이름 바꾸기), "다른 이름으로 저장"이 POST다.
- POST가 409면 같은 종류의 다른 리포트일 때만 "덮어쓰기(PUT)"를 권하고, 아니면 다른 이름을 고르게 한다(다른 종류를 덮으면 그 리포트가 사라진다). 이름을 바꾸는 PUT이 409면 덮어쓰기를 권하지 않는다(덮으면 두 리포트가 하나가 된다). 연 것이 그 사이 지워졌으면(PUT 404) 보던 설정과 결과를 두고 "다른 이름으로 저장"하게 한다. 연 뒤 다른 설정으로 보면 "저장 안 된 변경"을 표시한다. 마지막에 쓴 것이 남는다(혼자 쓰는 로컬 도구, 버전·공유 없음).
- 지우기는 두 번 누르고, 이미 지워졌으면(404) 지운 것으로 본다. 저장(새 id)·지우기 뒤의 이동은 주소를 바꿔 넣고(뒤로 가기가 빈 화면이나 지운 것으로 가지 않게), 그 요청을 낸 화면이 아직 있을 때만 한다. 알림은 새로 붙는 화면 바깥의 늘 있는 자리가 읽고, 포커스는 제목으로 옮긴다.
- 다른 종류의 id로 열면 그 화면으로 가는 길을, 없는 id면 "찾을 수 없음"을 보인다. 좁은 화면에서 목록은 본문 위 가로 한 줄이다.
- 앱 role의 권한은 0000의 기본 권한으로 따라온다(DML만). 앱 role로 테스트한다(`has_table_privilege`).

**E2E**(Playwright 하나, 10장 55)
- seat-booking과 같은 틀이다. DB `event_analytics_e2e`, 포트 API 3102·화면 5175, 주소는 모두 `127.0.0.1`이다.
- **날짜는 한 곳에서 정한다.** `playwright.config.ts` 맨 위에서 `process.env.E2E_DAY ??= 한국 시각의 어제`로 한 번 정하고, `webServer.env`로 준비에 넘긴다. 테스트(worker)는 같은 환경 변수를 읽는다. 준비와 테스트가 각자 계산하면 그 사이 한국 시각 자정을 넘을 때 어긋난다.
- `e2e:prepare`(소유자): 경로가 `/event_analytics_e2e`가 아니면 거절, 지우고 `NEW_DATABASE_OPTIONS`로 만들기(builtin `C.UTF-8`, 정렬 확인), 마이그레이션, 파티션(`dbToday` − 7일 ~ + 7일, 관리 작업의 만들기와 같은 범위. 한국 시각의 하루는 UTC 파티션 둘에 걸친다), 고정 데이터(한국 시각 10~14시, 오프셋을 붙인 글자).
- `e2e:serve`: 소유자 주소를 지우고 `INGEST_WRITE_KEY`를 무작위로 넣은 뒤 서버를 띄운다(화면은 수집하지 않는다). 스크립트는 `--env-file`을 쓰지 않고, `webServer.env`가 다섯 키(`DATABASE_URL`, `DATABASE_OWNER_URL`, `PORT`, `HOST`, `E2E_DAY`)를 모두 준다.
- 서버의 집계 작업이 테스트 중에 돌아도 수는 같다(집계 행과 워터마크를 함께 커밋하고, 리포트는 한 스냅샷에서 읽는다. 설계 리뷰가 확인함). `meta.source`만 바뀔 수 있다.
- 시나리오: 리포트를 설정해 표의 수가 고정 데이터와 같다 → 이름(재시도에 겹치지 않게 무작위 꼬리)을 붙여 저장 → 목록에서 다시 열어 같은 수. 저장한 화면에서 바로 지우면 "저장했습니다"가 남지 않는다. 퍼널에서 고정 데이터의 단계 수와 "첫 진입 기준". 리텐션에서 어제 무리의 1일째가 "아직"(빈칸)이다. 실행 중 한국 시각 자정을 넘기면 서버의 `meta.today`로 기대값을 정한다.
- CI: `e2e` 작업을 더한다(postgres:18, role 둘, Playwright chromium, 15분). 소유자 주소를 읽는 새 파일 셋(`e2e-prepare-cli.ts`, `e2e-serve-cli.ts`, `playwright.config.ts`)을 `ci.yml`의 허용 목록에 더한다. 테스트 작업에 화면의 형 검사·빌드·단위 테스트를 더한다. `.gitignore`에 `test-results/`, `playwright-report/`.

**테스트**
- 화면 단위 테스트(jsdom): 순수 변환(빈 묶음 채우기, 진행 중·아직 오지 않은 묶음, 계열 펼치기와 키, "(없음)", 상위 N개 + 기타와 사용자 수 규칙, 표의 합계 행, 퍼널 전환율과 0/0, 리텐션 비율과 `null`·0/0·진행 중), 두 `01:00`과 `partial` 묶음, 설정 양식이 스키마를 지키는지, 오류 표시.

### 6.8 측정과 튜닝 (7단계 설계)

합격 기준 A7이다. 부하 중 리포트의 p95를 재고, **측정이 가리킨 병목**을 고친 뒤 다시 잰다. 수집 처리량이 꺾이는 점도 잰다. 이 단계에서 설명할 것은 "병목이 어디였고 어떻게 찾았나"다. 그래서 이 설계는 무엇을 고칠지 정하지 않는다. 찾는 절차, 증거가 무엇을 가리키는지, 증거가 가리킬 때만 고칠 후보를 정한다.

**바꿀 수 있는 범위(앱 쪽만)**
- 사용자의 PostgreSQL 서버는 바꾸지 않는다. `ALTER SYSTEM`도 재시작도 없다.
  - 그래서 `pg_stat_statements`(서버 시작 때 불러야 함), `shared_buffers`, 서버 전체의 `work_mem`, `track_io_timing`(슈퍼유저)은 쓰지 않는다.
  - `auto_explain`도 쓸 수 없다. 슈퍼유저가 아니면 `$libdir/plugins` 밖의 라이브러리를 `LOAD`할 수 없다. 느린 문장·잠금 대기·임시 파일의 로그 설정도 슈퍼유저 전용이다.
- 쓸 수 있는 손잡이
  - 리포트 트랜잭션 안의 `SET LOCAL`: `work_mem`, `hash_mem_multiplier`, `jit`, `enable_*`, `max_parallel_workers_per_gather`(모두 USERSET)
  - 인덱스·확장 통계(소유자의 마이그레이션), 질의 모양
  - 풀 크기와 시간 한도(`DB_POOL_MAX`, `REPORT_POOL_MAX`)
  - 소유자가 도는 관리 작업(`db:maintain`)이 하는 일
- 쓰지 않는 손잡이(서버 튜닝을 우회하는 것)
  - 비용 상수(`random_page_cost`, `effective_cache_size`, `parallel_*_cost`)를 `SET LOCAL`로 바꾸기
  - `synchronous_commit`: USERSET이지만 수집의 200 응답이 보장하던 내구성(A1·A2)을 바꾼다. 바꾸려면 따로 결정으로 적는다.
  - IO가 원인으로 나와도 서버 쪽 답(`shared_buffers`, `max_wal_size`, `wal_compression`, `checkpoint_timeout`)은 범위 밖이다. 앱 쪽 답은 읽거나 쓰는 양을 줄이는 것뿐이다.
- **ANALYZE·VACUUM은 소유자만 한다.** 앱 role(DML만, 10장 12)의 `ANALYZE`는 오류 없이 경고(01000)만 내고 건너뛴다(`roles.test.ts`가 확인함). 그래서 통계를 챙기는 일은 소유자 경로에만 둔다. 앱 role에 `MAINTAIN`(PG17+)을 주면 `VACUUM FULL`·`CLUSTER`·`LOCK`까지 열려 10장 12가 바뀌므로 하지 않는다.

**설계 전에 확인한 것**
- **이 PC의 autovacuum은 사용자 표를 처리하지 않는다.**
  - event_analytics의 파티션 98개는 한 번도 자동 분석되지 않았다. 통계는 손으로 한 `ANALYZE`뿐이다. seat_booking도 10-21 뒤로 없다.
  - 새 DB에 표 하나를 만들고 20만 행을 넣은 뒤 4분(naptime 60초의 4배)을 기다려도 자동 분석이 없었다.
  - 원인이 아닌 것:
    - 통계는 쌓인다. `track_counts`가 켜져 있고, 시험 표의 `n_mod_since_analyze`·`n_ins_since_vacuum`이 20만이었다.
    - wraparound 우선순위가 아니다. DB마다 xid 나이가 636만(한도 2억)이고, 복제 슬롯과 준비된 트랜잭션이 없다.
    - 다른 DB의 긴 VACUUM에 붙잡힌 것도 아니다. `pg_stat_progress_vacuum`·`_analyze`를 20초 간격으로 세 번 봐도 행이 없었다.
  - 공유 카탈로그(`pg_shdepend` 등)는 수백 번 처리됐다.
  - 더 보려면 슈퍼유저로 autovacuum 일꾼과 서버 로그 설정을 봐야 한다. 서버의 일이라 사용자에게 넘긴다.
- **이것과 별개로 PostgreSQL은 파티션 부모 표를 자동 분석하지 않는다(설계).** 부모의 통계는 파티션을 가로지르는 묶기·조인의 어림에 쓰인다. 날마다 새로 생기는 파티션도 무언가 분석하기 전까지 통계가 없다.
  - 그래서 "통계"는 둘로 나눈다. 부모 표는 어느 서버에서나 생기는 앱의 빈틈이다. 오늘 파티션은 정상 서버라면 autovacuum이 금방 분석하므로, 이 PC의 결함이 만든 장면이다.
  - 하루 한 번 도는 관리 작업으로는 낮 동안 쌓이는 오늘 파티션의 통계를 새로 할 수 없다.
- `pg_stat_statements`는 깔려 있지 않다.
- 앱 role로는 다른 role의 `pg_stat_activity` 행이 거의 비어 보인다(`backend_type`까지 null). 표본기는 API의 연결만 본다.

**측정 템플릿**(회차마다 같은 출발점)
- 개발 DB는 계속 바뀐다(집계 작업, 관리 작업의 떼기, 손으로 한 `ANALYZE`). 그래서 측정 전용 템플릿 `event_analytics_load_template`을 한 번 만들고, 회차마다 그것을 `event_analytics_load`로 복제한다.
- 만들기: 개발 DB를 복제 → 집계 작업을 끝까지(`dirty_hours`가 비고 워터마크가 데이터 끝 이상) → 소유자로 잎 표마다 `VACUUM (FREEZE, ANALYZE)` → 일반 표마다 `autovacuum_enabled = false`(사용자가 서버의 autovacuum을 고쳐도 회차 조건이 같게).
  - DB 전체 VACUUM은 파티션 부모(`events`)까지 분석한다. 운영 서버에서 부모는 자동으로 분석되지 않으므로, 잎만 이름으로 해서 부모는 통계 없이 둔다. 그래야 후보 "부모 표의 통계"를 `ANALYZE ONLY events` 전후로 볼 수 있다(코드 리뷰).
- 복제는 `STRATEGY FILE_COPY`다. 기본값 `WAL_LOG`는 2.7GB를 WAL로 써서 측정 앞부분에 체크포인트가 겹친다. `FILE_COPY`는 앞뒤로 체크포인트를 하고 WAL이 적다.
- 실행기는 복제한 뒤 확인하고 기록한다.
  - `dirty_hours`가 비어 있고 워터마크가 데이터 끝 이상인지(아니면 회차를 거절)
  - 파티션 수와 행 수, 표마다 `relallvisible`·`n_dead_tup`·`last_(auto)vacuum/analyze`
  - 환경: `data_checksums`, `io_method`, `io_workers`, `max_parallel_workers`, `max_worker_processes`, `pg_jit_available()`
- 실행기는 템플릿보다 뒤의 마이그레이션을 복제에 먼저 적용한다(고침의 확장 통계 0004 등. 템플릿을 다시 만들지 않고 전후를 번갈아 재려고). 그래서 템플릿은 0004 앞의 DB에서 만든다(PostgreSQL 18에는 확장 통계를 지우는 함수가 없다).
- 실행기는 관리 작업 가운데 **만들기와 부모 표의 통계만** 돈다(부모 표의 통계는 첫 고침으로 더함, 10장 62. 템플릿에는 없고 회차마다 새로 한다). 만들기는 관리 작업과 같은 범위다(지난 7일 ~ 앞으로 7일. 지난 7일이 없으면 늦은 이벤트가 `partition_missing`이 된다). 새로 만든 파티션도 autovacuum을 끈다(`LIKE`로는 이어받지 않는다). 떼기는 돌지 않는다. 날이 지나면 보관 기간 밖 날이 생기는데, 회차마다 파티션 수와 행 수를 남겨 같은 일을 했는지 본다.
- 템플릿에서 복사된 워터마크와 지금 사이를 집계 작업이 따라잡을 때까지(워터마크 = 지금의 정시) 예열을 시작하지 않는다.
- 측정하는 동안에는 개발 API를 띄우지 않는다(복제에는 원본 DB에 연결이 없어야 한다).

**장면**

  - 몫의 근거: 대시보드에서는 이벤트 수 리포트를 자주 보고, 퍼널·리텐션은 가끔 연다. 몫이 판단을 미리 정하지 않는지 보려고, 같은 몫(모두 1)으로도 한 번 재서 고칠 곳의 순위가 바뀌는지 본다.
  - 1~6은 날짜를 고정해, 회차 사이와 고치기 전후가 같은 일을 한다. 6은 돌아옴 범위의 끝(무리 끝 + 1 + 30일 = 10-27)이 데이터 안이라 오늘 파티션을 읽지 않는다. 5단계에서 16초로 잰 그 질의다.
  - 7은 배경 수집과의 겨룸을 보는 리포트다. 원본 꼬리(워터마크부터 지금까지)가 정시까지 커진다. 그래서 표본마다 시작한 분과 오늘 파티션 행 수를 함께 남기고, 다른 종류와 따로 읽는다.
  - 90일은 이미 보관 기간 밖에 걸려(오늘 − 90일 > 07-29) 60일로 줄였다. 11-25(UTC)가 지나면 6이, 하루 뒤 3이 보관 기간 밖에 걸린다. 걸리면 실행기·진단 도구가 멈추므로 그때 날짜를 함께 옮기고 적는다.
- **지표**(종류마다, 정상 구간)
  - 성공한 요청의 p50·p95와 표본 수, 503(`busy`, `report_timeout`)의 비율과 503까지 걸린 시간
  - 503이 5%를 넘는 종류는 p95를 "한도 이상"으로 적는다. 503을 지연에서 빼면 고친 뒤 503이 줄어든 것이 p95를 나쁘게 보이게 할 수 있다.
  - 요청 시간 = 풀 연결 대기 + 실행. API가 `LOAD_STATS`일 때 응답 머리 `Server-Timing`에 풀 대기를 실어 k6가 종류별로 나눈다.
  - 수집: 처리량, p95, 5xx, 응답의 중복·거절 수
- **반복**: 판단 회차는 고치기 전과 뒤를 같은 날 번갈아 3회씩 잰다(전·후·전·후·전·후). 가운데 값과 범위를 적고, 범위가 겹치지 않을 때만 개선을 주장한다. 같은 PC에서 재고, 그동안 빌드·테스트처럼 무거운 일은 하지 않는다. 숫자는 이 PC의 전후 비교로만 쓴다.
- **무효 조건**: 회차 앞뒤로 다른 DB의 `xact_commit` 차이가 0이 아니면(다른 일이 같은 서버를 씀) 그 회차를 무효로 한다. 측정 DB에 vacuum·analyze 진행 행이 있었으면 적는다.

- `load:report-bench`는 진단에만 쓴다. 머리 숫자(p95)는 HTTP와 동시 사용자로 잰다.
  - EXPLAIN은 API와 같은 트랜잭션 틀(`inReportTransaction`)에서 돌린다. 그래야 고침으로 더한 `SET LOCAL`이 실행 계획에도 걸린다.

  - 진단 회차의 p95는 세지 않는다. EXPLAIN 자체가 리포트 풀 밖의 다섯째 무거운 질의다.

**판단 규칙**
- 판단은 판단 회차(N = 4, 20분)로 한다.
- 고치는 것은 사용자가 기다린 시간(요청 수 × 시간, 503까지 기다린 시간 포함)의 가장 큰 몫이 앉은 곳이다.
  - 풀 대기는 그동안 연결을 쥔 종류에 연결-초의 비율로 나눠 준다.
  - 몫을 바꿔(같은 몫) 순위가 바뀌면 그것도 적고, 두 몫 모두에서 큰 곳을 먼저 고친다.
- 전후 판정: 고친 종류의 p95가 줄고, 503 비율이 늘지 않으며, 다른 종류의 p95가 나빠지지 않는다. 열린 모형 확인도 같은 결론이어야 한다.
- 머리 숫자는 "고친 종류의 p95"다. 일곱 종류를 섞은 전체 p95는 쓰지 않는다(느린 종류의 분포에 묻힌다).
- PR 하나에 고침 하나다. 고친 뒤 같은 날 번갈아 다시 잰다.
- 다음 후보의 기대 이득이 회차 사이의 흔들림보다 작으면 멈춘다.
- 미리 정한 지표가 움직이지 않아도 그대로 적는다(seat-booking 6단계의 교훈).

**5,000만 건**: 고침을 고른 뒤, 5,000만 건 템플릿에서도 전후를 번갈아 잰다(판단 회차, 3회씩). 규모가 결론을 바꾸는지 보려는 것이다.

- 13GB 안팎이라 64GB PC의 OS 캐시에 다 들어간다. 디스크에서 읽는 영역까지는 가지 않는다고 적는다.
- 개발 DB는 그대로 둔다. 그래서 개발 DB로 중간 템플릿(`event_analytics_load_50m_src`)을 만들어 거기에 더하고, 그것을 원본으로 측정 템플릿을 다시 만든다(`load/README.md`). 템플릿 이름은 명령줄로 받되, 만들 때 그 DB를 지우므로 `event_analytics_load_` 접두어만 받는다.
- 고치기 전 회차는 main에서 첫 고침(#43)의 두 효과(마이그레이션 0004, 복제의 부모 분석)만 뺀 코드로 돈다(작업 트리의 로컬 커밋). 그래야 전후가 고침 하나만 다르고 실행기와 상태 기록은 같다. 템플릿은 0004 앞의 개발 DB에서 나온다.

### 6.9 seat-booking 연결 (8단계 설계)

합격 기준 A8이다. seat-booking의 이벤트가 outbox로 빠짐없이 한 번 이상 오고, 저장은 한 번이다. outbox 표와 릴레이는 seat-booking에 둔다(그 저장소의 DESIGN 6.8). 이 저장소가 정하는 것은 받는 계약(6.1을 그대로 씀)과 확인 방법이다.

**보내는 이벤트**(seat-booking의 서버 이벤트, 결정 65)

| 이벤트 | seat-booking에서 생기는 곳 | properties |
|---|---|---|
| `seats_held` | 선점 트랜잭션 | `performanceId`, `holdId`, `seats`(좌석 수) |
| `order_created` | 주문 트랜잭션 | `performanceId`, `holdId`, `orderId` |
| `payment_succeeded` | 결제 성공 반영(웹훅과 대사가 함께 쓰는 함수) | `performanceId`, `orderId`, `paymentId` |

- 업무의 쓰기와 같은 트랜잭션에서 outbox에 넣는다. 업무가 되돌아가면 이벤트도 없다. 업무가 커밋되면 이벤트도 남는다. 이것이 outbox를 쓰는 까닭이다. 업무를 커밋한 뒤 바로 HTTP로 보내면, 그 사이에 죽거나 수집이 503일 때 이벤트를 잃는다. 반대로 먼저 보내고 커밋하면, 커밋이 실패할 때 없던 일이 이벤트로 남는다.
- `userId`는 seat-booking 사용자 id의 문자열이다. `platform`은 `web`이다(seat-booking은 웹 앱). `channel`·`campaign`·`country`는 없다(서버가 모른다).
- **목록·좌석 지도 조회는 보내지 않는다.**
  - 쓰기가 없는 공개 경로다. 지킬 원자성이 없고, 세션을 읽지 않아 사용자도 없다.
  - 좌석 지도는 seat-booking의 가장 뜨거운 경로다(6단계 꺾이는 점 초당 약 1,000). 여기에 쓰기를 더하면 그때 잰 것이 바뀐다.
  - 조회는 화면 쪽 수집(SDK)의 일이고, 이 프로젝트에는 SDK가 없다(2장).
  - 그래서 seat-booking 데이터의 예매 퍼널은 선점 → 주문 → 결제 세 단계다. 생성기 데이터의 다섯 단계 퍼널은 그대로 둔다.
- 시각은 outbox에 넣는 순간의 `date_trunc('milliseconds', clock_timestamp())`다.
  - `now()`(트랜잭션 시작)가 아니다. 잠금을 오래 기다린 트랜잭션도 이벤트 시각은 그 일을 한 때다. 한 트랜잭션에 이벤트를 둘 넣는 곳은 없다(5단계 주의를 닫음).
  - 수집은 시각을 ms로 자르고 값으로 견준다. 처음부터 ms로 두면 다시 보낸 값이 같다는 것이 분명하다. 보내는 글자는 `toISOString()`이다(PostgreSQL의 글자 `2026-10-28 01:02:03.456+00`은 수집이 거절한다).
  - 한 사용자의 두 단계가 다른 요청에서 같은 ms에 들면 퍼널의 엄격한 `>`에서 빠진다(10장 43). 사람의 행동 사이라 드물다. 리허설에서는 단계 사이에 생각 시간을 둔다.

**릴레이**(seat-booking에 둠, 결정 66)
- 보내지 않은 행을 `sent_at is null and parked_at is null order by id limit N`으로 매번 고른다(부분 인덱스). "마지막으로 보낸 id" 같은 커서는 두지 않는다. 낮은 id의 트랜잭션이 늦게 커밋되면 커서가 그 행을 건너뛴다(outbox의 이름난 틈). `sent_at`이 비어 있는 한 다음 바퀴가 줍는다.
- 하나만 돈다(프로세스 내내 쥐는 전용 연결의 advisory lock). HTTP를 기다리는 동안 행 잠금을 쥐지 않는다.
- 보내기(`send(batch)`)와 적기(`markSent(ids)`)를 나눈다. 보낸 뒤 적기 전에 죽으면 다음 바퀴가 같은 배치를 다시 보낸다. 수집은 `(event_id, occurred_at)`로 둘째 것을 `duplicates`로 세고 저장하지 않는다. "정확히 한 번" 대신 "한 번 이상 보내기 + 멱등 저장"이다(6.1).
  - 정확히 한 번이 어려운 까닭: 보내는 쪽은 상대가 저장했는지와 자기가 그것을 적었는지를 한 원자적 일로 묶을 수 없다. 두 DB(두 서비스)에 걸친 트랜잭션이 없으면, 어느 순서로 해도 그 사이에 죽을 수 있다.
- 응답별로 하는 일은 6.1의 표를 따른다.
  - 200이면 적는다. `rejected`는 그 행을 보관으로 돌리고 까닭을 남긴다.
  - 400·415는 보관한다. 401은 멈춘다. 413은 반으로 나눈다.
  - 503과 네트워크 오류·시간 초과는 간격을 늘려 횟수 제한 없이 다시 보낸다. 6.1은 네트워크 오류에도 횟수를 정하라고 했지만, 수집이 꺼져 있으면 오류가 곧바로 나서 몇 초 만에 모두 보관된다(설계 리뷰). 한도는 7일(`too_old`)이다.
  - 500과 표에 없는 응답은 행마다 횟수를 세어 다시 보내고, 넘으면 보관한다. 보관한 행은 되살리는 명령이 있다.
- 7일 넘게 못 보낸 이벤트는 `too_old`로 보관된다. 6.1의 "알고 받아들이는 손실"이다.

**확인(A8)**
- seat-booking 테스트(가짜 수집 서버)
  - 업무가 되돌아가면 이벤트가 없다. 멱등 재생(같은 요청 키)은 이벤트가 하나다.
  - 보낸 뒤 적기가 한 번 실패하면 같은 `(eventId, occurredAt)`를 다시 보낸다.
  - 응답마다 위의 일을 한다.
- 이 저장소: 같은 키의 둘째 저장이 `duplicates`인 것은 1단계 테스트가 이미 지킨다.
- **연결 리허설**
  - 새 event-analytics DB와 API(다른 포트)에 새 seat-booking DB(`e2e:prepare`처럼 만듦)와 릴레이를 붙인다. seat-booking의 부하 데이터 도구는 outbox를 거치지 않고 업무 행을 넣으므로, 그 DB에서는 수가 맞지 않는다.
  - 스크립트로 여러 사용자의 예매 흐름(선점 → 주문 → 결제, 일부는 이탈)을 돌린다.
  - 그 사이 릴레이를 죽였다 살린다.
  - 셋의 수가 같은지 본다. seat-booking의 업무 행(선점·주문 행 수, 성공 결제 수), outbox 행, event-analytics에 저장된 이벤트(종류별)다. outbox의 보관·미전송은 0이어야 한다. 다시 보낸 것은 릴레이 로그의 `duplicates` 합으로만 보인다.
  - 그 DB에서 세 단계 퍼널을 그린다.
  - 이 저장소의 E2E 준비는 DB 이름(`event_analytics_e2e`)과 고정 이벤트를 정해 두고, E2E 서버는 쓰기 키를 무작위로 만든다. 리허설용으로 DB 이름, 고정 데이터 끄기, 쓰기 키를 받게 한다(소유자 주소를 읽는 새 파일은 CI의 허용 목록에 더한다).
- 개발 DB(`event_analytics`)에는 넣지 않는다. 생성기 데이터와 같은 이벤트 이름이라 섞이고, 측정 템플릿의 원본이다.

**PR 순서**: 이 설계 → seat-booking 설계 → seat-booking outbox 표와 넣기 → seat-booking 릴레이 → 연결 리허설과 기록(두 저장소)

## 10. 정한 것

1~11은 권장안을 사용자가 그대로 확정했다(2026-10-27, "그대로해줘. 너가 다 해줘. 내가 검토할게").

1. 이름은 `event-analytics`다. GitHub 공개 저장소는 사용자가 권한을 준 뒤 만들었다.
2. 스택은 seat-booking과 같다.
   - 서버: TypeScript ~6.0.3, Fastify 5, Drizzle 0.45, PostgreSQL 18(같은 서버, DB `event_analytics`)
   - 화면: React 19 + Vite + TanStack Query
   - 공통: `packages/shared` zod, Vitest, k6
   - 차트 라이브러리는 6단계에서 정한다.
3. PostgreSQL만 쓴다. 컬럼형 DB는 쓰지 않는다(1장 이유).
4. 파티션 키는 `occurred_at`이고 일 단위(UTC)다. 받을 기간은 과거 7일, 미래 1시간이다. 보관은 90일이다. `received_at` 파티션과의 비교는 2단계에서 한다.
5. 중복 제거는 유일 키 `(event_id, occurred_at)`로 한다.
   - 재전송은 같은 `occurred_at`을 싣는다고 보고, 테스트로 확인한다.
   - 보내는 쪽이 시각을 다시 만들면 받는 쪽은 막지 못한다고 적는다.
   - 대안(파티션하지 않은 최근 id 표)은 1단계 설계에서 견준다.
6. 데이터 규모는 기본 1,000만 건, 측정은 5,000만 건까지다.
7. 확장은 쓰지 않는다(`hll`·`pg_partman`·`pg_cron` 없음, `pg_stat_statements`는 서비스를 다시 띄워야 켜짐). 파티션 관리와 고유 사용자 수는 직접 한다.
8. 로그인은 없다. 수집은 쓰기 키로 지킨다. 앱은 하나다.
9. 배포는 없다.
10. 진행은 seat-booking과 같다: 단계마다 설계 PR → 짧은 PR → 리뷰 서브에이전트 → CI → 머지. 0~8단계 모두 묻지 않고 진행하고, 끝난 뒤 사용자가 한꺼번에 검토한다(사용자 결정). 단계 안의 판단은 이 장에 번호를 이어 적는다.
11. 8단계(seat-booking 연결)는 seat-booking 저장소에도 PR을 낸다.

0단계에서 정한 것(AI 판단):

12. **seat-booking 7단계의 것을 가져온다.** 가져오는 것은 셋이다.
    - 마이그레이션 실행기와 그 테스트. 마이그레이션마다 트랜잭션, 잠금 대기 1초와 다시 하기, `-- 트랜잭션 밖`, INVALID 인덱스 확인, drizzle 기록 호환이 들어 있다.
    - role 나누기. 소유자 `event_analytics`, 앱 `event_analytics_app`(DML만)으로 나누고, 권한은 첫 마이그레이션이 준다.
    - 템플릿을 복제하는 테스트 DB.

    다시 만들지 않는 이유가 있다. 이 셋은 seat-booking에서 리뷰와 변이 시험으로 고친 결과다. 다시 만들면 같은 버그(CONCURRENTLY와 advisory lock의 교착, 연결이 끊길 때 프로세스가 죽음)를 다시 밟는다. 이 프로젝트의 2단계는 파티션을 만들고 떼느라 DDL이 잦아, 잠금 대기를 묶는 실행기가 처음부터 필요하다.

    실행기(`migrate.ts`)는 주석 말고 그대로다. 나머지에서 바꾼 것은 이렇다.
    - 테스트 준비의 advisory lock 번호. postgres DB에서 잡으므로 seat-booking과 같으면 두 저장소의 테스트가 서로 기다린다.
    - 새 DB를 만드는 옵션(13)과 앱 풀의 UTC 고정(14).
    - 첫 마이그레이션은 이미 있는 표에 권한을 주지 않는다(표가 없다). 앞으로 만들 표와 파티션에 붙는 기본 권한만 둔다.
    - 테스트에서 seat-booking의 표를 쓰던 것은 시험용 표와 만든 폴더로 바꿨다.
    - 리뷰에서 나와 더한 것: 풀의 쉬는 연결이 끊길 때 프로세스가 죽지 않게 `error`를 듣는다(seat-booking에도 같은 빈틈이 있다). 서버의 연결 대기는 5초로 묶는다.
13. **DB는 UTF8, builtin `C.UTF-8` 정렬로 만든다**(`LOCALE_PROVIDER builtin`, PostgreSQL 17부터). 정렬을 OS에 맡기면 로컬과 CI가 다르다. 로컬은 Windows의 `Korean_Korea.949`, CI는 Linux의 `en_US.utf8`이다. 이 프로젝트는 차원 값(국가·채널·캠페인)으로 묶고 정렬하므로, 같은 쿼리의 행 순서가 두 곳에서 달라진다.
    - builtin `C.UTF-8`은 코드 포인트 순서로 정렬하고, 대소문자는 유니코드로 바꾼다. OS 라이브러리가 바뀌어도 인덱스 순서가 그대로다.
    - 사람이 읽기 좋은 정렬(가나다, 대소문자 무시)은 필요한 곳에서 `COLLATE`로 따로 쓴다.
    - 새로 만드는 DB(개발, 테스트 템플릿, CI)는 모두 같은 옵션을 쓴다(`NEW_DATABASE_OPTIONS`).
14. **앱 연결의 세션 시간대를 UTC로 고정한다**(`createPool`이 `-c TimeZone=UTC`를 붙임. 주소의 `?options=`와 호출한 쪽의 options 뒤에 붙여 늘 이긴다). 서버 기본값은 로컬이 Asia/Seoul, CI가 UTC다. 그래서 시간대 없는 시각 글자나 `timestamptz → date` 변환이 어디서 도느냐에 따라 다른 날이 된다. 파티션 경계와 시간 집계는 UTC 기준이다(10장 4).
    - 리포트의 시간대(기본 Asia/Seoul)는 세션 설정이 아니라 쿼리의 인자로 준다(`AT TIME ZONE $tz`, 3인자 `date_trunc`).
    - 세션 고정은 실수를 줄이는 장치일 뿐이다. 코드는 거기에 기대지 않고 시각 글자에 오프셋을 붙인다(`'2026-10-27 00:00+00'`). 소유자 연결(마이그레이션, 파티션 만들기)은 이 풀을 쓰지 않기 때문이다.

1단계에서 정한 것(AI 판단, 6.1):

15. **이벤트는 한 건씩 판단한다.** 틀린 것만 이유(`invalid`, `too_old`, `too_far_in_future`)와 함께 거절하고 나머지는 저장한다. 400은 봉투가 틀릴 때만이다.
16. **받을 기간의 "지금"은 DB의 트랜잭션 시각이다.** 앱 서버의 시계를 쓰지 않는다. 파티션 관리와 같은 시계를 쓰기 위해서다.
17. **시각은 밀리초로 잘라 저장한다.** 처음에는 글자 그대로(마이크로초) 넘기려 했다. 리뷰에서 반대가 낫다는 것이 나왔다. 보내는 쪽이 재전송 때 시각을 밀리초로 다시 쓰면 글자 그대로는 키가 달라지지만, 자르면 같아진다. 시각을 `Date`로 바꿔 UTC 글자로 넘기므로, PostgreSQL은 보내는 쪽의 오프셋을 보지 않는다.
18. **문자열의 NUL과 짝 없는 서로게이트는 그 이벤트만 거절한다.** 그대로 넘기면 PostgreSQL이 배치 전체를 실패시키거나(NUL, jsonb의 서로게이트), 조용히 U+FFFD로 바꾼다(text의 서로게이트).
19. **중복 제거는 `(event_id, occurred_at)` 기본 키로 한다**(측정으로 10장 5 확인). 최근 id 표는 10% 느리고 표 하나가 따로 커진다. 그 표가 더 거르는 경우(재전송 때 시각을 새로 만듦)는 드물다.
20. **파티션이 없으면 503 `partition_missing`이다.** 기본 파티션은 두지 않는다(6.2). 23514 가운데 표 이름이 `events`(부모)이고 제약 이름이 없는 것만 이것으로 본다. 잠금 대기 초과·교착·문장 시간 초과는 503 `busy`다. 둘 다 다시 보내면 되는 오류다.
21. **쓰기 키는 하나이고, 본문을 읽기 전에 SHA-256 + `timingSafeEqual`로 견준다.**
22. **응답마다 보내는 쪽이 할 일을 정해 둔다**(6.1 표). 401은 지니고 멈춤, 413은 나눠 보냄, 400은 따로 보관, 503은 다시 보냄, 500은 횟수를 정해 다시 보냄. `rejected`는 "이 요청이 저장하지 않은 것"이다.
23. **배치는 키 순서로 넣는다.** 겹치는 배치가 반대 순서로 넣으면 교착(40P01)이 난다. 같은 배치에 같은 `eventId`가 다른 시각으로 있으면 뒤의 것을 거절한다.
24. **`db:partitions`는 잠금 대기를 1초로 묶는다.** `CREATE TABLE … PARTITION OF`가 부모 표를 통째로 잠그므로, 기다리는 동안 수집이 그 뒤에 줄을 서지 않게 한다. 2단계에서 `ATTACH`로 바꾼다.

2단계에서 정한 것(AI 판단, 6.2):

25. **파티션은 `occurred_at`의 일 단위(UTC)로 그대로 둔다.** `received_at`으로 나누면 이벤트 시각으로 하루를 보는 리포트가 여덟 파티션을 읽고, 보관 기간도 받은 시각으로 지워진다.
26. **리포트의 기간은 늘 `occurred_at`의 반열린 구간으로 거른다.** 파티션 키에 형 변환이나 함수(`::date`, `at time zone`)를 씌우면 가지치기가 되지 않아 모든 파티션을 읽는다(확인함). A3는 UTC 하루로 보고, 한국 시각의 하루는 두 파티션이 맞다. 리포트는 이름 없는 문장으로 보낸다(일반 계획은 실행 때 가지를 쳐도 모든 파티션을 잠근다).
27. **기본 파티션은 계속 두지 않는다.** 있으면 파티션을 붙일 때마다 기본 파티션을 잠그고 훑으며, 그 날의 행이 있으면 새 파티션을 만들 수 없다(확인함).
28. **관리 작업은 소유자 명령 하나(`db:maintain`)이고, 하루 한 번 OS 예약 작업으로 돌린다.** 순서는 만들기(`ATTACH`) → 끊긴 떼기 마무리(`FINALIZE`, 1초) → 떼기(`DETACH … CONCURRENTLY`, 5분) → 남은 표 치우기다. 한 단계가 실패해도 다음 단계를 돌리고 끝에 실패로 끝낸다. 겹쳐 돌지 않게 advisory lock을 잡아 보고, 있는지는 이름이 아니라 `pg_inherits`로 본다. "오늘"은 DB 시각이다. API 서버는 표를 만들지 않고, 받을 기간부터 앞으로 3일까지 붙지 않은 날이 있으면 경고만 한다(리뷰 반영).
29. **생성기는 씨앗과 끝 날로 정해진다.** `event_id`까지 씨앗에서 만들고 시각은 고정한 끝 날에서 재어, 다시 넣으면 모두 중복이다. 받을 기간 밖(지난 90일)은 DB에 바로 넣고, 리허설과 측정은 수집 API로 보낸다.
30. **떼기 리허설은 관리 작업, 일반 DETACH(잠금 대기 한도 없음), 기준선(떼지 않음)을 같은 장면(수집 중 + 오래 도는 리포트)에서 견준다.** 수집의 5xx 수(원인별)와 지연, 떼기가 기다린 시간을 숫자로 남긴다.

3단계에서 정한 것(AI 판단, 6.3):

31. **리포트 설정은 허용 목록이다.** 지표 둘, 차원 다섯(0~2개), 필터(차원별 값 목록, `null`로 값 없음도, AND), 기간(리포트 시간대의 날짜, 90일까지), 단위 넷(`hour`·`day`·`week`·`total`), 시간대 여덟이다. 모르는 필드와 목록 밖의 값은 400이다. 보관 기간 밖이 섞인 기간은 422 `out_of_retention`이다.
32. **SQL에는 코드의 상수 식별자와 매개변수만 들어간다.** 기간을 시각으로 바꾸는 일과 시간 묶음은 PostgreSQL이 한다(`at time zone`, 3인자 `date_trunc`). 둘 다 immutable이라 매개변수여도 계획할 때 가지를 친다.
33. **묶음은 기간 끝에서 늘리지 않는다**(일부만 찬 첫·끝 묶음은 `partial`). 일광 절약 시간이 바뀌는 날의 시간 묶음은 23개나 25개다. 응답에 기간의 모든 묶음(빈 것 포함)과 UTC 오프셋을 함께 준다.
34. **요청한 지표만 센다.** 고유 사용자 수는 원본에서 묶음마다 정확히 센다(`count(distinct)`). 행끼리 더할 수 없고, 기간 전체는 `total`로 묻는다.
35. **리포트는 수집과 다른 연결 풀(4개)에서, 빌린 연결 하나의 읽기 전용 트랜잭션으로 돈다(문장 30초, 잠금 대기 3초, 트랜잭션 안에서만).** 행이 20,000개를 넘으면 잘라 주지 않고 422다. 끝이 최근 7일이면 `provisional`이다(리뷰 반영).

4단계에서 정한 것(AI 판단, 6.4):

36. **이벤트 수는 시간 집계 표(UTC 정시 × 차원 다섯) 하나로 센다.** 원본의 38%(385만 행)까지만 줄지만 리포트가 2~7배 빨라진다(측정).
37. **고유 사용자 수는 원본에서 두 단계 `GROUP BY`로 정확히 센다.** `count(distinct)`보다 빠르다(90일 캠페인별 3.9~4.6배는 병렬 부분 해시 집계, 30일 일별 1.35배는 해시 집계만, 4단계 기록). 사용자 × 시간 표는 줄지 않아 버린다. 근사는 쓰지 않는다.
38. **늦은 이벤트는 수집이 같은 트랜잭션에서 더러운 시간을 덧붙여 적고(유일 키 없음), 집계 작업이 조각 트랜잭션마다 범위 안의 것과 가장 이른 늦은 시간부터 `chunkHours`만큼을 가져와 다시 센다.** 유일 키 + `DO NOTHING`은 행을 잠그지 않아 늦게 커밋한 수집을 놓친다. 집계 표가 원본과 다른 것은 다음 작업(1분)까지뿐이다(A6).
39. **집계 작업은 API 서버의 1분 타이머와 명령이다(앱 role).** DDL이 없어 소유자가 필요 없다. 겹쳐 돌기는 `rollup_state` 행의 `for update skip locked`로 막는다(풀의 연결에 세션 잠금이 남지 않게).
40. **리포트는 이벤트만이고 시간대가 정수 시간 오프셋이면 집계 표 + 워터마크 뒤 원본을 한 스냅샷(반복 읽기)으로 센다. 워터마크는 먼저 읽어 매개변수로 넘긴다(계획할 때 가지치기, 코드 리뷰).** 고유 사용자나 30분 단위 시간대는 원본이다. `meta.source`로 알리고, 아직 다시 세지 않은 시간이 기간에 있으면 `meta.stale`이다.
41. **워터마크는 NOT NULL이고 보관 기간의 시작으로 시작한다. 다시 세기는 중복 없는 시간 집합의 INSERT 하나이고, 가져온 시간의 최소·최대로 가지를 친다.** 작업은 조각마다 잠근 행에서 워터마크를 읽고, `setTimeout`으로 잇고, 문장 60초·잠금 대기 3초, 전용 연결이다(리뷰 반영).

5단계에서 정한 것(AI 판단, 6.5, 설계 리뷰 반영):

42. **퍼널은 첫 진입 기준 전환이다.** 진입은 사용자의 기간 안 첫 1단계 하나이고, 전환 기간은 진입부터의 분이다(Mixpanel의 기본). 다음 시도의 전환은 세지 않아 아무 시도 기준의 절반쯤이 된다(7일·15분 결제 16,871 vs 33,234). 아무 시도 기준은 90일에 31초로 문장 한도를 넘어 7단계에서 다시 잰다. 응답(`meta.entry`)과 화면에 이름을 붙이고, 최종 검토에 제품 결정으로 올린다.
43. **k단계는 앞 단계보다 엄격히 뒤의 첫 이벤트다.** 필터는 모든 단계에, 나눔은 진입 이벤트의 값에 건다(같은 밀리초는 `event_id`로 정함). 필터와 나눔에서 `event_name`을 뺀다. 응답은 단계별 사용자 수뿐이고 전환율은 화면이 나눈다.
44. **퍼널 SQL은 단계마다 조인한다.** 한 번 훑는 창 함수 사슬보다 30일에서 3.7배 빠르다(9.3초 vs 2.5초, 측정). 기간 끝 + 전환 기간은 트랜잭션 첫 문장에서 계산해 매개변수로 넘긴다(계획할 때 가지치기).
45. **리텐션은 날마다 무리다.** 무리 d는 그날 시작 이벤트가 있는 사용자 전부(행끼리 더할 수 없음), N일째는 날짜 차이가 N인 날의 돌아옴, 아직 다 지나지 않은 칸은 `null`, 기간의 모든 날을 준다. 처음 설계한 "기간 안 첫 시작 이벤트의 날"은 추세를 만들고 `from`에 따라 값이 바뀌어 버렸다(설계 리뷰). 돌아옴의 끝은 날짜 산술(`($to::date + 1 + $N)::timestamp at time zone $tz`)이다.
46. **한도는 퍼널 90일·전환 기간 7일, 리텐션 무리 31일·30일째까지다(측정, 리텐션 31일 15.4초가 가장 느림).** 리포트·퍼널·리텐션은 같은 트랜잭션 틀을 쓰고, `provisional`의 끝은 각자 정한다(기간 끝, `windowEnd`, `to` + 1 + N).
47. **퍼널·리텐션 트랜잭션은 중첩 반복 조인을 끈다(트랜잭션 안에서만).** `user_id` 인덱스가 없어 중첩 반복은 안쪽을 거듭 훑고, 범위 조인 조건 때문에 계획기는 통계와 상관없이 그것을 고를 수 있다(개발 DB 61초 vs 0.4초, 통계 없는 새 DB 39초 vs 31ms). ANALYZE로는 고쳐지지 않는다.

6단계에서 정한 것(AI 판단, 6.7, 설계 리뷰 반영):

48. **화면은 seat-booking 5단계와 같은 판이다(React 19.3, React Router 8.4, TanStack Query 5.104, Playwright 1.64).** 다만 `lib`는 ES2024(공유 스키마가 원본으로 들어옴), Vite는 루트에 있는 판에 맞춰 한 벌로 둔다. Vite가 `/api`를 넘겨 같은 origin이고, 요청과 응답을 모두 공유 zod 스키마로 검사한다.
49. **범위는 리포트·퍼널·저장한 리포트에 리텐션 표 하나다(그래프 없음).** 리텐션 API의 `null` 칸과 `meta.today` 계약은 쓰는 쪽이 있어야 검증된다. 설정을 URL에 담는 것은 미룬다(다시 열기는 저장한 리포트가 맡는다).
50. **그래프는 손으로 쓴 SVG 둘(시간 계열, 퍼널 막대)이고 표가 늘 함께 있다. x축은 묶음 순서로 같은 간격이다.** 확대가 필요 없고 툴팁은 십자선 하나(키보드 화살표로도)라 차트 라이브러리의 판을 하나 더 고정하지 않는다. 계열 색은 검증한 팔레트의 앞 다섯 칸이고 계열을 따라간다(다시 세어도 남은 계열은 같은 색).
51. **계열은 차원 값의 짝(키는 `JSON.stringify`), `null`은 "(없음)"이라는 값이다. 그래프는 상위 N개이고, 이벤트 수는 나머지를 "기타"로 더하고 사용자 수는 더하지 않는다(숨긴 값의 수만).** 순위는 이벤트 수가 있으면 그것, 없으면 묶음별 사용자 수의 합이다. 표는 긴 표이고 합계 행은 이벤트 수에만 둔다. 퍼널의 나눔 행은 겹치지 않아 더할 수 있다.
52. **저장한 리포트는 검사를 거친 설정을 저장하고, 목록은 `config: unknown`과 `valid`로 준다(옛 설정 하나가 목록을 500으로 만들지 않게). 열 때 다시 검사해 맞지 않으면 "설정이 바뀌어 열 수 없음"이다.** 이름은 유일(409), 기간은 저장한 날짜 그대로, 마지막 쓰기가 남는다.
53. **리포트·퍼널 응답에 `meta.asOf`(서버가 판단에 쓴 "지금")를 더한다.** 화면은 그것으로 아직 오지 않은 묶음을 그리지 않고 진행 중인 묶음을 표시하며, 퍼널의 열린 전환 기간을 알린다. 화면이 하는 날짜 계산은 시간대와 상관없는 달력 날짜 계산뿐이다(양식의 "최근 n일", 공유 스키마의 기간 길이 검사).
54. **차원 값과 이벤트 이름 목록은 새 API 없이 리포트 API(`total`, 차원 하나)로 채운다.** 손으로 친 값의 오타가 오류 없이 0이 되는 것을 막는다.
55. **E2E의 날짜는 `playwright.config.ts`가 한 번 정해(`E2E_DAY`) 준비와 테스트가 함께 쓴다.** 준비는 `NEW_DATABASE_OPTIONS`로 DB를 만들고 관리 작업과 같은 범위의 파티션을 만든다. 저장 이름은 재시도에 겹치지 않게 무작위 꼬리를 붙인다.

7단계에서 정한 것(AI 판단, 6.8):

56. **7단계 설계는 고칠 것을 정하지 않는다.** 찾는 절차와 증거표, 후보표, 판단 규칙을 먼저 적고, 고침은 기준선을 잰 뒤 고른다. 판단은 판단 회차(N = 4, 20분, 종류마다 표본 약 100개)로 하고, 기다린 시간(503까지 기다린 시간 포함, 풀 대기는 연결-초로 나눔)의 가장 큰 몫을 고친다. 머리 숫자는 고친 종류의 p95이고, 503이 5%를 넘으면 "한도 이상"으로 적는다. 알려진 느린 리포트(리텐션 31일 16초)도 측정이 가리킬 때만 고친다.
57. **서버 설정은 바꾸지 않고 앱 쪽 손잡이만 쓴다.** `SET LOCAL`(`work_mem`, `jit`, `enable_*`, 병렬 작업자 수), 인덱스·확장 통계, 질의 모양, 풀, 관리 작업이다. 비용 상수와 `synchronous_commit`은 `SET LOCAL`로도 바꾸지 않는다. `ANALYZE`·`VACUUM`은 소유자의 관리 작업에만 둔다(앱 role의 `ANALYZE`는 경고만 내고 건너뛴다). 앱 role에 `MAINTAIN`을 주지 않는다(10장 12를 지킨다). `pg_stat_statements`·`auto_explain` 대신 진단 회차의 `EXPLAIN (ANALYZE, BUFFERS)`와 `pg_stat_activity` 표본(병렬 작업자는 리더에 묶음), `pg_statio_*`·`pg_stat_database`·`pg_stat_wal` 차이로 찾는다.
58. **이 PC의 autovacuum이 사용자 표를 처리하지 않는 것은 사용자에게 넘긴다**(서버의 일, 원인을 보려면 슈퍼유저가 필요하다). 슈퍼유저 없이 지운 원인은 적어 둔다(통계 수집, wraparound, 다른 DB의 긴 VACUUM). "통계" 후보는 부모 표(어느 서버에서나 생기는 앱의 빈틈)와 오늘 파티션(이 PC 결함의 보정)으로 나누고, 보정이면 앱의 빈틈으로 주장하지 않는다.
59. **측정은 전용 템플릿에서 출발한다.** 개발 DB를 복제해 집계 작업을 끝까지 돌리고, 잎 표마다 `VACUUM (FREEZE, ANALYZE)`(부모는 고치기 전의 운영처럼 통계 없이) 뒤 표마다 `autovacuum_enabled = false`로 둔다(사용자가 서버를 고쳐도 회차 조건이 같게). 회차마다 `STRATEGY FILE_COPY`로 복제하고(측정 앞부분의 체크포인트를 피함), 관리 작업은 만들기와 부모 표의 통계(62에서 더함)만 돈다. `dirty_hours`가 비어 있지 않거나 워터마크가 데이터 끝보다 앞이면 회차를 거절한다.
60. **S2는 배경 수집(초당 2,000건, 전후 같은 절대값) 위의 리포트 묶음이다.** 몫은 이벤트 수 리포트를 자주, 퍼널·리텐션을 가끔 보는 대시보드를 따라 3·2·2·2·1·1·2로 두고, 같은 몫으로도 재서 고칠 곳의 순위가 바뀌는지 본다. 닫힌 모형(시작·순서·생각 시간을 씨앗으로 섞음)으로 판단하고, 기준선의 처리량으로 고정한 열린 모형으로 확인한다. 전후는 같은 날 번갈아 3회씩 재고 범위가 겹치지 않을 때만 개선을 주장한다. 리텐션은 오늘 파티션을 읽지 않는 무리(08-27~09-26)로 두고, 오늘을 읽는 리포트 7은 따로 읽는다.
61. **5,000만 건은 고침을 고른 뒤 전후를 번갈아 잰다**(별도 템플릿, 개발 DB는 그대로). 생성기의 사용자 수를 옵션으로 열어 사용자당 활동을 1,000만 건과 같게 한다(100만 명). 6.6의 "5,000만까지"를 조용히 빼지 않는다.
62. **첫 고침은 (사용자, 날) 무리 수의 어림이다: 관리 작업의 `ANALYZE ONLY events`와 (사용자, 한국 날) 식 확장 통계(마이그레이션 0004).** 둘 다 있어야 한다. 측정이 가리킨 곳과 찾은 길:
    - 처음 기준선 판단 회차(늦은 몫 1%)와 진단 회차(0%)에서 리텐션이 기다린 시간의 55%·70%였고, 리텐션 요청의 31%·34%가 503이었다(고치기 전 판단 회차 세 번은 57~60%, 37~39%). 표본은 대부분 DB CPU(대기 없음)였고 임시 파일 대기는 작았다. 부모 통계가 있는 복제에서 `work_mem` 64MB는 오히려 느렸다(9.7초 vs 그대로 8.1초).
    - 부모 통계가 없으면 (사용자, 날) 무리를 4만으로 어림해 병렬 해시 묶기를 고른다. 실제는 115만~237만이라 리더의 마지막 해시 묶기가 CPU로 문장 한도 30초를 넘길 때가 있다(한도 없이 40초 넘게). 부하 중 혼자일 때는 10초였고, 둘 이상이 겹치면 31~38%가 넘겼다(N 훑기). 같은 질의를 정렬 묶기로 하면 2.6초, 병렬을 끄면 6.9초다.
    - 복제에서 부모 통계를 지우고 분석하기를 번갈아 두 번씩 쟀다(진단 도구, 부하 없음, 3회 가운데값). 리텐션 30초 초과 → 7.7~7.8초, r4 1.75~1.80 → 1.38~1.39초였다. 나빠진 것도 있다: r5 2.65~2.92 → 3.05~3.26초(12~15%), r7 0.40~0.41 → 0.78~0.79초.
    - r7이 나빠진 까닭은 오늘 파티션에 통계가 없어서다(이 PC의 autovacuum 결함, 복제에서는 끔). 입력을 2,218행으로 어림해(실제 270만) 부분 묶기를 버린다. 그 파티션을 분석하면 0.37초로 돌아온다. 정상 서버에서는 autovacuum이 맡는 일이라 앱의 고침으로 주장하지 않는다.
    - 질의 모양(시작과 돌아옴을 한 번 훑기)도 쟀다. 4개 동시에서 가운데값이 14.7 → 8.9초였다. Gather가 하나라 작업자를 훑는 동안만 쥔다(지금 모양은 조인이 끝날 때까지 쥐어, 작업자가 모자라면 0명을 받는다). 그러나 부모 통계가 없으면 이 모양도 같은 해시 묶기로 무너진다. 그래서 어림이 먼저이고, 한 번 훑기는 다음 후보다.
    - **부모 통계만으로는 모자랐다(첫 "고친 뒤" 판단 회차).** 503은 0%가 되었지만 리텐션이 17초(p95 18초)였고, r4가 2.0 → 3.3초로 나빠졌다. 부하가 없어도 17초였다. 그 복제의 표본에서는 `occurred_at`이 "모두 다름"(n_distinct -1)이라, 계획기가 무리 수를 행 수(340만~670만)로 어림하고 병렬 부분 묶기를 버렸다. 앞의 7.7초는 수집이 같은 초에 넣은 행이 표본에 들어 n_distinct가 27만이 된 복제였다. 식(`(occurred_at at time zone …)::date`)에 통계가 없으면 열의 값을 쓰기 때문에, 같은 데이터에서도 표본에 따라 어림이 4만(통계 없음)과 행 수(통계 있음) 사이를 오간다. 실제 서버의 밀리초 시각이면 대개 -1 쪽이다.
    - 그래서 식 확장 통계를 더한다. 계획기의 어림이 (사용자, 날)의 n_distinct(1,000만 건에서 33만~39만)가 되어, 실제(115만~237만)보다 작지만 병렬 정렬 묶기를 고른다. 부하 없는 새 복제에서 리텐션 8.5초, r4 1.42초, r7 63ms였고, 부모를 다시 세 번 분석해도 계획이 그대로였다.
    - 식은 질의와 글자까지 같아야 맞고, 시간대는 상수다. 그래서 한국 시각(제품의 기본, S2 묶음)만 덮는다. 다른 시간대는 열의 어림으로 돌아간다(부모 통계만 있던 회차처럼 느린 계획이 될 수 있다. 그 회차는 503 없이 17초였다). 리텐션의 날 식과 리포트의 `date_trunc('day', …, 시간대)`가 달라 통계도 둘이다. 한 식으로 맞추는 것은 질의 모양을 바꾸는 일이라 이 고침에 넣지 않는다.
    - 첫 "고친 뒤" 회차는 고친 뒤의 표본으로 세지 않고 이 증거로 남긴다. 고치기 전 1회차는 그대로 쓴다.

8단계에서 정한 것(AI 판단, 6.9):

65. **seat-booking은 쓰기가 있는 세 업무 이벤트만 outbox로 보낸다**(`seats_held`, `order_created`, `payment_succeeded`). 목록·좌석 지도 조회는 보내지 않는다.
    - 조회는 쓰기가 없는 공개 경로라 outbox가 지킬 원자성이 없다. 세션을 읽지 않아 사용자도 없다.
    - 좌석 지도는 seat-booking 6단계가 잰 가장 뜨거운 경로다. 쓰기를 더하면 그 측정과 보장이 바뀐다.
    - 다른 안 둘을 견줬다. 하나는 공개 경로에서 세션을 골라 읽어 로그인한 조회만 넣는 것이다. 그러면 뜨거운 경로에 쓰기가 생기고, 다시 재야 한다. 다른 하나는 화면이 seat-booking의 수집 경로로 보내는 것이다. 그러면 SDK에 가까운 일이 생겨 2장의 범위 밖이다.
    - 그래서 seat-booking 데이터의 예매 퍼널은 세 단계다(1장 4를 고침). 생성기 데이터는 다섯 단계 그대로다.
66. **릴레이는 커서 없이 보내지 않은 행을 매번 고르고, 보내기와 적기를 나눈다.** 하나만 돌고(전용 연결의 advisory lock), HTTP 동안 행 잠금을 쥐지 않는다. 커서는 늦게 커밋된 낮은 id를 건너뛴다. 보내기와 적기를 나누면 "보낸 뒤 적기 전에 죽음"을 테스트에서 결정적으로 만들 수 있다(적기가 한 번 실패하는 가짜). 그것이 A8의 증명이다. 프로세스를 죽이는 리허설은 확인용이다. 네트워크 오류와 시간 초과는 503처럼 횟수 제한 없이 다시 보낸다(6.1의 "횟수를 정해"를 이 보내는 쪽에서는 500에만 쓴다, 설계 리뷰).
67. **outbox의 시각은 넣는 순간의 `date_trunc('milliseconds', clock_timestamp())`다.** 잠금을 기다린 트랜잭션도 이벤트 시각은 그 일을 한 때다. 보내는 글자는 Date의 `toISOString()`이다. `userId`는 seat-booking id의 문자열, `platform`은 `web`이고, 채널·캠페인은 없다(채널 필터를 건 퍼널은 0이 된다, 5단계 주의).
68. **연결 리허설은 새 DB들에서 한다.** 개발 DB는 생성기 데이터(같은 이벤트 이름)와 섞이고 측정 템플릿의 원본이다. seat-booking의 부하 데이터 DB는 outbox 없이 넣은 업무 행이 있다. 이 저장소의 E2E 준비·서버를 DB 이름, 고정 데이터 끄기, 쓰기 키를 받게 고쳐 쓴다. 셋의 수(선점·주문 행, 성공 결제 / outbox / 저장된 이벤트)가 같고, 보관·미전송이 0이며, 재전송은 릴레이 로그의 `duplicates`로만 보이면 A8 합격이다.
