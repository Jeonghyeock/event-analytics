# 이벤트 분석 대시보드 — 설계 문서

> 상태: 확정(2026-10-27, 사용자 "그대로해줘"). 단계마다 설계 PR에서 자세히 정하고, 결과는 PROGRESS.md에 쓴다.

## 1. 목표

마케터가 앱·웹의 행동 이벤트를 **어떻게 볼지 설정**해 그래프와 표로 보는 리포트 대시보드의 뒷단을 만든다. AB180에서 앞단(화면)을 맡았던 리포트 대시보드의 반대쪽이다. 다음을 지킨다.

1. 이벤트를 빠짐없이, 한 번만 저장한다. 같은 배치가 다시 오거나, 이벤트가 늦게 와도 그렇다.
2. 리포트 설정(지표 × 차원 × 필터 × 기간 × 단위)을 안전한 SQL로 바꾼다. 결과는 작은 데이터에서 손으로 센 값과 같다.
3. 수천만 건에서도 리포트가 빠르다. 시간 파티션, 집계 표(rollup), 실행 계획으로 보인다.
4. 퍼널(단계의 순서와 전환 기간)과 리텐션을 낸다. seat-booking의 행동 이벤트(목록 → 좌석 지도 → 선점 → 주문 → 결제)로 예매 퍼널을 그린다.
5. 위 넷을 테스트와 측정 **숫자**로 보인다. 숫자는 수집 처리량, 리포트 p95, 원본과 집계 표의 일치다.

**왜 PostgreSQL인가.** 분석에는 컬럼형 DB(ClickHouse 등)가 더 맞다는 것을 알고 PostgreSQL을 쓴다. 이 프로젝트의 목적은 PostgreSQL을 많은 데이터에서 운영하는 것이다(파티션, 집계, 파티션 가지치기, 튜닝). 그래서 주장도 "분석 DB를 골랐다"가 아니다. "PostgreSQL에서 파티션과 집계로 N천만 이벤트의 리포트를 X ms 안에 냈다"이다.

### 이력서 주장과 근거

| 쓸 수 있게 될 주장 | 근거(단계) |
|---|---|
| 재전송·중복 배치에도 이벤트를 한 번만 저장했다 | 수집 멱등 테스트(1) |
| 일 단위 파티션으로 리포트가 필요한 날만 읽게 했다. 보관 기간이 지난 파티션은 쓰기를 막지 않고 뗐다 | 실행 계획, 수집 중 리허설(2) |
| 화면의 리포트 설정을 허용 목록 기반의 매개변수 SQL로 바꿨다 | 쿼리 빌더 테스트(3) |
| 시간 집계 표로 리포트 p95를 X → Y ms로 줄였다. 원본과 같은 값임을 테스트로 보였다 | 측정표와 일치 테스트(4·7) |
| seat-booking의 행동 이벤트를 outbox로 받아 예매 퍼널을 그렸다 | 연결 테스트(8) |

## 2. 하지 않을 것

- **수집 SDK나 실제 앱은 없다.** 이벤트는 생성기와 seat-booking의 outbox가 보낸다.
- **어트리뷰션 계산은 없다.** 광고 클릭과 설치를 맞추는 일은 AB180 제품의 핵심이지만 범위를 넘는다. 채널·캠페인은 이벤트에 붙어 온다고 본다.
- **컬럼형 DB, Kafka, Redis, 스트림 처리는 없다.** PostgreSQL만으로 어디까지 되는지 잰다.
- **여러 고객(테넌트)은 없다.** 앱은 하나다.
- **로그인은 없다.** 로컬 도구다. 수집 API만 쓰기 키로 지킨다.
- **배포는 없다.** 로컬과 CI로 끝낸다(seat-booking과 같음).
- **화면은 최소로 한다.** 리포트 설정, 그래프와 표, 퍼널까지다. 대시보드를 꾸미거나 공유하는 기능은 없다.

## 3. 합격 기준

모든 기준은 앱 로그가 아니라 **DB를 직접 조회하는 SQL**로 확인한다.

| # | 상황 | 통과 조건 |
|---|---|---|
| A1 | 같은 배치를 다시 보내거나, 한 배치 안에 같은 `event_id`가 있음 | `event_id`마다 한 번만 저장한다. 응답에 받은 수·새로 넣은 수·중복 수가 있다 |
| A2 | 받을 수 있는 기간 밖의 이벤트(너무 늦거나 미래) | 이유와 함께 거절한다. 조용히 버리지 않는다 |
| A3 | 하루 범위의 리포트 | 실행 계획이 그날의 파티션만 읽는다 |
| A4 | 보관 기간이 지난 파티션 떼기 | 수집이 도는 중에도 쓰기 오류가 0이다. 대기 시간을 숫자로 남긴다 |
| A5 | 리포트 결과 | 작은 고정 데이터에서 손으로 센 값과 같다. 집계 표의 결과가 원본의 결과와 같다 |
| A6 | 늦게 온 이벤트 | 다음 집계 뒤 집계 표와 원본이 다시 같다 |
| A7 | 부하 중 리포트 | p95를 개선 전후로 잰다(숫자). 개선은 측정이 가리킨 병목이다 |
| A8 | seat-booking의 이벤트 | outbox로 빠짐없이 한 번 이상 오고, 저장은 한 번이다 |

## 4. 구조

```
[브라우저: React + Vite]
        │  REST(JSON)
[API 서버: Fastify] ── POST /ingest(쓰기 키) ── POST /reports/query ── 퍼널·리텐션
        │
[PostgreSQL 18] events(일 단위 파티션) · 시간 집계 표 · 다시 집계할 시간 목록
        ▲
[집계 작업: 명령 또는 서버 안 타이머]    [이벤트 생성기 CLI] → /ingest    [seat-booking outbox 릴레이] → /ingest
```

- seat-booking과 같은 PostgreSQL 서버에 DB를 따로 둔다(`event_analytics`). role도 따로 둔다(소유자, 앱).
- 저장소 구조는 seat-booking과 같다: `apps/api`, `apps/web`, `packages/shared`(zod), `load/`.

## 6. 핵심 결정 (단계마다 설계 PR에서 자세히)

### 6.1 수집 (1단계 설계)

**정확히 한 번은 약속하지 않는다.** 보내는 쪽은 응답을 못 받으면 같은 배치를 다시 보낸다("한 번 이상"). 받는 쪽은 `event_id`로 중복을 걸러 한 번만 저장한다(멱등 저장). 둘을 합치면 저장 결과는 정확히 한 번과 같다.

**요청.** `POST /ingest`, 헤더 `X-Write-Key`, 본문 `{ "events": [ … ] }`(1~1,000건, 본문 6MiB까지).

**이벤트 한 건**(`packages/shared`의 `IngestEvent`)

| 필드 | 규칙 | 열 |
|---|---|---|
| `eventId` | UUID(버전은 묻지 않는다. 보내는 쪽에는 v7을 권한다) | `event_id uuid` |
| `occurredAt` | ISO 8601, 오프셋 필수(`Z`, `+09:00`) | `occurred_at timestamptz`(밀리초) |
| `userId` | 1~128자(익명 id) | `user_id text` |
| `eventName` | 영문 소문자로 시작, 소문자·숫자·밑줄, 64자까지 | `event_name text` |
| `platform` | `ios` · `android` · `web` | `platform text` + CHECK |
| `country` | 대문자 두 글자(ISO 3166-1) 또는 없음 | `country text` |
| `channel`, `campaign` | 1~128자 또는 없음 | `channel`, `campaign text` |
| `properties` | 객체, 객체·배열 10단계까지, JSON으로 UTF-8 4KiB까지, 없으면 `{}` | `properties jsonb` |

- 모르는 필드가 있으면 그 이벤트를 거절한다. 조용히 버리면 보내는 쪽의 오타가 데이터 손실이 된다.
- **문자열은 NUL(`\u0000`)과 짝 없는 서로게이트를 거절한다.** `properties` 안의 키와 값도 그렇다. 확인한 것은 셋이다.
  - NUL은 text(22021)와 jsonb(22P05) 모두에서 배치 전체를 실패시킨다.
  - 짝 없는 서로게이트는 jsonb에서 배치 전체를 실패시킨다(22P02).
  - text에서는 node-postgres가 U+FFFD로 조용히 바꿔 저장한다.
- `properties`의 깊이 한도는 검사가 재귀하지 않게 하려는 것이다. 수천 단계로 중첩된 값은 재귀 검사의 스택을 넘쳐 배치 전체를 500으로 만들었다(리뷰가 재현함). 검사는 반복문으로 하고, 깊이를 먼저 막는다.
- `properties`의 정수는 JSON을 풀 때 JS 숫자가 되므로 2^53을 넘으면 정밀도를 잃는다. 큰 id는 문자열로 보낸다.
- `received_at`은 DB가 넣는다(트랜잭션 시각). 4단계에서 늦게 온 이벤트를 가리는 데 쓴다.
- **시각은 밀리초로 잘라 저장한다**(JS `Date`를 거친 ISO 글자). 보내는 쪽이 처음에는 마이크로초로, 재전송 때는 밀리초로 같은 시각을 쓰더라도 키가 같아진다. 분석에는 밀리초보다 작은 차이가 필요 없다. 반올림하지 않고 잘라서 자정 직전의 이벤트가 다음 날 파티션으로 넘어가지 않는다.

**검사**
- 키가 없거나 틀리면 401이다. 본문을 읽기 전에 본다.
- 봉투가 틀리면 400이다. 본문이 JSON 객체가 아니거나, `events`가 1~1,000개의 배열이 아닌 경우다.
- 본문 어딘가에 `__proto__` 키나 `constructor.prototype`이 있어도 400이다. Fastify가 JSON을 풀 때 거절한다(기본값 `onProtoPoisoning: 'error'`). 프로토타입 오염을 노린 본문이라 배치째 거절한다.
- 본문이 6MiB를 넘으면 413이다. 보통의 글자로 꽉 채운 이벤트는 한 건에 5.6KB쯤이라 1,000건이 들어간다. 이스케이프(`\uXXXX`)를 많이 쓰면 넘을 수 있다.
- **이벤트는 한 건씩 판단한다.** 틀린 이벤트는 이유와 함께 `rejected`에 담고, 나머지는 저장한다. 한 건 때문에 배치를 통째로 거절하면, 보내는 쪽은 그 배치를 끝없이 다시 보내거나 통째로 버려야 한다.
- 거절 이유는 셋이다.
  - `invalid`: 스키마. 어느 필드가 왜 틀렸는지 함께 준다. 같은 배치에 같은 `eventId`가 다른 시각으로 또 있으면 뒤의 것도 `invalid`다(합격 기준 A1: `event_id`마다 한 번).
  - `too_old`: 지금 − 7일보다 앞.
  - `too_far_in_future`: 지금 + 1시간보다 뒤.
  - 경계는 받는다. 받는 범위는 `지금 − 7일 ≤ occurred_at ≤ 지금 + 1시간`이다.
- "지금"은 DB의 트랜잭션 시각이다. 파티션 관리(2단계)와 같은 시계를 쓰고, 한 배치는 한 시각으로 판단한다.

**응답과 보내는 쪽이 할 일**

| 응답 | 뜻 | 보내는 쪽이 할 일 |
|---|---|---|
| 200 | `{ received, inserted, duplicates, rejected: [{ index, reason, message }] }`. `received = inserted + duplicates + rejected 수` | 배치를 지운다. `rejected`는 로그로 남긴다 |
| 400, 415 | 봉투가 틀림(배치 전체) | 다시 보내지 않는다. 따로 보관하고 알린다(보내는 쪽 버그) |
| 401 | 키가 없거나 틀림 | 배치를 지니고 보내기를 멈춘 뒤 알린다. 지우면 잃는다 |
| 413 | 본문이 6MiB를 넘음 | 배치를 반으로 나눠 다시 보낸다 |
| 503 `partition_missing`, `busy` | 다시 보내면 되는 실패. 아무것도 저장하지 않았다 | 같은 배치를 간격을 늘리며 다시 보낸다 |
| 500, 네트워크 오류, 시간 초과 | 알 수 없음. 저장됐을 수도 있다 | 같은 배치를 다시 보내되, 횟수를 정해 두고 넘으면 따로 보관한다 |

- `rejected`는 "이 요청이 저장하지 않은 것"이다. 재전송이 받을 기간의 경계를 넘으면, 첫 요청에서 저장된 이벤트가 둘째 요청에서는 `too_old`로 나올 수 있다.
- **알고 받아들이는 손실은 셋이다.**
  - `too_far_in_future`: 기기 시계가 앞선 경우다. 나중에 보내면 받아질 수도 있지만, 보내는 쪽은 200을 받으면 지운다.
  - 파티션 장애가 7일을 넘는 경우다. 그동안 다시 보낸 이벤트는 `too_old`가 된다.
  - 보내는 쪽이 재전송 때 시각을 새로 만드는 경우다. 아래의 `(event_id, occurred_at)` 한계다.
- 파티션이 없을 때 PostgreSQL이 내는 23514는 이렇게 가린다. 부모 표(`events`) 이름이 붙고 제약 이름이 없다(확인함). CHECK 위반은 제약 이름이 있고, 파티션 경계 위반은 파티션 이름이 붙는다. 이것만 503 `partition_missing`으로 바꾼다. 2단계 전이거나 관리 작업이 멈춘 경우다. 기본 파티션이 없으므로 이벤트가 엉뚱한 곳에 조용히 쌓이지 않는다.
- 503 `busy`로 바꾸는 것은 넷이다. 잠금 대기 초과(55P03), 교착(40P01), 문장 시간 초과(57014), 풀에서 연결을 얻지 못함이다. 같은 이벤트를 넣는 다른 트랜잭션을 기다리다 한도에 닿을 수 있다. 그 밖의 오류는 500이다.

**저장**
- 배치 하나를 문장 하나로 넣는다. `INSERT … SELECT FROM unnest($1::uuid[], …) WITH ORDINALITY ORDER BY event_id, occurred_at, 순번 ON CONFLICT (event_id, occurred_at) DO NOTHING`. 들어간 행 수가 `inserted`이고, 받은 것 중 나머지가 `duplicates`다. 문장이 거르는 것은 충돌뿐이라 나머지는 모두 중복이다.
- **키 순서로 넣는다.** 겹치는 두 배치가 서로 반대 순서로 넣으면, 서로 상대가 넣은 키를 기다리는 교착이 난다(리뷰가 재현함). 같은 순서로 넣으면 한쪽만 기다린다. 같은 키가 둘이면 배열에서 앞의 것이 남는다.
- 같은 문장 안의 중복도 DO NOTHING이 거른다(확인함: 같은 키 두 줄을 넣으면 1행).
- 같은 이벤트가 동시에 오면, 뒤의 것은 유일 인덱스에서 앞 트랜잭션이 끝나길 기다린다. 앞이 커밋하면 중복이 되고, 되돌리면 뒤의 것이 넣는다.
- 넣는 방법(`unnest`, 행마다 INSERT, `COPY`)의 비교는 7단계 측정에서 한다.
- 트랜잭션에는 문장 5초, 잠금 대기 3초의 한도를 둔다. 실행기의 1초보다 길다. 그래서 마이그레이션 뒤에 줄 선 수집이 먼저 포기하지 않는다(10장 12).

**쓰기 키**
- `INGEST_WRITE_KEY` 환경 변수다. 32자 이상이어야 하고, 없으면 서버가 뜨지 않는다.
- 비교는 두 값의 SHA-256을 `timingSafeEqual`로 한다. 길이가 달라도 같은 시간이 걸린다.
- 키는 하나다(10장 8). 키를 바꾸는 동안 둘을 함께 받는 기능은 없다. 그래서 바꾸는 동안 보내는 쪽은 401을 받는다. 401이면 배치를 지니고 멈추는 이유다.

**중복 제거: `(event_id, occurred_at)` 기본 키 vs 최근 id 표**(10장 5의 대안, 측정)

같은 조건으로 쟀다. 8일에 퍼진 200만 건을 배치 1,000건씩, 연결 하나로 `unnest`로 넣었다.

| | 초당 저장 | 더 쓰는 공간 | 거르는 범위 |
|---|---|---|---|
| A. 파티션 표의 기본 키 | 92,600건 | 없음(파티션마다 키 인덱스, 합 105MB) | 같은 id + 같은 시각(밀리초) |
| B. 파티션하지 않은 최근 id 표 | 83,200건 | id 표 184MB | 같은 id면 시각이 달라도 |

- B는 A보다 10% 느리다. 모든 쓰기가 파티션하지 않은 표 하나에 모이고, 이 표는 데이터와 함께 커진다. 오래된 id를 지우는 DELETE와 VACUUM도 따로 돌려야 한다. 이 표를 다시 파티션하면, 유일 키에 파티션 키가 들어가야 하는 같은 문제로 돌아온다.
- B가 더 거르는 것은 보내는 쪽이 재전송 때 시각을 새로 만드는 경우뿐이다. SDK는 보통 이벤트를 만들 때 시각을 찍어 큐에 넣는다. 그래서 A로 간다.
- A의 한계는 배치 사이에서 같은 id가 다른 시각으로 오면 두 행이 된다는 것이다. 같은 배치 안에서는 거절로 막고, 배치 사이의 경우는 테스트로 남긴다. 보내는 쪽 계약은 "재전송 때 처음과 같은 `occurredAt`을 보낸다"이다.

**파티션(1단계 범위)**
- 1단계에서 만드는 것은 둘이다. 부모 표와, 날짜 범위의 일 파티션을 만드는 명령(`db:partitions`, 소유자)이다.
- `CREATE TABLE … PARTITION OF`는 부모 표에 `AccessExclusiveLock`을 건다. 오래 도는 리포트 뒤에서 이 잠금을 기다리면, 그 뒤에 수집이 줄을 서 3초 한도에 닿는다. 그래서 명령은 잠금 대기를 1초로 묶고, 닿으면 실패한다(다시 돌리면 된다).
- 테스트 템플릿은 지금 기준 −8일 ~ +2일의 파티션을 만든다.
- 미리 만드는 주기, 보관 기간이 지난 파티션 떼기, `ATTACH`로 잠금을 줄이는 것은 2단계다.

**PR 순서**: 이 설계 → 이벤트 표·공유 스키마·파티션 명령 → `POST /ingest`(A1, A2) → 기록

### 6.2 파티션 (2단계 설계)

**나누는 기준은 `occurred_at`의 일 단위(UTC)로 그대로 둔다**(1단계에서 만든 대로).
- 리포트는 거의 늘 이벤트 시각으로 기간을 거른다. 그래서 기간에 든 날의 파티션만 읽는다(가지치기, 아래 A3).
- 반대안은 `received_at`(받은 시각)으로 나누는 것이다. 늦게 온 이벤트가 지난 파티션에 들어가는 문제는 없다. 대신 이벤트 시각으로 하루를 보는 리포트가 그날부터 7일 뒤까지 여덟 파티션을 읽어야 한다(받을 기간이 7일이라 그날의 이벤트가 7일 뒤까지 온다). 보관 기간도 이벤트 시각이 아니라 받은 시각으로 지워진다.
- 늦은 이벤트의 대가(지난 파티션과 집계를 다시 건드림)는 받을 기간(7일)으로 범위를 묶고, 4단계의 다시 집계로 다룬다.

**가지치기가 되는 조건과 안 되는 조건**(확인함, 10일치 파티션)

| 조건 | 읽는 파티션 |
|---|---|
| `occurred_at >= '…-25 00:00+00' and occurred_at < '…-26 00:00+00'` | 1개 |
| 한국 시각의 하루(`+09`로 같은 식) | 2개(한국의 하루는 UTC로 두 날에 걸친다) |
| 매개변수(`$1`, `$2`)로 같은 식, 일반 계획 | 1개(실행할 때 9개를 뺀다, `Subplans Removed: 9`) |
| `occurred_at::date = '…-25'` | 10개 전부 |
| `(occurred_at at time zone 'Asia/Seoul')::date = '…-25'` | 10개 전부 |

- 파티션 키에 함수나 형 변환을 씌우면 가지치기가 되지 않는다. 가지치기는 `키 연산자 식` 모양의 조건만 쓴다. 변하지 않는 함수여도 키를 감싸면 쓰지 못한다.
- 그래서 리포트(3단계)는 기간을 늘 `occurred_at >= $시작 and occurred_at < $끝`(시각, 반열린 구간)으로 거른다. 리포트 시간대의 날짜를 시각으로 바꾸는 일은 SQL 밖(또는 상수 식)에서 한다.
- **리포트는 이름 없는 문장(node-postgres의 기본)으로 보낸다.** 그러면 매번 값을 아는 계획(custom plan)이라 표 하나와 인덱스 하나만 잠근다. 이름 붙인 문장이나 plpgsql은 몇 번 뒤 일반 계획으로 바뀐다. 일반 계획은 실행할 때 가지를 쳐도 98개 파티션을 모두 잠근다(리뷰가 확인함).
- 합격 기준 A3("하루 범위의 리포트는 그날의 파티션만 읽는다")은 UTC 하루로 본다. 리포트 시간대가 Asia/Seoul이면 두 파티션이 맞다. 둘 다 테스트로 남긴다.

**기본 파티션은 계속 두지 않는다**(확인함).
- 기본 파티션이 있으면 새 파티션을 붙일 때마다 기본 파티션을 `AccessExclusiveLock`으로 잠그고 훑는다. 그동안 거기 들어갈 수집이 멈춘다.
- 기본 파티션에 그 날의 행이 이미 있으면 새 파티션을 만들 수 없다(23514). 행을 옮겨야 한다.
- 받을 기간 밖은 수집이 거절하므로 기본 파티션에 들어갈 정상 이벤트가 없다. 파티션이 없으면 503 `partition_missing`으로 드러나는 편이 낫다(10장 20).

**관리 작업**(`db:maintain`, 소유자, 여러 번 돌려도 같은 결과)

하는 일은 넷이고, 이 순서로 한다. 한 단계가 실패해도 다음 단계를 돌리고, 하나라도 실패했으면 끝에 실패(종료 코드 1)로 끝낸다. 수집에 가장 중요한 것(만들기)을 먼저 한다.
1. **앞으로 쓸 파티션 만들기.** 오늘(UTC) 기준 7일 전부터 7일 뒤까지 없는 날을 만든다. 1단계의 `CREATE TABLE … PARTITION OF`는 부모 표를 `AccessExclusiveLock`으로 잠근다. 그래서 바꾼다. 따로 표를 만들고(`LIKE events INCLUDING ALL`) `ATTACH PARTITION`으로 붙인다.
   - 부모에는 `ShareUpdateExclusiveLock`만 건다. 수집(INSERT)과 리포트(SELECT)는 막지 않는다(확인함: 열린 INSERT·전체 SELECT 트랜잭션이 있어도 3ms).
   - 만들기와 붙이기는 한 트랜잭션이다. 붙이다 실패하면(ANALYZE 뒤에서 잠금 대기 초과 등) 따로 만든 표도 남지 않는다.
   - 있는지는 이름이 아니라 `pg_inherits`(붙어 있는지)로 본다. 그 날 이름의 표가 붙지 않은 채 있으면(끊긴 작업이 남긴 것) 붙인다. 붙일 때 경계 밖 행이 있는지 PostgreSQL이 훑어 본다.
   - 기본 키 인덱스는 따로 만든 표의 것이 부모 인덱스에 붙는다(다시 만들지 않음, 확인함). 권한은 소유자의 기본 권한으로 붙는다(0단계 테스트).
2. **중간에 끊긴 떼기 마무리.** 떼기가 중간에 끊기면 파티션이 "떼는 중"(`pg_inherits.inhdetachpending`)으로 남는다. 취소, 프로세스 종료, 재부팅, 아래의 시간 한도가 그런 경우다. 떼는 중인 파티션이 있으면 다른 파티션은 뗄 수 없다(55000, 확인함). 그래서 `DETACH PARTITION … FINALIZE`로 먼저 마무리한다.
   - FINALIZE는 DB의 더 오래된 스냅샷이 모두 끝나길 기다린다. 그래서 잠금 대기 1초로 묶는다. 묶지 않으면 기다리는 동안 부모의 `ShareUpdateExclusiveLock`을 쥐어 다음 실행의 ATTACH를 막는다(리뷰가 확인함).
3. **보관 기간이 지난 파티션 떼기.** 오늘 − 90일보다 앞선 날을 `DETACH PARTITION … CONCURRENTLY`로 뗀 뒤 `DROP TABLE`로 지운다. 떼는 중인 것이 남아 있으면 이 단계를 건너뛴다(다음 실행이 마무리부터 한다).
   - CONCURRENTLY는 부모 표에 잠금을 쥔 트랜잭션이 모두 끝나길 기다린다(`virtualxid`). 그 파티션을 읽지 않았어도 기다린다(리뷰가 확인함: 오늘만 읽고 쉬는 트랜잭션도). 그동안 수집과 ATTACH는 막히지 않는다(확인함: 기다리는 중 INSERT 6ms).
   - 잠금 줄은 만들지 않으므로 잠금 대기 한도는 끈다. 대신 문장 시간 한도(5분)를 둔다. 한도가 없으면 열린 채 잊힌 트랜잭션 앞에서 작업이 끝나지 않는다. 그러면 다음 날의 예약 실행이 건너뛰어져(Windows 작업 스케줄러의 기본값) 만들기까지 멈춘다. 한도에 닿으면 파티션은 떼는 중으로 남고, 다음 실행이 마무리한다.
   - 떼고 난 표를 지우는 `DROP`은 그 표만 잠근다.
4. **남은 표 치우기.** 떼었지만 지우지 못한 표(`DROP` 직전에 끊긴 것)를 지운다. 이름이 `events_pYYYYMMDD`이고 붙어 있지 않으며 보관 기간이 지난 표다.

- **겹쳐 돌지 않는다.** 시작할 때 advisory lock을 잡아 보고(`pg_try_advisory_lock`), 다른 실행이 돌고 있으면 바로 실패한다.
- **"오늘"은 DB 시각의 UTC 날짜다**(10장 16). 서버의 경고도 같다.
- **소유자 확인.** 마이그레이션 실행기처럼 DB 소유자(슈퍼유저 아님)로 돌리는지 먼저 본다. 슈퍼유저가 만든 파티션에는 앱 role의 권한이 붙지 않는다.
- 지운 파티션은 되살리지 않는다. 지우기 전에 보관(덤프)하는 일은 범위 밖이다(seat-booking 7단계의 백업 리허설이 방법을 보였다).
- **누가 언제 돌리나.** 하루 한 번 OS의 예약 작업(cron, Windows 작업 스케줄러)으로 돌린다. 앞으로 7일치를 미리 만들어 두므로, 관리 작업이 멈춰도 7일 동안은 수집이 503이 되지 않는다.
- API 서버가 관리 작업을 대신 돌리지 않는다. 서버는 앱 role(DML만)로 접속하고, 표를 만들고 떼는 권한은 소유자에게만 둔다(10장 12). 대신 서버는 뜰 때와 한 시간마다 받을 기간(과거 7일)부터 앞으로 3일까지 붙어 있지 않은 날이 있는지 보고, 있으면 경고 로그를 남긴다. 관리 작업이 7일을 미리 만드므로, 이 경고가 뜨면 4일 넘게 돌지 않은 것이다.
- `db:partitions`(1단계)는 `db:maintain`으로 바꾼다.

**이벤트 생성기**(`load:generate`)
- 씨앗(seed)으로 정해지는 의사 난수를 쓴다. 같은 씨앗과 같은 끝 날(`--end-day`)이면 같은 이벤트가 나온다. `event_id`도 씨앗에서 만들므로, 다시 넣으면 모두 중복이 된다(재실행이 안전하다). 시각을 "지금"에서 재면 다른 날 다시 돌릴 때 키가 달라 두 배가 되므로, 끝 날을 고정해 잰다.
- 분포(DESIGN 6.6)
  - 캠페인은 소수가 대부분을 차지한다(zipf).
  - 시간대별로 많고 적다(밤에 적음).
  - 사용자마다 이벤트 수가 다르다(소수의 헤비 사용자).
  - 행동은 seat-booking의 예매 흐름을 따른다(목록 → 좌석 지도 → 선점 → 주문 → 결제, 단계마다 이탈). 5단계 퍼널에 쓸 데이터다.
- 보내는 곳은 둘이다.
  - 수집 API: 받을 기간(7일) 안만 보낼 수 있다. 떼기 리허설(A4)과 7단계 측정이 이 생성기로 지금 근처의 이벤트를 만들어 보낸다.
  - DB(`load:generate`): 소유자로 바로 넣는다. 지난 90일을 채우는 데 쓴다(받을 기간 밖). 필요한 파티션을 만들고, 수집과 같은 문장(`unnest` + `ON CONFLICT`)으로 넣는다. 보관 기간보다 앞선 날은 넣지 않는다(관리 작업이 지울 날을 다시 만들게 되므로).
- 기본 데이터는 1,000만 건이다(10장 6). 크기와 넣는 시간은 2단계 기록에 숫자로 남긴다.

**떼기 리허설(합격 기준 A4)**
- 생성기가 수집으로 일정한 속도(초당 2,000건, 배치 200건)를 보내는 동안, 오래 도는 리포트(20초)를 하나 걸어 두고 관리 작업 전체(`maintain`: 만들기, 마무리, 떼기, 치우기)로 90일 지난 파티션을 뗀다.
- 보내는 쪽은 열린 모형이다. 앞 요청이 끝나길 기다리지 않고 정해진 간격으로 보낸다. 기다리면 막힌 동안 보내는 양이 줄어 지연이 가려진다.
- 잰다.
  - 수집 응답 코드별 수(5xx 0이어야 함)
  - 수집 지연(p50, p99, 최대)
  - 떼기가 기다린 시간
- 비교는 둘이다.
  - 기준선: 같은 장면에서 아무것도 떼지 않는다.
  - 일반 `DETACH`: 잠금 대기 한도 없이(`lock_timeout = 0`) 돌린다. 이것은 부모를 `AccessExclusiveLock`으로 잠그려고 리포트 뒤에 줄을 서고, 수집은 그 뒤에 줄을 선다. 한도를 1초로 두면 떼기가 먼저 포기해 수집이 거의 다치지 않는다(리뷰가 확인함). 그래서 한도를 적어 둔다.
- 503은 원인별로 센다. 원인은 잠금 대기 초과와 풀 연결 대기 초과다.
- 리허설 DB는 개발 DB를 복제해 만들고 끝나면 지운다(seat-booking 7단계와 같은 방식).

**PR 순서**: 이 설계 → 관리 작업(ATTACH로 만들기, CONCURRENTLY로 떼기, 마무리, 서버의 남은 날 경고) → 가지치기 테스트(A3) → 생성기 → 떼기 리허설(A4) → 기록

### 6.3 리포트 설정 → SQL (3단계 설계)

**요청.** `POST /reports/query`, 본문은 리포트 설정(`packages/shared`의 `ReportQuery`)이다. 로그인은 없다(10장 8). 화면(6단계)과 같은 스키마를 쓴다.

| 필드 | 규칙 |
|---|---|
| `metrics` | `events`(이벤트 수), `users`(고유 사용자 수) 가운데 1~2개 |
| `dimensions` | `event_name` · `platform` · `country` · `channel` · `campaign` 가운데 0~2개, 겹치지 않게 |
| `filters` | `[{ dimension, values }]`. 차원은 위 목록이고 같은 차원은 한 번만, 값은 1~100개. 값 목록 안에 있으면 남긴다(`IN`). `null`을 넣으면 값이 없는 것(예: 캠페인 없음)도 남긴다. 여러 필터는 모두 맞아야 한다(AND) |
| `from`, `to` | 리포트 시간대의 날짜(`YYYY-MM-DD`, 달력에 있는 날), 둘 다 포함, 90일까지 |
| `granularity` | `hour` · `day` · `week` · `total` |
| `timezone` | 허용 목록의 IANA 이름(대소문자까지 그대로). 기본 `Asia/Seoul` |

- 모르는 필드와 목록 밖의 값, `from > to`는 400이다(수집과 같다). 시간대를 허용 목록으로 두는 것은 PostgreSQL이 `asia/seoul`이나 부호가 뒤집힌 `UTC+5`도 받기 때문이다(리뷰가 확인함).
- 시간대 허용 목록은 `UTC`, `Asia/Seoul`, `Asia/Tokyo`, `Asia/Singapore`, `Asia/Kolkata`(+05:30), `Europe/London`, `America/New_York`, `America/Los_Angeles`다. 일광 절약 시간이 있는 곳과 30분 단위 오프셋이 하나씩 들어 있다. 시간 집계 표(4단계)가 어느 시간대를 그대로 받을지는 4단계에서 정한다.
- `week`는 월요일에 시작하는 주다(PostgreSQL `date_trunc`).
- **묶음은 기간 끝에서 늘리지 않는다.** 기간이 수요일에 시작하면 첫 주 묶음은 그 주 월요일의 순간이지만, 안에는 수요일부터의 이벤트만 있다. 그래서 `bucket`이 `from`보다 앞설 수 있다. 이런 묶음은 응답의 묶음 목록에 `partial: true`로 표시한다(일부만 찬 주가 줄어든 것처럼 보이지 않게).
- `total`은 기간 전체를 한 묶음으로 센다. `bucket`은 `from`의 시작 순간, `label`은 `from ~ to`다.

**보관 기간과 늦은 이벤트**
- 기간의 시작이 보관 기간(90일, UTC 날짜 기준)보다 앞서면 422 `out_of_retention`이다. 조용히 0을 돌려주면 "그때는 이벤트가 없었다"로 읽힌다. 시작 날이 일부만 남은 경우(한국 시각의 하루가 지운 UTC 날에 걸친 경우)도 거절한다.
- 기간의 끝이 지금으로부터 7일 안이면 `meta.provisional: true`다. 받을 기간이 7일이라 늦은 이벤트가 더 올 수 있다.

**SQL을 만드는 규칙**(주입 막기)
- 식별자(열 이름)는 허용 목록의 차원을 코드의 상수 표로 바꾼 것만 쓴다. 설정의 글자를 SQL에 넣지 않는다.
- 값(날짜, 시간대, 필터 값)은 모두 매개변수(`$n`)로 넘긴다. 필터는 `col = any($n::text[])`이고, `null`을 골랐으면 `or col is null`을 더한다.
- 리포트는 이름 없는 문장으로 보낸다(10장 26). 그러면 매번 값을 아는 계획이라 계획할 때 가지를 친다.
- **풀에서 연결 하나를 빌려 그 위에서** 트랜잭션을 연다. 읽기 전용이고, 트랜잭션 안에서만 걸리는 설정(`set_config(…, true)`)으로 문장 30초, 잠금 대기 3초(수집과 같다)를 건다. `pool.query`로 `set local`을 보내면 트랜잭션 밖이라 아무것도 걸리지 않는다(리뷰가 확인함).
  - 잠금 대기 한도가 없으면, 일반 `DETACH` 같은 `AccessExclusiveLock` 요청 뒤에 리포트가 줄을 선다(A4 리허설).
- **리포트는 수집과 다른 연결 풀(4개)을 쓴다.** 리포트는 30초까지 연결을 쥘 수 있다. 수집과 풀을 함께 쓰면 느린 리포트 몇 개가 수집의 연결을 빼앗아 수집이 503이 된다.
- **요청한 지표만 센다.** `users`를 고르지 않으면 `count(distinct user_id)`를 하지 않는다. 원본 리포트 시간의 대부분이 이것이다.

**기간과 시간대**
- 기간은 `occurred_at >= ($from::date::timestamp at time zone $tz) and occurred_at < (($to::date + 1)::timestamp at time zone $tz)`로 거른다. 리포트 시간대의 하루가 UTC의 어느 구간인지 PostgreSQL이 바꾼다. 일광 절약 시간이 바뀌는 날은 23시간이나 25시간이 된다.
- `timezone(text, timestamp)`는 변하지 않는 함수(immutable)라, 매개변수가 든 이 식도 계획할 때 상수가 되어 가지를 친다(확인함: 서울·뉴욕·콜카타의 하루 → 파티션 2개, UTC 하루 → 1개).
- 시간 묶음은 `date_trunc($unit, occurred_at, $tz)`다(3인자, PostgreSQL 14부터, immutable). 시간대의 자정·정시로 자르고 일광 절약 시간을 따른다.

**응답**

```json
{
  "rows": [{ "bucket": "2026-10-26T15:00:00.000Z", "label": "2026-10-27", "dimensions": { "platform": "ios" }, "events": 120, "users": 37 }],
  "meta": {
    "timezone": "Asia/Seoul", "from": "…", "to": "…", "rowCount": 1, "source": "raw", "provisional": false,
    "buckets": [{ "bucket": "2026-10-26T15:00:00.000Z", "label": "2026-10-27", "utcOffset": "+09:00", "partial": false }]
  }
}
```

- `label`은 리포트 시간대의 벽시계 글자다. `hour`는 `YYYY-MM-DD HH:MM`, `day`·`week`는 `YYYY-MM-DD`, `total`은 `from ~ to`다.
- `meta.buckets`는 기간의 모든 묶음이다(이벤트가 없는 묶음도). 4인자 `generate_series(…, $tz)`로 만든다. 행에는 이벤트가 있는 묶음만 있으므로, 화면은 이 목록으로 빈 묶음을 0으로 채운다(그래프가 빈 시간을 건너뛰어 잇지 않게). 묶음마다 UTC 오프셋이 있어, 일광 절약 시간이 끝나는 날의 두 `01:00`(`-04:00`, `-05:00`)을 가린다.
- 차원 값이 없으면(국가·채널·캠페인이 비어 있음) `null`로 묶는다.
- 행은 묶음 → 차원 순으로 정렬한다. 차원 값의 정렬은 builtin `C.UTF-8`의 코드 포인트 순서이고, `null`은 맨 뒤다(10장 13).
- 행에는 요청한 지표만 있다.
- **`users`는 행끼리 더할 수 없다.** 같은 사람이 여러 묶음·여러 차원 값에 나온다(7일 일별 × 플랫폼의 합 30만 vs 실제 13만, 리뷰가 잼). 기간 전체의 사용자 수는 `total`, 차원 없이 묻는다.
- 행이 20,000개를 넘으면(`LIMIT 20001`로 본다) 422 `too_many_rows`다. 잘라서 주지 않는다(잘린 표를 전체로 오해하지 않게). 이 한도로 92일 시간별 × 플랫폼(6,624행)이나 30일 일별 × 캠페인(6,030행)은 들어간다. "상위 N개 + 기타"는 화면(6단계)에서 정한다.
- 문장 한도에 닿으면 503 `report_timeout`, 잠금 대기·교착·연결 대기는 503 `busy`다.
- `source`는 3단계에서 늘 `raw`(원본)다. 4단계에서 `rollup`이 생긴다.

**고유 사용자 수**
- 원본에서 `count(distinct user_id)`로 정확히 센다. 묶음마다 따로 센다. 하루의 사용자 수는 그 날 시간별 사용자 수의 합이 아니다(6.4).

**합격 기준 A5(손으로 센 값)**
- 작은 고정 데이터(이벤트 수십 건)를 테스트 파일만 쓰는 새 DB에 넣고, 손으로 센 값과 견준다. 경우는 이렇다.
  - 한국 시각 자정을 사이에 둔 이벤트(UTC로는 같은 날)
  - 같은 사용자가 여러 시간에 나오는 경우(시간별 사용자 합 ≠ 하루 사용자)
  - 뉴욕의 일광 절약 시간이 끝나는 날(2026-11-01). 하루가 25시간이라 시간 묶음이 25개이고, 벽시계 `01:00` 묶음이 둘이다(`bucket`과 `utcOffset`이 다름)
  - 뉴욕의 일광 절약 시간이 시작하는 날(2027-03-14). 시간 묶음이 23개이고 `02:00`이 없다
  - 수요일에 시작하는 기간의 주 묶음(일부만 찬 첫 주, `partial`)
  - 차원 값이 없는 경우와 그것을 고르는 필터, 필터 여러 개, 30분 단위 시간대
- 주입 시험: 허용 목록 밖의 차원 이름과 시간대는 400이다. SQL 글자가 든 필터 값은 그저 값이다(결과 0행, 표는 그대로).
- 리포트 SQL 자체에 대한 가지치기 시험: 한국 시각 하루 리포트가 파티션 2개만 읽는다.
- 보관 기간과 "지금"은 테스트가 정한 시각으로 판단한다(실제 날짜가 지나도 테스트가 깨지지 않게).

**원본에서 세는 시간**(1,000만 건, 같은 PC, 탐색에서 한 번)

| 리포트 | 시간 |
|---|---|
| 30일 일별, 이벤트 수 + 고유 사용자 | 2.6초 |
| 90일 캠페인별(상위 20), 이벤트 수 + 고유 사용자 | 15.3초 |

- 3단계 기록에서 정한 리포트 몇 개를 API가 만드는 SQL 그대로(`LIMIT` 포함) 세 번씩 잰다(가운데 값, 첫 회차는 따로). 그 실행 계획(`EXPLAIN (ANALYZE, BUFFERS)`)도 남긴다.
- 리뷰가 실행 계획에서 본 것은 둘이다. 이것을 기록에서 확인한다.
  - 계획기는 `date_trunc(…, $tz)`로 묶은 무리의 수를 행 수만큼으로 어림한다(333만 vs 실제 90). 그래서 모든 행을 디스크에서 정렬한다.
  - 부분 집계는 `count(distinct)`가 없어도 쓰이지 않는다. `LIMIT`이 붙으면 병렬 계획으로 바뀐다.
- 이것이 4단계(집계 표)와 7단계(측정)의 "전" 숫자다.

**PR 순서**: 이 설계 → 공유 스키마와 SQL 만들기(순수 함수, 단위 테스트) → `POST /reports/query`(A5, 주입, 가지치기) → 기록(원본 시간)

### 6.4 집계
- 이벤트 수는 시간 집계 표로 미리 센다. 증분으로 센다: 늦은 이벤트가 들어오면 그 시간을 `dirty_hours`에 적고, 그 시간만 다시 센다.
- **고유 사용자 수는 시간끼리 더할 수 없다.** 같은 사람이 두 시간에 나오면 두 번 세어진다. 그래서 다음 중 하나를 4단계에서 측정으로 고른다.
  - 원본에서 정확히 센다(인덱스가 필요하고 느림).
  - 사용자×일 사실 표를 둔다(일 안에서만 더할 수 있음).
  - HLL 같은 근사는 확장(`hll`)이 없어 쓰지 않는다(확인함).
- 리포트는 집계 표로 답할 수 있으면 집계 표를, 아니면 원본을 쓴다. 두 경로의 결과가 같은지 테스트한다.

### 6.5 퍼널과 리텐션
- 퍼널: 사용자마다 단계가 순서대로, 정한 기간 안에 일어났는지 본다. 원본에서 기간을 좁혀 센다.
- 리텐션: 첫 이벤트 날로 묶은 무리가 며칠 뒤에도 돌아오는지 센다.
- 둘 다 작은 고정 데이터에서 손으로 센 값과 견준다.

### 6.6 측정
- 생성기의 분포
  - 캠페인은 소수가 대부분을 차지한다(zipf).
  - 시간대별로 많고 적다.
  - 사용자마다 이벤트 수가 다르다.
- 기본 데이터는 1,000만 건(약 3GB 예상)이다. 측정은 5,000만 건까지 한다. 디스크 여유는 547GB다(확인함).

## 9. 위험

- **생성 데이터가 실제와 다르다.** 분포를 문서로 남기고, 숫자는 같은 PC의 전후 비교로만 쓴다.
- **범위가 크다.** 화면에 시간을 쓰면 뒷단이 얕아진다. 화면은 6단계 하나로 묶고 최소로 한다.
- **고유 사용자 수의 비용.** 정확한 값이 느리면 근사 없이 어디까지 되는지를 숫자로 남긴다.

## 10. 정한 것

1~11은 권장안을 사용자가 그대로 확정했다(2026-10-27, "그대로해줘. 너가 다 해줘. 내가 검토할게").

1. 이름은 `event-analytics`다. GitHub 공개 저장소는 사용자가 권한을 준 뒤 만들었다.
2. 스택은 seat-booking과 같다.
   - 서버: TypeScript ~6.0.3, Fastify 5, Drizzle 0.45, PostgreSQL 18(같은 서버, DB `event_analytics`)
   - 화면: React 19 + Vite + TanStack Query
   - 공통: `packages/shared` zod, Vitest, k6
   - 차트 라이브러리는 6단계에서 정한다.
3. PostgreSQL만 쓴다. 컬럼형 DB는 쓰지 않는다(1장 이유).
4. 파티션 키는 `occurred_at`이고 일 단위(UTC)다. 받을 기간은 과거 7일, 미래 1시간이다. 보관은 90일이다. `received_at` 파티션과의 비교는 2단계에서 한다.
5. 중복 제거는 유일 키 `(event_id, occurred_at)`로 한다.
   - 재전송은 같은 `occurred_at`을 싣는다고 보고, 테스트로 확인한다.
   - 보내는 쪽이 시각을 다시 만들면 받는 쪽은 막지 못한다고 적는다.
   - 대안(파티션하지 않은 최근 id 표)은 1단계 설계에서 견준다.
6. 데이터 규모는 기본 1,000만 건, 측정은 5,000만 건까지다.
7. 확장은 쓰지 않는다(`hll`·`pg_partman`·`pg_cron` 없음, `pg_stat_statements`는 서비스를 다시 띄워야 켜짐). 파티션 관리와 고유 사용자 수는 직접 한다.
8. 로그인은 없다. 수집은 쓰기 키로 지킨다. 앱은 하나다.
9. 배포는 없다.
10. 진행은 seat-booking과 같다: 단계마다 설계 PR → 짧은 PR → 리뷰 서브에이전트 → CI → 머지. 0~8단계 모두 묻지 않고 진행하고, 끝난 뒤 사용자가 한꺼번에 검토한다(사용자 결정). 단계 안의 판단은 이 장에 번호를 이어 적는다.
11. 8단계(seat-booking 연결)는 seat-booking 저장소에도 PR을 낸다.

0단계에서 정한 것(AI 판단):

12. **seat-booking 7단계의 것을 가져온다.** 가져오는 것은 셋이다.
    - 마이그레이션 실행기와 그 테스트. 마이그레이션마다 트랜잭션, 잠금 대기 1초와 다시 하기, `-- 트랜잭션 밖`, INVALID 인덱스 확인, drizzle 기록 호환이 들어 있다.
    - role 나누기. 소유자 `event_analytics`, 앱 `event_analytics_app`(DML만)으로 나누고, 권한은 첫 마이그레이션이 준다.
    - 템플릿을 복제하는 테스트 DB.

    다시 만들지 않는 이유가 있다. 이 셋은 seat-booking에서 리뷰와 변이 시험으로 고친 결과다. 다시 만들면 같은 버그(CONCURRENTLY와 advisory lock의 교착, 연결이 끊길 때 프로세스가 죽음)를 다시 밟는다. 이 프로젝트의 2단계는 파티션을 만들고 떼느라 DDL이 잦아, 잠금 대기를 묶는 실행기가 처음부터 필요하다.

    실행기(`migrate.ts`)는 주석 말고 그대로다. 나머지에서 바꾼 것은 이렇다.
    - 테스트 준비의 advisory lock 번호. postgres DB에서 잡으므로 seat-booking과 같으면 두 저장소의 테스트가 서로 기다린다.
    - 새 DB를 만드는 옵션(13)과 앱 풀의 UTC 고정(14).
    - 첫 마이그레이션은 이미 있는 표에 권한을 주지 않는다(표가 없다). 앞으로 만들 표와 파티션에 붙는 기본 권한만 둔다.
    - 테스트에서 seat-booking의 표를 쓰던 것은 시험용 표와 만든 폴더로 바꿨다.
    - 리뷰에서 나와 더한 것: 풀의 쉬는 연결이 끊길 때 프로세스가 죽지 않게 `error`를 듣는다(seat-booking에도 같은 빈틈이 있다). 서버의 연결 대기는 5초로 묶는다.
13. **DB는 UTF8, builtin `C.UTF-8` 정렬로 만든다**(`LOCALE_PROVIDER builtin`, PostgreSQL 17부터). 정렬을 OS에 맡기면 로컬과 CI가 다르다. 로컬은 Windows의 `Korean_Korea.949`, CI는 Linux의 `en_US.utf8`이다. 이 프로젝트는 차원 값(국가·채널·캠페인)으로 묶고 정렬하므로, 같은 쿼리의 행 순서가 두 곳에서 달라진다.
    - builtin `C.UTF-8`은 코드 포인트 순서로 정렬하고, 대소문자는 유니코드로 바꾼다. OS 라이브러리가 바뀌어도 인덱스 순서가 그대로다.
    - 사람이 읽기 좋은 정렬(가나다, 대소문자 무시)은 필요한 곳에서 `COLLATE`로 따로 쓴다.
    - 새로 만드는 DB(개발, 테스트 템플릿, CI)는 모두 같은 옵션을 쓴다(`NEW_DATABASE_OPTIONS`).
14. **앱 연결의 세션 시간대를 UTC로 고정한다**(`createPool`이 `-c TimeZone=UTC`를 붙임. 주소의 `?options=`와 호출한 쪽의 options 뒤에 붙여 늘 이긴다). 서버 기본값은 로컬이 Asia/Seoul, CI가 UTC다. 그래서 시간대 없는 시각 글자나 `timestamptz → date` 변환이 어디서 도느냐에 따라 다른 날이 된다. 파티션 경계와 시간 집계는 UTC 기준이다(10장 4).
    - 리포트의 시간대(기본 Asia/Seoul)는 세션 설정이 아니라 쿼리의 인자로 준다(`AT TIME ZONE $tz`, 3인자 `date_trunc`).
    - 세션 고정은 실수를 줄이는 장치일 뿐이다. 코드는 거기에 기대지 않고 시각 글자에 오프셋을 붙인다(`'2026-10-27 00:00+00'`). 소유자 연결(마이그레이션, 파티션 만들기)은 이 풀을 쓰지 않기 때문이다.

1단계에서 정한 것(AI 판단, 6.1):

15. **이벤트는 한 건씩 판단한다.** 틀린 것만 이유(`invalid`, `too_old`, `too_far_in_future`)와 함께 거절하고 나머지는 저장한다. 400은 봉투가 틀릴 때만이다.
16. **받을 기간의 "지금"은 DB의 트랜잭션 시각이다.** 앱 서버의 시계를 쓰지 않는다. 파티션 관리와 같은 시계를 쓰기 위해서다.
17. **시각은 밀리초로 잘라 저장한다.** 처음에는 글자 그대로(마이크로초) 넘기려 했다. 리뷰에서 반대가 낫다는 것이 나왔다. 보내는 쪽이 재전송 때 시각을 밀리초로 다시 쓰면 글자 그대로는 키가 달라지지만, 자르면 같아진다. 시각을 `Date`로 바꿔 UTC 글자로 넘기므로, PostgreSQL은 보내는 쪽의 오프셋을 보지 않는다.
18. **문자열의 NUL과 짝 없는 서로게이트는 그 이벤트만 거절한다.** 그대로 넘기면 PostgreSQL이 배치 전체를 실패시키거나(NUL, jsonb의 서로게이트), 조용히 U+FFFD로 바꾼다(text의 서로게이트).
19. **중복 제거는 `(event_id, occurred_at)` 기본 키로 한다**(측정으로 10장 5 확인). 최근 id 표는 10% 느리고 표 하나가 따로 커진다. 그 표가 더 거르는 경우(재전송 때 시각을 새로 만듦)는 드물다.
20. **파티션이 없으면 503 `partition_missing`이다.** 기본 파티션은 두지 않는다(6.2). 23514 가운데 표 이름이 `events`(부모)이고 제약 이름이 없는 것만 이것으로 본다. 잠금 대기 초과·교착·문장 시간 초과는 503 `busy`다. 둘 다 다시 보내면 되는 오류다.
21. **쓰기 키는 하나이고, 본문을 읽기 전에 SHA-256 + `timingSafeEqual`로 견준다.**
22. **응답마다 보내는 쪽이 할 일을 정해 둔다**(6.1 표). 401은 지니고 멈춤, 413은 나눠 보냄, 400은 따로 보관, 503은 다시 보냄, 500은 횟수를 정해 다시 보냄. `rejected`는 "이 요청이 저장하지 않은 것"이다.
23. **배치는 키 순서로 넣는다.** 겹치는 배치가 반대 순서로 넣으면 교착(40P01)이 난다. 같은 배치에 같은 `eventId`가 다른 시각으로 있으면 뒤의 것을 거절한다.
24. **`db:partitions`는 잠금 대기를 1초로 묶는다.** `CREATE TABLE … PARTITION OF`가 부모 표를 통째로 잠그므로, 기다리는 동안 수집이 그 뒤에 줄을 서지 않게 한다. 2단계에서 `ATTACH`로 바꾼다.

2단계에서 정한 것(AI 판단, 6.2):

25. **파티션은 `occurred_at`의 일 단위(UTC)로 그대로 둔다.** `received_at`으로 나누면 이벤트 시각으로 하루를 보는 리포트가 여덟 파티션을 읽고, 보관 기간도 받은 시각으로 지워진다.
26. **리포트의 기간은 늘 `occurred_at`의 반열린 구간으로 거른다.** 파티션 키에 형 변환이나 함수(`::date`, `at time zone`)를 씌우면 가지치기가 되지 않아 모든 파티션을 읽는다(확인함). A3는 UTC 하루로 보고, 한국 시각의 하루는 두 파티션이 맞다. 리포트는 이름 없는 문장으로 보낸다(일반 계획은 실행 때 가지를 쳐도 모든 파티션을 잠근다).
27. **기본 파티션은 계속 두지 않는다.** 있으면 파티션을 붙일 때마다 기본 파티션을 잠그고 훑으며, 그 날의 행이 있으면 새 파티션을 만들 수 없다(확인함).
28. **관리 작업은 소유자 명령 하나(`db:maintain`)이고, 하루 한 번 OS 예약 작업으로 돌린다.** 순서는 만들기(`ATTACH`) → 끊긴 떼기 마무리(`FINALIZE`, 1초) → 떼기(`DETACH … CONCURRENTLY`, 5분) → 남은 표 치우기다. 한 단계가 실패해도 다음 단계를 돌리고 끝에 실패로 끝낸다. 겹쳐 돌지 않게 advisory lock을 잡아 보고, 있는지는 이름이 아니라 `pg_inherits`로 본다. "오늘"은 DB 시각이다. API 서버는 표를 만들지 않고, 받을 기간부터 앞으로 3일까지 붙지 않은 날이 있으면 경고만 한다(리뷰 반영).
29. **생성기는 씨앗과 끝 날로 정해진다.** `event_id`까지 씨앗에서 만들고 시각은 고정한 끝 날에서 재어, 다시 넣으면 모두 중복이다. 받을 기간 밖(지난 90일)은 DB에 바로 넣고, 리허설과 측정은 수집 API로 보낸다.
30. **떼기 리허설은 관리 작업, 일반 DETACH(잠금 대기 한도 없음), 기준선(떼지 않음)을 같은 장면(수집 중 + 오래 도는 리포트)에서 견준다.** 수집의 5xx 수(원인별)와 지연, 떼기가 기다린 시간을 숫자로 남긴다.

3단계에서 정한 것(AI 판단, 6.3):

31. **리포트 설정은 허용 목록이다.** 지표 둘, 차원 다섯(0~2개), 필터(차원별 값 목록, `null`로 값 없음도, AND), 기간(리포트 시간대의 날짜, 90일까지), 단위 넷(`hour`·`day`·`week`·`total`), 시간대 여덟이다. 모르는 필드와 목록 밖의 값은 400이다. 보관 기간 밖이 섞인 기간은 422 `out_of_retention`이다.
32. **SQL에는 코드의 상수 식별자와 매개변수만 들어간다.** 기간을 시각으로 바꾸는 일과 시간 묶음은 PostgreSQL이 한다(`at time zone`, 3인자 `date_trunc`). 둘 다 immutable이라 매개변수여도 계획할 때 가지를 친다.
33. **묶음은 기간 끝에서 늘리지 않는다**(일부만 찬 첫·끝 묶음은 `partial`). 일광 절약 시간이 바뀌는 날의 시간 묶음은 23개나 25개다. 응답에 기간의 모든 묶음(빈 것 포함)과 UTC 오프셋을 함께 준다.
34. **요청한 지표만 센다.** 고유 사용자 수는 원본에서 묶음마다 정확히 센다(`count(distinct)`). 행끼리 더할 수 없고, 기간 전체는 `total`로 묻는다.
35. **리포트는 수집과 다른 연결 풀(4개)에서, 빌린 연결 하나의 읽기 전용 트랜잭션으로 돈다(문장 30초, 잠금 대기 3초, 트랜잭션 안에서만).** 행이 20,000개를 넘으면 잘라 주지 않고 422다. 끝이 최근 7일이면 `provisional`이다(리뷰 반영).
