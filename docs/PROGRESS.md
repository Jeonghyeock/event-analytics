확인한 것:
- 테스트 45개가 로컬(Windows, PostgreSQL 18.6)과 CI(`postgres:18`)에서 통과한다. 테스트가 끝나면 남는 DB는 템플릿 하나다.
- 앱 role은 DML만 한다. 표·인덱스·스키마를 만들 수 없고, 마이그레이션 기록을 읽을 수 없다. 소유자가 뒤에 만든 표와 **파티션**에는 DML 권한이 붙는다(2단계에서 날마다 만들 파티션 대비).
- 변이 시험 두 가지:
  - 풀의 `error` 듣기를 빼면, 쉬는 연결을 끊는 테스트가 "처리되지 않은 오류"로 실행을 깬다.
  - 주소의 `?options=`를 합치지 않으면, 주소로 넘긴 설정이 UTC 고정을 지우는 테스트 두 개가 실패한다.

리뷰에서 나와 고친 것:
- 풀의 쉬는 연결이 끊기면(DB 재시작, `pg_terminate_backend`) 풀이 낸 `error`를 아무도 듣지 않아 서버 프로세스가 죽었다. 리뷰가 버리는 DB로 재현했다. `buildApp`이 듣고 로그만 남긴다. seat-booking에도 같은 빈틈이 있다.
- pg는 주소에 `?options=`가 있으면 `config.options`를 통째로 덮는다. 그래서 UTC 고정이 조용히 사라졌다. 주소의 것을 꺼내 합치고 고정을 맨 뒤에 둔다(같은 설정은 뒤의 것이 이긴다).
- 서버 풀에 연결 대기 한도가 없어, DB에 닿지 않으면 `/health`가 503 대신 멈춰 있었다. 5초로 묶었다.
- 개발 DB를 손으로 옵션 없이 만들면 정렬이 CI와 달라도 테스트(복제 DB)로는 드러나지 않는다. `db:migrate`가 먼저 확인한다.
- GRANT·REVOKE 테스트가 되돌린 뒤에 ACL을 견줘 늘 통과했다. 같은 트랜잭션 안에서 견준다.

로컬과 CI에서 부딪힌 것:
- CI의 소유자 주소 검사가 `main.ts` 주석의 변수 이름에 걸렸다. 검사는 주석까지 본다. 주석을 고쳤고, 그 뒤로는 같은 grep을 로컬에서 먼저 돌린다.
- 공개 저장소 만들기를 auto mode가 막았다. 사용자가 권한을 준 뒤 만들었다.
- `npm audit`의 moderate 4건은 개발용 drizzle-kit 안의 옛 esbuild에서 나온다(seat-booking과 같다).

1·2단계 설계를 위해 미리 확인한 것(버리는 DB에서):
- 파티션 표에는 `event_id`만으로 기본 키를 걸 수 없다(`0A000`). 유일 인덱스가 파티션마다 따로 있어서, 키에 파티션 키가 들어 있어야 같은 키가 같은 파티션에 모인다.
- `CREATE TABLE … PARTITION OF`는 부모 표에 `AccessExclusiveLock`을 건다. 그동안 수집과 리포트가 모두 멈춘다. 따로 만든 표를 `ATTACH PARTITION`으로 붙이면 부모에는 `ShareUpdateExclusiveLock`만 건다(읽기·쓰기와 부딪히지 않음). 2단계에서 쓴다.
- PostgreSQL 18에는 `uuidv7()`이 있다.

### 0단계 — 설명할 수 있어야 할 것

**무엇을 가져왔고 왜 다시 만들지 않았나**

1. 가져온 것은 셋이다. 마이그레이션 실행기와 그 테스트 16개, 소유자·앱 role 나누기, 템플릿을 복제하는 테스트 DB다. 실행기는 주석 말고 그대로다.
2. 이 셋은 seat-booking에서 리뷰와 변이 시험으로 버그를 고친 결과다. 다시 만들면 같은 버그를 다시 밟는다.
   - `CREATE INDEX CONCURRENTLY`와 advisory lock이 서로 기다리는 교착
   - 잠금 대기 한도가 CONCURRENTLY를 매번 실패시켜 INVALID 인덱스만 남기는 것
   - 연결이 끊길 때 프로세스가 죽는 것
3. 이 프로젝트는 2단계부터 파티션을 만들고 떼느라 DDL이 잦다. 그래서 잠금 대기를 1초로 묶는 실행기가 처음부터 필요하다.
4. 바꾼 것은 이 저장소에만 있는 사정 때문이다.
   - advisory lock 번호. 테스트 준비는 같은 서버의 postgres DB에서 잠그므로, 번호가 같으면 두 저장소의 테스트가 서로 기다린다.
   - 새 DB의 정렬. 아래 둘째 질문이다.

**DB를 만들 때 정렬과 시간대를 왜 정해 두나**

1. PostgreSQL의 문자열 정렬은 DB를 만들 때 정하고 바꿀 수 없다. 기본값은 OS의 로캘이다. 이 PC는 `Korean_Korea.949`(Windows), CI는 `en_US.utf8`(Linux, glibc)이다. 같은 `ORDER BY country`가 두 곳에서 다른 순서를 낼 수 있다. OS 라이브러리가 바뀌면 인덱스 순서까지 어긋날 수 있다.
2. PostgreSQL 17부터 있는 builtin 공급자의 `C.UTF-8`은 OS에 기대지 않는다. 코드 포인트 순서로 정렬하고(대문자 → 소문자 → 한글), 대소문자 바꾸기는 유니코드 규칙을 따른다. 그래서 어디서나 같다. 사람이 읽기 좋은 정렬이 필요한 곳만 `COLLATE`로 따로 쓴다.
3. 시간대는 연결마다 정해지는 세션 설정이다. 기본값은 서버를 따르므로 로컬은 Asia/Seoul, CI는 UTC다. 그래서 `'2026-10-27'::timestamptz`나 `timestamptz::date`가 두 곳에서 9시간 다른 결과를 낸다.
4. 이 프로젝트는 파티션 경계와 시간 집계를 UTC로 정했다. 그래서 앱 연결은 UTC로 고정하고, 리포트의 시간대는 쿼리의 인자로 준다. 고정은 실수를 줄이는 장치일 뿐이라, 코드는 시각 글자에 늘 오프셋을 붙인다.

### 1단계 — 설명할 수 있어야 할 것

**"정확히 한 번" 대신 "한 번 이상 + 멱등 저장"을 쓰는 이유**

1. 보내는 쪽은 요청을 보낸 뒤 응답을 못 받으면, 서버가 저장했는지 알 수 없다. 응답이 오는 길에 끊겼을 수도 있고, 서버가 저장하기 전에 죽었을 수도 있다. 둘은 보내는 쪽에서 똑같이 보인다.
2. 그래서 보내는 쪽이 고를 수 있는 것은 둘뿐이다. 다시 보내지 않으면 잃을 수 있다("많아야 한 번"). 다시 보내면 두 번 갈 수 있다("한 번 이상"). 네트워크 너머로 "정확히 한 번 보냄"을 보장하는 방법은 없다.
3. 분석 데이터는 잃는 것보다 두 번 오는 것이 낫다. 두 번 온 것은 받는 쪽이 거를 수 있지만, 잃은 것은 되살릴 수 없다. 그래서 보내는 쪽은 "한 번 이상" 보내고, 받는 쪽은 `event_id`로 걸러 한 번만 저장한다. 저장 결과만 보면 정확히 한 번과 같다.
4. 이 저장소에서 그것을 이루는 것은 셋이다.
   - 기본 키 `(event_id, occurred_at)`와 `ON CONFLICT DO NOTHING`이다. 같은 이벤트가 다시 와도, 한 배치 안에 둘 있어도, 동시에 와도 한 행이다.
   - 배치 하나를 트랜잭션 하나로 넣는다. 503이면 아무것도 저장되지 않았으니 같은 배치를 그대로 다시 보내면 된다.
   - 응답마다 보내는 쪽이 할 일을 정해 두었다(DESIGN 6.1 표). 401에 배치를 지우면 잃고, 400에 다시 보내면 끝이 없다.
5. 한계도 있다. 보내는 쪽이 재전송 때 시각을 새로 만들면 키가 달라 두 행이 된다. 계약은 "처음과 같은 `occurredAt`을 보낸다"이다. 시각은 밀리초로 잘라 저장하므로, 재전송이 마이크로초를 밀리초로 다시 써도 같은 키다.

**파티션 표의 유일 키가 왜 파티션 키를 담아야 하나**

1. PostgreSQL의 파티션 표에는 표 전체에 걸친 인덱스(전역 인덱스)가 없다. 부모에 만든 인덱스는 실제로는 파티션마다 따로 있는 인덱스의 묶음이다.
2. 유일 제약은 인덱스로 지킨다. 그래서 파티션마다 따로 지킨다. 같은 `event_id`가 서로 다른 파티션에 들어가면, 어느 인덱스도 둘을 함께 보지 못한다.
3. 키에 파티션 키(`occurred_at`)가 들어 있으면 이 문제가 없다. 같은 키는 늘 같은 파티션으로 가므로, 파티션 안의 유일성이 곧 표 전체의 유일성이다. 그래서 PostgreSQL은 파티션 키를 빼고 만든 유일 제약을 거절한다(`event_id`만으로 기본 키를 걸면 `0A000`).
4. 대가는 "같은 `event_id`"가 아니라 "같은 `event_id` + 같은 시각"만 거른다는 것이다. 대안은 파티션하지 않은 최근 id 표였다. 200만 건으로 견주니 10% 느리고 184MB가 더 들었다. 그래서 키 쪽을 골랐다(DESIGN 6.1).

### 2단계 — 설명할 수 있어야 할 것

**파티션이 빠르게 만드는 것과 느리게 만드는 것**

1. 빠르게 만드는 것
   - **기간이 좁은 조회.** 계획이 그 기간의 파티션만 읽는다(가지치기). 90일치 98개 가운데 하루면 하나다.
   - **오래된 데이터 지우기.** 파티션을 떼고 지우면 표 하나를 버리는 일이다. 같은 양을 `DELETE`하면 행마다 지우고, 나중에 VACUUM이 그 자리를 치워야 한다.
   - **인덱스가 작다.** 하루치 인덱스는 메모리에 들어가 넣기가 빠르다.
2. 느리게 만드는 것
   - **파티션 키로 거르지 않는 조회.** 모든 파티션을 읽는다. 사용자 한 명의 모든 이벤트가 그렇다. 파티션 키에 함수를 씌워도 그렇다(`::date`, `at time zone`). 가지치기는 `키 연산자 식` 모양의 조건만 쓴다.
   - **계획과 잠금의 비용.** 파티션이 많을수록 계획이 길어진다. 일반 계획은 실행할 때 가지를 쳐도 모든 파티션을 잠근다.
   - **표 전체에 걸친 유일성.** 전역 인덱스가 없다. 유일 키에는 파티션 키가 들어가야 한다(1단계).
   - **파티션을 만들고 떼는 DDL의 잠금.** `CREATE TABLE … PARTITION OF`와 일반 `DETACH`는 부모 표를 통째로 잠근다. 오래 도는 리포트가 하나 있으면 그 뒤에 수집이 줄을 선다. 리허설에서 18초 동안 503이 116건 났다. 그래서 따로 만든 표를 `ATTACH`로 붙이고, `DETACH … CONCURRENTLY`로 뗀다.

**기본 파티션을 왜 두지 않나**

1. 기본 파티션은 어느 파티션에도 맞지 않는 행이 들어가는 곳이다. 있으면 파티션이 없는 날의 이벤트도 조용히 저장된다.
2. 대가는 둘이다(확인함).
   - 새 파티션을 붙일 때마다 PostgreSQL이 기본 파티션을 `AccessExclusiveLock`으로 잠그고, 그 날의 행이 있는지 훑는다. 그동안 기본 파티션으로 가는 쓰기가 멈추고, 기본 파티션이 클수록 오래 걸린다.
   - 기본 파티션에 그 날의 행이 이미 있으면 새 파티션을 만들 수 없다(23514). 행을 옮겨야 한다.
3. 이 프로젝트는 받을 기간(과거 7일~미래 1시간) 밖을 수집이 거절한다. 관리 작업은 7일을 미리 만든다. 그래서 정상이라면 기본 파티션에 들어갈 이벤트가 없다.
4. 파티션이 없는 것은 관리 작업이 멈췄다는 뜻이다. 그때는 조용히 쌓기보다 503 `partition_missing`으로 드러내는 편이 낫다. 보내는 쪽은 503이면 다시 보내므로 이벤트를 잃지 않는다. 서버는 그 전에 경고 로그를 남긴다(받을 기간과 앞으로 3일 안에 빠진 날).

- 스크립트로 TS 파일에 `$${…}`를 넣다가 `String.replace`가 `$$`를 `$` 하나로 바꿔, 매개변수 번호의 `$`가 빠졌다(테스트가 잡음). 바꿀 글자에 `$`가 있으면 `split/join`을 쓴다.
- 합계 묶음의 SQL이 `$2`를 쓰지 않아 PostgreSQL이 그 매개변수의 형을 몰랐다(42P18). 쓰지 않는 열로 `$2`를 둔다.
- 테스트의 "지금"이 실제 날짜면 보관 기간 판단이 날마다 바뀐다. 리포트에 "지금"(`asOf`)을 넘길 수 있게 하고, 봄 일광 절약 시간 테스트는 2027-03-14로 옮겼다.

### 3단계 — 설명할 수 있어야 할 것

**설정을 SQL로 바꿀 때 주입을 어떻게 막나**

1. 설정은 모두 허용 목록이다. 지표·차원·단위·시간대는 정해진 이름 가운데 고르고, 모르는 필드는 거절한다(zod, 400).
2. SQL 글자에 들어가는 것은 코드의 상수뿐이다. 차원 이름은 상수 표(`COLUMNS`)를, 지표는 `METRIC_SQL`을, 단위와 글자 모양은 `UNITS`·`LABELS`를 거친다. 설정에서 온 글자를 SQL에 그대로 붙이지 않는다.
3. 값은 모두 매개변수로 넘긴다. 날짜, 시간대, 필터 값 목록(`= any($n::text[])`)이 그렇다. PostgreSQL은 매개변수를 SQL로 해석하지 않으므로 `x'); drop table events; --` 같은 값도 그저 글자다(테스트: 0행, 표는 그대로).
4. 그래도 남는 위험을 줄이는 둘
   - 리포트는 읽기 전용 트랜잭션에서 돈다.
   - 앱 role은 DML만 할 수 있다(0단계).
5. 시간대를 허용 목록으로 둔 이유는 하나 더 있다. PostgreSQL은 `asia/seoul`이나 부호가 뒤집힌 `UTC+5` 같은 이름도 받는다. 마케터가 뜻한 것과 다른 결과를 조용히 낼 수 있다.

**시간대가 일 단위 집계를 어떻게 바꾸나**

1. "하루"는 시간대마다 다른 구간이다. 한국 시각 10월 27일은 UTC로 10월 26일 15시부터 27일 15시까지다. 그래서 같은 이벤트가 한국 시각으로는 27일, UTC로는 26일에 세어진다. 고정 데이터에서 한국 시각 하루는 4건, UTC 하루는 3건이었다.
2. 일광 절약 시간이 있으면 하루가 24시간이 아니다. 뉴욕은 11월 1일이 25시간(새벽 1시가 두 번), 3월 14일이 23시간(새벽 2시가 없음)이다. 그래서 시간 묶음이 25개나 23개가 되고, 같은 벽시계 글자의 묶음이 둘일 수 있다. 응답은 묶음의 UTC 순간과 오프셋으로 둘을 가린다.
3. 그래서 날짜를 자르는 일은 시간대를 알고 해야 한다. PostgreSQL의 3인자 `date_trunc(단위, 시각, 시간대)`는 그 시간대의 자정·정시로 자르고 일광 절약 시간을 따른다. 기간도 `날짜::timestamp at time zone 시간대`로 그 시간대의 자정을 UTC 순간으로 바꿔 거른다.
4. 이 둘은 변하지 않는 함수(immutable)다. 그래서 시간대를 매개변수로 넘겨도 계획할 때 상수가 되어 가지를 친다. 반대로 `occurred_at::date` 같은 식으로 거르면 세션 시간대에 따라 값이 달라 가지를 못 친다(2단계).
5. 집계 표에도 영향을 준다. UTC 시간 단위로 미리 센 표는 정수 시간 오프셋의 시간대에서만 그대로 하루를 맞출 수 있다. +05:30 같은 곳은 하루의 경계가 시간 묶음의 중간에 걸친다. 4단계에서 정한다.

### 4단계 — 설명할 수 있어야 할 것

**고유 사용자 수는 왜 더할 수 없나**

1. 시간별 사용자 수를 더하면 하루 사용자 수가 아니다. 한 사람이 여러 시간에 오면 시간마다 세어진다. 3단계 고정 데이터에서 시간별 합은 4명, 하루는 3명이었다. 7일 일별 × 플랫폼의 합은 30만인데 실제는 13만이었다.
2. 그래서 집계 표에 사용자 수를 시간별로 적어 두어도 일·주·기간 리포트에 쓸 수 없다. 이벤트 수는 더할 수 있어 시간 집계 표를 일·주로 다시 묶어도 맞다.
3. 미리 세려면 "누가 왔는지"를 남겨야 한다. 사용자 × 시간 표는 원본보다 별로 줄지 않아 버렸다(10장 37). 근사(HyperLogLog)는 더할 수 있지만 쓰지 않는다. 마케터에게 정확한 수를 주려는 것이고, 이 서버에는 `hll` 확장도 없다(10장 7).
4. 대신 원본에서 빨리 센다. `count(distinct)`는 병렬로 나눠 셀 수 없고, 정렬해서 센다. (묶음, 차원, 사용자)로 먼저 묶고 바깥에서 무리마다 행 수를 세면, 안쪽 단계를 해시로 센다.
   - 묶음이 `date_trunc` 식이 아니면(기간 전체 × 캠페인) 안쪽이 병렬 부분 해시 집계가 된다. 90일 캠페인별이 14.8초에서 3.8초가 됐다.
   - 일·시간 묶음은 계획기가 (날, 사용자) 무리 수를 행 수만큼으로 어림해 병렬을 고르지 않는다. 정렬 대신 해시로 세는 만큼만 빨라진다(30일 일별 4.1초 → 3.0초).

**늦은 이벤트를 어떻게 다시 세나**

1. 집계 작업은 워터마크(여기까지 셌다)부터 끝난 시간까지 센다. 그런데 이벤트는 몇 시간·며칠 늦게 올 수 있다. 워터마크 앞의 시간에 들어온 이벤트는 범위로는 다시 세지지 않는다.
2. 그래서 수집이 이벤트를 넣는 같은 트랜잭션에서 그 시간을 `dirty_hours`에 덧붙여 적는다. 같은 트랜잭션이라 이벤트가 커밋되면 표시도 커밋된다. 늦었는지 따지지 않고 배치에 든 모든 시간을 적는다. 늦은 것만 적으려면 "지금"(워터마크)을 언제 쟀느냐에 기대야 해서, 그 사이 작업이 워터마크를 옮기면 놓친다(DESIGN 6.4).
3. 작업은 조각 트랜잭션마다 범위 [워터마크, 조각 끝)의 더러운 시간과, 가장 이른 늦은 시간부터 `chunkHours`만큼을 지우며 가져온다(`delete … returning`). 범위와 가져온 시간을 중복 없는 한 집합으로 지운 뒤 원본에서 INSERT 하나로 다시 센다.
4. 유일 키를 두지 않는 까닭: 유일 키 + `DO NOTHING`이면, 작업이 행을 지우기 전에 같은 시간을 적으려던 수집은 "이미 있음"으로 넘어간다. 작업이 지우고 나면 그 수집의 이벤트는 표시 없이 커밋돼 영영 고쳐지지 않는다. 덧붙여 적으면 커밋 전인 수집의 행은 작업에게 보이지 않아 남고, 다음 작업이 센다(테스트로 재현). `DO UPDATE`면 행을 잠가 맞게 되지만, 지금 시간의 행 하나에 모든 수집이 줄을 선다.
5. 다시 셀 때까지(1분) 집계 표는 옛 값이다. 리포트는 기간 안·워터마크 앞에 더러운 시간이 남아 있으면 `meta.stale: true`로 알린다.

### 5단계 — 설명할 수 있어야 할 것

**퍼널의 순서와 기간을 SQL로 어떻게 보나**

1. 정의부터 정한다. 진입은 사용자의 기간 안 첫 1단계다. k단계는 k−1단계로 고른 순간보다 엄격히 뒤이고, 진입 + 전환 기간 앞인 첫 k단계 이벤트다.
2. SQL은 단계마다 CTE 하나다.
   - `s1`: 기간 안의 1단계를 사용자로 묶어 `min(occurred_at)`(진입).
   - `sk`: `s(k−1)`과 k단계 이벤트를 `user_id`로 조인한다. 조건 `occurred_at > 앞 단계의 순간`이 **순서**, `occurred_at < 진입 + 전환 기간`이 **기간**이다. 사용자마다 그 최솟값을 다음 단계로 넘긴다.
   - 단계마다 행 수를 세면 단계별 사용자 수다.
3. 단계마다 가장 이른 것을 고르면 되는 까닭: 진입이 정해지면 기간의 끝이 고정된다. 앞 단계를 이르게 고를수록 뒤 단계가 고를 수 있는 이벤트가 늘기만 한다. 귀납으로, 어떤 유효한 사슬보다 가장 이른 사슬의 각 단계가 같거나 이르다. 그래서 찾기가 필요 없다. 단계마다 기간을 따로 두면("단계 사이 10분") 이 논리가 깨진다.
4. 고르지 않은 것과 까닭
   - 창 함수로 한 번 훑기: 단계 이벤트 전체를 사용자로 정렬해야 하고(30일 171MB를 디스크에서), 겹마다 무거운 사용자의 나눔을 통째로 담아 디스크에 쓴다(30일 9.3초 vs 조인 2.5초). 조인은 단계마다 그 단계의 이벤트만 해시에 담는다.
   - 아무 시도 기준: 엄격히 앞선 행들 가운데 가장 늦은 진입을 들고 가는 창 함수로 셀 수 있다. 하지만 사용자·시각 정렬이 병목이라 90일 31초다. 첫 진입 기준은 다음 시도를 세지 않아 결제가 절반쯤 된다. 이 차이를 응답과 문서에 이름으로 남겼다.
5. 실행에서 지킨 것 둘
   - 기간 끝 + 전환 기간은 트랜잭션 첫 문장에서 계산해 매개변수로 넘긴다. 문장 안에서 `timestamptz + interval`(STABLE)로 쓰면 계획할 때 가지를 못 친다.
   - 중첩 반복 조인을 끈다. `user_id` 인덱스가 없어 중첩 반복은 안쪽을 거듭 훑는다. 범위 조인 조건의 어림 때문에 계획기가 통계와 상관없이 그것을 고를 수 있다.

**리텐션의 무리를 왜 날마다로 했나**

1. "기간 안 첫 이벤트의 날"로 무리를 만들면, 자주 오는 사용자는 기간 첫날이나 이틀째에 처음 보여 앞쪽 날의 무리에 몰린다. 뒤쪽 날의 무리에는 드물게 오는(기간 안에서 늦게 처음 보이는) 사용자만 남는다. 그래서 무리가 작아지고 1일째 비율이 떨어져 보인다. 생성기는 사용자 20만 명이 고정이고 오는 빈도만 다른데도 1일째가 30% → 14%였다. 정의가 빈도로 사용자를 골라 추세를 만든 것이다.
2. 같은 날의 무리가 `from`에 따라 달라지는 것도 문제다. 화면에서 기간을 바꾸면 같은 날의 숫자가 바뀐다.
3. 날마다 무리(그날 온 사용자 전부)는 `from`과 상관없다. 대신 한 사람이 여러 무리에 들어 행끼리 더할 수 없다. 고유 사용자 수와 같은 규칙이다.
4. 진짜 "새 사용자" 리텐션은 앞 L일에 없던 사용자로 걸러야 한다. 보관 기간이 90일이라 L만큼 앞을 더 읽어야 해서 미뤘다.

  - 이벤트 이름 목록을 못 읽으면 단계를 고를 수 없는데 아무 안내가 없었다. 저장한 설정의 값이 선택지에 없으면 보이는 값과 보내는 값이 달랐다.
  - x축 글자 사이를 첫 두 후보로만 재서, 두 01:00을 빼는 일광 절약 시간이 끝나는 날에 겹쳤다. 가장 좁은 사이로 잰다.
  - 지운 뒤에도 "저장했습니다"가 남았다(실제 브라우저에서만). 알림을 history state로 넘겼고, 목록 갱신이 라우터 이동(transition)보다 먼저 그려져 화면이 옛 주소로 다시 붙었다. 알림을 새로 붙는 화면 바깥의 늘 있는 자리로 옮겼다.
  - 저장하는 사이 원본이 지워지면(PUT 404) 목록을 다시 읽어 보던 결과가 사라졌다. 저장·지우기 뒤 포커스가 body로 빠졌다.
  - E2E의 "지운 뒤 알림" 검사가 헛돌았다. 저장한 뒤 다른 화면을 거쳐 다시 열면 알림이 먼저 사라져, 버그가 있어도 통과한다. 저장한 화면에서 바로 지우는 시나리오를 따로 두고, 알림이 있었는지 먼저 본다.
  - 주소를 URL로 못 읽으면 오류가 입력 전체(비밀번호 포함)를 찍었다. 키 이름만 알린다.

부딪힌 것:
- 고정 `viewBox`를 늘려 그린 그래프가 넓은 화면에서 글자 18px, 폰에서 5px였다. jsdom은 크기를 모르므로 스크린숏을 보고서야 알았다. 실제 너비(ResizeObserver)로 1:1로 그린다.
- 화면 읽기용 구분자(`visually-hidden`, absolute)가 가로로 넘기는 목록 밖에 자리를 잡아 360px 문서가 1,754px로 넓어졌다. 요소마다 오른쪽 끝을 재서 찾았다.
- 포커스 테스트가 파일 전체로 돌 때만 실패했다. 알림이 그려진 뒤 포커스를 옮기는 `useEffect`(그린 뒤 미뤄 돎)보다 테스트의 확인이 먼저였다. `useLayoutEffect`로 그 커밋에서 옮긴다.
- 수정 스크립트(heredoc 안의 템플릿 문자열)에서 정규식의 백슬래시가 빠졌다. 5단계와 같은 교훈이다. 백슬래시가 든 글은 Edit 도구로 고친다.
- CI의 e2e 작업이 한 번은 1분, 한 번은 11분이었다. 브라우저가 쓰는 시스템 라이브러리를 받는 apt 미러가 40kB/s였다. 작업 한도를 15분에서 20분으로 늘렸다.

### 6단계 — 설명할 수 있어야 할 것

**화면이 무엇을 서버에 맡기고 무엇을 직접 하나**

1. 날짜와 시각은 모두 서버에 맡긴다.
   - 서버가 주는 것: 묶음 목록(빈 것 포함)과 글자, UTC 오프셋, 앞뒤가 잘린 묶음(`partial`), "지금"(`meta.asOf`), 리텐션의 "오늘"(`meta.today`), 퍼널의 `windowEnd`, provisional.
   - 까닭: 브라우저의 시계와 시간대는 리포트 시간대와 다르다. 23·25시간인 날, 두 01:00, 주의 시작을 화면이 다시 계산하면 서버와 어긋난다. 화면의 시계로 "진행 중"을 정하면 PC 시계가 틀린 사람에게 다르게 보인다.
   - 예외 하나: 양식의 기본값 "최근 n일"만 `Intl`로 리포트 시간대의 오늘을 읽는다. 검사는 서버가 한다(보관 기간 밖이면 422).
2. 검사는 양쪽이 같은 스키마로 한다.
   - 공유 zod 스키마로 보내기 전에 검사해, 틀린 설정을 양식에서 한국어로 알리고 기본값을 채운다. 서버도 같은 스키마로 다시 검사한다.
   - 응답도 스키마로 검사한다. 어긋나면 그리지 않고 "계약이 다르다"고 알린다(조용히 틀리게 그리지 않는다).
   - 저장한 설정은 열 때 지금의 스키마로 다시 검사한다. 서버의 `valid`와 둘 다 맞아야 연다.
3. 화면이 직접 하는 것은 보이는 방법이다.
   - 행을 계열로 펼친다. 차원 값의 짝이 키이고, `null`은 "(없음)"이라는 값이다.
   - 상위 5개 + 기타. 이벤트 수만 더한다. 고유 사용자 수는 더할 수 없어 기타의 사용자 수는 비운다.
   - 전환율과 리텐션 비율을 나눈다(0/0은 "—").
   - 색은 계열을 따라간다(다시 세어도 남은 계열은 같은 색). 축 글자는 다듬기만 하고 겹치지 않을 만큼 고른다.
   - "진행 중"·"아직 오지 않음"은 묶음 시작과 서버의 `meta.asOf`를 견줘 정한다. 견주기만 하고 시각을 만들지 않는다.
4. 서버 상태는 TanStack Query 캐시에만 둔다.
   - 결과와 그 결과를 만든 설정을 함께 둔다. 다시 세는 동안 앞의 결과를 흐리게 보이는데, 그 사이 양식이 바뀌어도 표와 그래프가 어긋나지 않는다.
   - 같은 설정으로 다시 "보기"는 키가 같아 저절로 묻지 않으므로 `refetch`한다.
   - 저장하는 것은 다 센 결과의 설정이다. 그래서 양식의 상태를 화면 위로 끌어올리지 않아도 된다.
